(c) 最終来院閾値

last_visit_bucket は SQL の CASE 式で分類（days_since_last_visit = EXTRACT(DAY FROM NOW() - MAX(mr.date))）:

CASE
  WHEN MAX(mr.date) IS NULL THEN 'no_visit'
  WHEN EXTRACT(DAY FROM NOW() - MAX(mr.date)) < 90  THEN 'within_3m'
  WHEN EXTRACT(DAY FROM NOW() - MAX(mr.date)) < 180 THEN 'over_3m'
  WHEN EXTRACT(DAY FROM NOW() - MAX(mr.date)) < 365 THEN 'over_6m'
  ELSE 'over_1y'
END AS last_visit_bucket

実装根拠: ltv_repository.go:164-170（バケット名定数 :18-24）

→ 「add=fatal」は主経路（1系統）でおおむね成立するが、「remove=non-fatal」はクリーンアップ系（2系統）とエラーカウンター補助（3系統）に限られ、通常の同期パスでは remove も fatal。q&a 回答文の一様な一般化は不正確。なお (a) の通り Write API 自体が現在 no-op のため、上記の fatal/non-fatal 分岐は現状すべて到達不能（Write API 再有効化後にのみ意味を持つ）。
