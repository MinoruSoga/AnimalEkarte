SELECT pg.id, pg.clinic_id, pg.name, COUNT(DISTINCT sp.staff_id) AS assigned_staff
FROM permission_groups pg
LEFT JOIN permission_group_rules r ON r.group_id = pg.id AND r.deleted_at IS NULL
LEFT JOIN staff_permission_groups sp ON sp.group_id = pg.id
WHERE pg.deleted_at IS NULL
GROUP BY pg.id, pg.clinic_id, pg.name
HAVING COUNT(r.id) = 0
ORDER BY pg.clinic_id, pg.id;

7-1 既存集計3項目の仕様

対象は顧客集計 API（GET /api/v1/clinics/:clinic_id/owners/aggregations、backend/internal/lstep/aggregation_handler.go）が返す集計値。集計元 SQL は backend/internal/owner/ltv_repository.go の FindOwnerLTV。

(a) 年間定義・合算・CSV

年間定義は指標ごとに異なり、統一されていない。

  • annual_visit_count（年間来院回数）: 直近365日ローリング固定。パラメータで変更不可。 
    COUNT(DISTINCT CASE WHEN mr.date >= NOW() - INTERVAL '365 days' THEN mr.date END) AS annual_visit_count
    実装根拠: ltv_repository.go:157
  • annual_amount（年間売上）: 暦年（calendar_year）または明示的な期間指定に依存し、指定なしなら全期間。ローリング365日ではない。優先順位は From/To（明示日付）→ Year（暦年 1/1〜12/31）→ PeriodPreset（last_3_months/last_6_months/last_12_months/calendar_year）→ 指定なし（全期間）。last_12_months プリセットのみが「直近12ヶ月ローリング」に相当。実装根拠: ltv_repository.go:296-339（calculateDateRange）
    → 「直近365日ローリング」は q&a 回答文が想定する統一仕様としては不正確。実際は annual_visit_count のみローリング365日固定で、annual_amount は別ロジック（暦年/期間指定/全期間）。この乖離自体をクライアントに確認する必要がある。
  • 合算方法: オーナー単位（GROUP BY o.id, ltv_repository.go:185）。オーナーに紐づく全ペットの medical_records を owner_id で JOIN し（:180）、来院回数は COUNT(DISTINCT mr.date) で日付の重複を除去して集計。medical_records.date は type:date（時刻を持たない日付型）のため、同日に複数ペットが来院しても1回とカウント。ペット単位の内訳は本 API のレスポンスに含まれない。実装根拠: ltv_repository.go:156-157, 180, 185、backend/internal/model/medical_record.go:20
  • CSV出力: ListOwnerAggregation ハンドラは c.JSON のみを返し、CSV エンドポイントは存在しない（aggregation_handler.go:106-129）。CSV 出力機能を持つのは別機能（accounting_report_handler.go:78-80 の会計レポート、lstep_tag_summary_handler.go:45-50 の Lステップタグサマリー）で、顧客集計（本項目）には未実装。

(c) 最終来院閾値

last_visit_bucket は SQL の CASE 式で分類（days_since_last_visit = EXTRACT(DAY FROM NOW() - MAX(mr.date))）:

CASE
  WHEN MAX(mr.date) IS NULL THEN 'no_visit'
  WHEN EXTRACT(DAY FROM NOW() - MAX(mr.date)) < 90  THEN 'within_3m'
  WHEN EXTRACT(DAY FROM NOW() - MAX(mr.date)) < 180 THEN 'over_3m'
  WHEN EXTRACT(DAY FROM NOW() - MAX(mr.date)) < 365 THEN 'over_6m'
  ELSE 'over_1y'
END AS last_visit_bucket

実装根拠: ltv_repository.go:164-170（バケット名定数 :18-24）

これとは別に、Lステップ配信（dormant/VISIT 系タグ付与）で使う休眠判定閾値はクリニックごとに設定可能な4段階（DormantThresholds{Stage180, Stage210, Stage240, Stage365}）で、DB 未設定時は既定値 180日/210日/240日/365日（q&a 回答文の「C-1確定値」に一致）。実装根拠: 既定値 = backend/internal/model/dormant_thresholds.go:21-34、クリニック設定からの取得 = backend/internal/lstep/lstep_settings_thresholds.go の GetDormantThresholds、タグ判定（240日以上で cpm_dormant も付与）= lstep_tag_sync_visit_dormant.go:31-45、別系統の VISIT_* タグ閾値（120/180/220/240日、重複付与可）= 同 :94-112。

→ 集計 API 側の last_visit_bucket（90/180/365日、3分類+未来院）と、Lステップ配信側の dormant 閾値（180/210/240/365日、4段階）は別ロジック・別目的であり、日数の境界値も一致しない。クライアントには両者が別物である旨の確認が必要。
7-3 Lステップ API 仕様3項目

対象実装: backend/internal/infra/lstep/tag.go, user.go（Lステップ HTTP クライアント）、backend/internal/lstep/lstep_tag_sync_api.go, lstep_tag_service.go, lstep_lifecycle_service.go, checkup_sync_service_create.go（呼び出し側・いずれも backend/internal/lstep/）。

(a) タグ付与解除

重要な前提: Lステップ Write 系 API は 2026-05-15 頃から一時停止（no-op 化）されており、ファクトシート作成時点（2026-07-16）でも停止継続中。

  • AddTag / RemoveTag（tag.go:18-25, 27-38）、SetProperty（user.go:61-72）は全て [DISABLED] コメント付きで実 HTTP 呼び出しが削除され、lineUserID が空文字の場合のみ ErrUserNotFound を返し、それ以外は常に nil（成功扱い）を返す no-op 実装。
  • AddTagBulk（tag.go:71-79）も同様に [DISABLED] だが挙動が異なる: 単一 lineUserID パラメータを取らず、空文字チェックも存在せず、入力に関わらず無条件に nil を返す（ErrUserNotFound を返す経路は無い）。関数コメントの「空の lineUserIDs は即座に nil を返す」は未実装のコメントのみ。
  • Read 系（GetUserTags / GetUser）は稼働継続中で実際に HTTP GET を呼ぶ（tag.go:40-69, user.go:25-59）。
  • 呼び出し側サービスは no-op を成功と区別できないため、実際には Lステップ上のタグは一切変化していないにもかかわらず、ローカルのタグキャッシュ（lstep_tag_cache 等）は「付与/解除済み」として更新され続ける。UI 上は成功して見えても、LINE 公式アカウント側の友だちタグには反映されない状態。

(b) エラー処理

q&a 回答文の「add=fatal/remove=non-fatal」はコード上、文脈依存で一様ではないため、そのまま正としない。実際の挙動は3系統:

  1. 通常のタグ同期パス（sync/manual 操作）— add・remove 双方とも fatal: applyTagState（失敗時 notifyAPIFailure 後にラップしたエラーを返す、lstep_tag_sync_api.go:108-133。タグキャッシュ更新の失敗のみ non-fatal）／AddOwnerTag（fatal、lstep_tag_service.go:209-212）／RemoveOwnerTag（fatal・ErrUserNotFound のみ冪等成功、:253-259）／applyCheckupTag（AddTag 失敗 fatal、checkup_sync_service_create.go:144-156）。
  2. ライフサイクル系クリーンアップパス（オプトアウト・オーナー削除・ペット死亡）— remove は non-fatal（best-effort）: removeAllTagsFromLstep（ログのみ・継続、lstep_lifecycle_service.go:261-286）／HandleOwnerDeletion（「タグ解除失敗は削除フローを止めない」、:241-259）／removePetDerivedTagsFromLstep（best-effort、:288-313）。
  3. エラーカウンター補助パス — add・remove とも non-fatal（付随処理）: notifyAPIFailure（EXCL_カルテ連携エラー タグ付与の失敗はログのみ、lstep_tag_sync_api.go:135-157）／notifyAPISuccess（EXCL_ タグ解除失敗もログのみ、:163-191）。
→ 「add=fatal」は主経路（1系統）でおおむね成立するが、「remove=non-fatal」はクリーンアップ系（2系統）とエラーカウンター補助（3系統）に限られ、通常の同期パスでは remove も fatal。q&a 回答文の一様な一般化は不正確。なお (a) の通り Write API 自体が現在 no-op のため、上記の fatal/non-fatal 分岐は現状すべて到達不能（Write API 再有効化後にのみ意味を持つ）。

(c) LINE ID 紐付け

LinkLineUserID（PATCH /owners/:id/line-user-id, backend/internal/owner/http_owner.go）の実装:

  • 重複判定: 同一クリニック内で同じ line_user_id が既に別オーナーに紐付いている場合、FindByLineUserID で検出し apperrors.WrapConflict を返す（owner_service_line.go:17-23）。
  • ステータスコード: WrapConflict は resolveErrorResponse で http.StatusConflict（409）にマッピング（response.go:52-54、owner_handler.go:148-151）。
  • 監査ログ: 紐付け成功時、auditSvc.LogLstepOperation で action = "owner.line_id.link"（解除時は "owner.line_id.unlink"）を記録。監査ログ書き込みの失敗は best-effort（警告ログのみ、リンク操作自体はロールバックしない）（owner_service_line.go:28-37）。参考: ConfirmLineID も owner.line_id.confirm を best-effort で監査記録（:40-67）。
→ q&a 回答文の「LINE ID 紐付け=409+監査」は本項目についてはコードと一致することを確認済み。
