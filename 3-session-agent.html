並行化・統合ルール

  • 開始条件: clean local mainのcommit/treeをB0として固定する。dirty mainを検出したら、Aは他ownerのWIPをstash / clean / restore / bulk commitせずHOLDする。
  • main単一writer: Session Aだけがlocal mainとcentral/shared surfaceを変更する。Aの実行中、frontend / infra / 別backend taskを含む他writerは別branch/worktreeを使う。
  • Session B worktree: BはB0から専用worktreeを1つだけ作り、domain-local allowlistだけを変更する。A landing後はnew main tipから再構成し、blind merge / rebaseしない。
  • largest-ready: file・symbol・callerだけでなく、business fact・table・write owner・DI・transaction / lock・route / RBAC / OpenAPI・gate・protected WIPまで非競合な候補だけを並行化する。固定domain順は作らない。
  • central surface: backend/cmd/api/main.go、backend/docs/api.yaml、handler.go、master_routes.go、service.go、repositories.go、route snapshot、OpenAPI drift、lint inventory、manifest、ADR-006、boundary map、BE-refactor.mdとcross-cutting packageはA専有。
  • 共有DB: Docker / DB-backed testはAのglobal leaseで直列化する。-p 1はprocess間の競合を防がず、別worktreeだけでもCompose project・DB・bind mountは分離されない。Docker checkはcontainer sourceとcandidate tree / 対象file hashの一致を証明し、証明できない結果は合格根拠にせず、Aが統合したexact tipで再実行する。
  • origin relation: B0 packetへlocal main / origin main / merge-base / ahead / behindを記録する。diverge中はremote reconciliationを先行するか、local-only authorityとしてremote integrationをHOLDするかを明記し、自動pull / rebase / history rewriteをしない。
  • handoff: base commit、candidate commit / tree hash、path/hunk allowlist、structural / behavior区分、共有面の変更要求、scoped検証結果、未解消事項を必須とする。Aとのtree一致とfixed-tree reviewが揃うまで統合しない。
