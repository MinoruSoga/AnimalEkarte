BE9 backend 再編との整合（2026-07-20 追記）

backend は BE9 により internal/handler|service|repository の3層フラットから ADR-006 の 13 domain package（internal/medicalrecord 等）へ移行中。正本 = BE-refactor.md（進捗・着手前ゲート・申し送り）／docs/architecture/adr/006-backend-domain-package-boundaries.md／file 帰属 = docs/architecture/be9-2a-classification-manifest.csv。全セッション共通ルール:

  • 新規 backend 実装は旧3層へ追加禁止（BE9-2B 発効）。target domain package へ実装する。既存 resource の修正は現在地のまま行ってよい（移動は BE9 batch の仕事。混ぜない）。
  • ファイルの現在地は着手時に manifest で確認する。Issue 本文や本 HTML のパス表記は移行で古くなる（例: exam_type の handler/service/repository は既に internal/medicalrecord へ移動済み）。
  • domain package へ route を追加する場合: route 登録は <domain>.Handler.RegisterRoutes 1本に集約（複数 struct の同名メソッドは OpenAPI drift 検知から静かに脱落する）。route_snapshot.golden・openapi_route_drift_test.go の追随が必須。
  • safety lint は package 非依存（internal/lintscan が internal/** 全走査）。新 package に置いても clinic isolation・audit・N+1 lint の監査対象から外れない。
  • BE9 batch との衝突回避: BE9 側の次バッチ = medicalrecord sub-batch②（checkup/vaccine/prescription/inquiry）。同一 domain の file 群を session と BE9 batch が同時に触らない — 着手前に git log/worktree 状態を確認し、重なる場合は単一 owner に直列化する（BUG-415 の二重実行事故の再発防止）。

S1 — #249 検査機能条件付き

  • legacy 相当 CSV は 1,324,612 行中 1,323,933 行で field ID が空。ID-only pivot は不可。読み取り専用の visibly-unmapped 表示と mapping/backfill review を先に行う。
  • reference range は clinic ownership を DB で強制できる schema にし、species は既存 animal_species_id を正本にする。
  • lab import の自動 commit は最後。初期 auto_commit=false、実機形式確認、代表データの手動照合、権限付き enable、停止・通知・監査を必須とする。
  • #211 の A1+A2/A6 は実装済み。A6 は checkup_type_fields → checkup_types 複合 FK であり、exam_results ではない。残りは USER の DB 適用確認と臨床確認。

依存・実行ルール

  • migration: 作成直前に実ファイル最大+1を再計算する。2026-07-17 に 001_init.sql 単一構成へ統合済み（現在作るなら 002。適用済み 001 の編集は checksum mismatch を生むため禁止 — 詳細は backend/migrations/CLAUDE.md）。#249・#234・#239・#250 を含め、作成と integration は単一担当が直列化する。
  • 並列化: 独立 worktree／checkout と file ownership を使い、単一 integration owner が順に取り込む。S2 owners と #239、S1 examinations と #239 は重なる。同一 dirty worktree で blind git pull しない。
  • 哲学: 要件ごとに一人の責任者と業務目的を確定し、削除→簡素化→高速化→自動化の順で判断する。確認ダイアログを安全装置にせず、二重入力・二重管理を増やさない。
  • 責任者: 公開 Issue から access-controlled 台帳上の一人へ一意に解決できることを開始条件とする。「現場」「担当部門」だけでは着手しない。
  • 横断規約: 仕様機能を推測追加しない。ただし clinic isolation、input validation、audit atomicity、API/docs/type sync、既存 security/verification gate は Issue の書き漏れでも省略せず、先に Issue を修正する。
  • 外部操作: scoped verification のみ自動実行。push、本番操作、credential・billing 変更は明示依頼なしに行わない。

#229 は実装・close 済み。public serializer の非露出は raw grep 件数ではなく contract test で維持する。#99 は旧 ECS 経路撤去、#109 は CI 認証設定の二重管理／サイレント skip 解消として別途追跡する。
