Infra Refactor — ローカル Docker 環境軽量化・是正計画

計測日: 2026-07-11 / 環境: OrbStack 29.4.0 (macOS, ホスト RAM 18GB, VM 上限 9.77GiB 自動割当)
対象: リポジトリ内の Docker 系ファイル全数（compose 4・Dockerfile 4・.dockerignore 2・entrypoint 2・Makefile の docker ターゲット）
ステータス: IR-1〜11 実施済み・IR-12 A案採用済み（2026-07-11） / IR-2 は安全サブセット（build cache + dangling image prune）のみ実施済み・全体 prune と volume/イメージ一括削除は対象外 / IR-7 は任意対応で未着手
残: stage-import 検証は old_db 側前提未整備のため BLOCKED 継続

0. 結論（TL;DR）

メモリは既に軽い。真の問題はディスクと設定腐敗である。 アイドル時のコンテナ合計メモリは約 209MiB（frontend 146 / db 39 / backend 24）で削減余地はほぼない。 一方で、

  • backend コンテナの書込層に Go ビルドキャッシュが 27.2GB 蓄積（GOCACHE 未 volume 化が根本原因）。ホスト側 prune と合わせ約 40〜50GB が回収可能
  • frontend/.dockerignore が .env* を除外しておらず、.env.local / .env.production が本番用イメージに焼き込まれる（衛生違反・確認済み）
  • docker-compose.swagger.yml は存在しない外部ネットワークを参照しており現状起動不能（stale 設定・確認済み）
  • make lint / seed-old-db / stage-import はキャッシュ volume 未共有のため毎回フルダウンロード・フルコンパイル

メモリ対策はピーク時（go build / go test / Vite cold start）のガードレール設置に絞る。

4. 施策詳細

P0 IR-1: backend GOCACHE の volume 化 + 即時回収

変更（docker-compose.yml）:

  backend:
    volumes:
      - ./backend:/app
      - go_mod_cache:/go/pkg/mod
+     - go_build_cache:/root/.cache/go-build

volumes:
+  go_build_cache:
+    name: ekarte-go-build-cache

実施手順:

# 1. compose 変更を適用しつつ、30GB の書込層ごとコンテナを作り直す
docker compose up -d --force-recreate backend

# 2. 回収確認（Containers が 30.41GB → 数百 MB になること）
docker system df
docker ps -s --format "table {{.Names}}\t{{.Size}}"

効果: 書込層 30.3GB を即時解放。以後キャッシュは named volume に載るため、 イメージ rebuild でコンテナを作り直してもキャッシュが消えず、むしろ cold start が速くなる。

運用ルール（再肥大防止）: volume 化してもキャッシュ自体は成長する。月次または volume が 5GB を超えたら:

docker compose exec backend go clean -cache
docker compose exec backend du -sh /root/.cache/go-build   # サイズ確認

リスク: ほぼなし。状態は volume / bind mount に分離済みで、コンテナ再作成時は entrypoint が migration を再実行するだけ（冪等）。 go clean -cache 直後の初回ビルドのみ数分遅くなる。

P0 IR-2: ホスト側 prune 運用

# 1. build cache: 3GB だけ残して削減（−10.9GB 見込み）
docker builder prune --keep-storage 3GB

# 2. 孤児 volume: 一括削除は禁止。他プロジェクトの実データが混在している
docker volume ls -f dangling=true
# → agriterrace-postgres-data / old_db_old_db_postgres_data / server_db-store は
#   他プロジェクトの DB データ。各プロジェクトの要否をユーザーが判断してから個別に:
#   docker volume rm <name>
# 無名ハッシュ volume (1a5f..., 9f8b..., 11e1...) は中身確認の上で削除可

# 3. 不要イメージ: dangling のみまず削除
docker image prune
# 他プロジェクトの大物 (playwright 2.49GB, postgres:16/17, pgadmin4 等) は個別判断で:
#   docker rmi mcr.microsoft.com/playwright:v1.60.0-jammy
禁止: docker system prune -a --volumes の一括実行。 agriterrace / old_db など他プロジェクトの DB volume を巻き添えにする。volume 削除は個別・明示的に行うこと。 （プロジェクト CLAUDE.md 上も docker system prune は自動実行禁止コマンド）

効果: 確実に −10.9GB（build cache）。volume / イメージの個別判断分を含めれば最大 −20GB。 OrbStack はディスクイメージを自動シュリンクするため、prune 後にホストの空き容量へ反映される。

P0 IR-9: frontend/.dockerignore に .env* を追加

事実: frontend/.env.local と frontend/.env.production が実在し、 frontend/.dockerignore はどちらも除外していない。frontend/Dockerfile は COPY . . のため、 make build-prod を実行するとこれらが animal-ekarte-front:latest に焼き込まれる。

# frontend/.dockerignore に追記
+ .env
+ .env.*
+ !.env.production.example

VITE_ 変数はビルド成果物に埋め込まれる前提の公開値だが、「イメージにシークレット類を焼かない」は内容に依存しないベースラインであり、 将来 .env に非公開値が追加された瞬間に事故になる構造を先に塞ぐ。backend/.dockerignore は既に除外済みで、FE だけが漏れている非対称も解消する。

検証: 適用後 docker build -t tmp-fe ./frontend && docker run --rm tmp-fe ls -la /app | grep env で .env.production.example 以外が存在しないこと。確認後 docker rmi tmp-fe。

P1 IR-3: compose メモリ上限ガードレール

現状は無制限で、コンテナ内プロセスが暴走すると VM 上限（9.77GiB）まで食い、ホストの他アプリを圧迫する。

  backend:
+   mem_limit: 4g        # go build / scoped test のピークを考慮して緩めに
  frontend:
+   mem_limit: 2g        # Vite dev + HMR には十分
  db:
+   mem_limit: 1g        # dev 用途の PG18 には十分

検証: スコープ限定テスト（docker compose exec backend go test ./internal/service/...）と フロント通常操作で OOMKill が出ないこと（docker inspect --format '{{.State.OOMKilled}}' animalekarte-backend-1）。

リスク: 上限を攻めすぎると go test が OOMKill され「テストが謎に落ちる」事故になる。 初期値は緩め設定とし、実測してから絞ること。backend を 2g 未満に絞るのは禁止。 make test（go test -race ./... 全件）を Docker 内で回す運用があるため、その日は 4g でも足りない可能性を織り込み、OOMKilled 監視を検証項目に含めた。

P1 IR-4: Go ビルド並列度の抑制

air の再ビルドは保存のたびに CPU 11 コアをフルに使い、コンパイラプロセス群が瞬間的に数 GB 消費する。 dev では並列度を落としてもインクリメンタルビルド主体のため劣化は軽微。

  backend:
    environment:
+     GOFLAGS: "-p=4"      # コンパイル並列度を 4 に制限（既定 = 全コア）
+     GOMAXPROCS: "4"      # ランタイム側も揃える（dev では十分）

検証: 適用前後で air の再ビルド時間を体感比較。cold build が 2 倍以上遅くなるなら -p=6 に緩める。

P1 IR-9': Makefile lint / lint-fix にキャッシュ volume 追加

現状の make lint は使い捨てコンテナで毎回 go module のダウンロードとフルコンパイルを行う。 遅い（数分）だけでなく、ネットワーク負荷とビルドキャッシュ肥大の発生源でもある。

# Makefile
 lint:
 	docker run --rm \
 		-v $(PWD)/backend:/app \
+		-v ekarte-go-mod-cache:/go/pkg/mod \
+		-v ekarte-golangci-cache:/root/.cache \
 		-w /app \
 		golangci/golangci-lint:$(GOLANGCI_LINT_VERSION) \
 		golangci-lint run
# lint-fix / ci-local 内の同一 docker run ブロックにも同じ 2 行を追加
設計判断: /root/.cache（go-build + golangci-lint 両キャッシュの親）は backend dev コンテナと共用しない専用 volume とする。 golangci-lint はバージョン固有のキャッシュ形式を持ち、dev コンテナの GOCACHE と混ぜると invalidation が非決定的になる。 module cache（content-addressable・並行安全）のみ既存 ekarte-go-mod-cache を共用する。 既知の罠「キャッシュ stale による偽 0 件」（ops メモ）があるため、lint 結果が疑わしい時のリセット手順を併記する: docker volume rm ekarte-golangci-cache（次回実行時に自動再作成）。

P2 IR-5: codegen サービスへのキャッシュ共有

codegen は素の golang:1.25-alpine で、実行のたびに tygo と依存 module をダウンロード・コンパイルしている。

  codegen:
    volumes:
      - ./backend:/app
      - ./frontend:/frontend
+     - go_mod_cache:/go/pkg/mod
+     - go_build_cache:/root/.cache/go-build   # IR-1 の volume を共用

リスク: backend との並行書込だが、Go の module cache / build cache は content-addressable + ロック機構ありで並行アクセスに安全。問題なし。

P2 IR-6: healthcheck 間隔の緩和

db / backend / frontend とも interval: 5s で永続的にヘルスチェックが走っている。 起動完了後も 5 秒ごとの wget / pg_isready を続けるのは無駄で、VM の wakeup を増やす。

  # db / backend / frontend 共通
-     interval: 5s
+     interval: 30s
+     start_interval: 5s    # 起動中だけ 5s 間隔

start_period は既存値を維持。start_interval により depends_on: service_healthy の解決速度 （= make up の起動待ち時間）は劣化しない。Docker Engine 25+ / Compose 2.20+ が必要（OrbStack 29.4 は充足）。

P2 IR-8: seed-old-db / stage-import に go_build_cache 共有

両 one-shot サービスは go run ./cmd/... を --rm コンテナで実行するため、 go_mod_cache はあってもビルドキャッシュがなく毎回フルコンパイルになる。IR-1 の volume を共有する。

# docker-compose.seed-old-db.yml / docker-compose.stage-import.yml 共通
  volumes:
    - ./backend:/app
    - go_mod_cache:/go/pkg/mod
+   - go_build_cache:/root/.cache/go-build

override ファイルは docker-compose.yml とマージされるため volume 定義の追記は不要（トップレベル volumes: は本体側の定義を参照する）。 検証: make stage-import-dry-run の 2 回目実行がコンパイル待ちなしで始まること。

P2 IR-10: docker-compose.swagger.yml の是正

事実: 参照する外部ネットワーク animal_ekarte_default は存在しない （docker network ls 実測: 実在は ekarte-network と animalekarte_default）。 つまりこのファイルは現在 network ... not found で起動できない。加えて obsolete な version: '3.9' と未 pin の :latest イメージ 2 本。

- version: '3.9'
  services:
    swagger-ui:
-     image: swaggerapi/swagger-ui:latest
+     image: swaggerapi/swagger-ui:v5.31.4      # 実施時の最新安定版に pin
    ...
    redoc:
-     image: redocly/redoc:latest
+     image: redocly/redoc:v2.5.1               # 同上
    ...
  networks:
    animal_ekarte:
-     external: true
-     name: animal_ekarte_default
+     external: true
+     name: ekarte-network

両サービスは静的ファイル（./docs の bind mount）を配信するだけで backend への接続は不要のため、 ネットワーク定義ごと削除して既定ネットワークにする案でもよい（その場合 networks: セクション全削除）。 どちらでも動くが、削除案の方が KISS に適う。pin バージョンは実施時に docker run --rm <image> --version 等で確認して固定すること。

検証: docker compose -f docker-compose.swagger.yml up -d → localhost:8081 / 8082 表示 → down。

P2 IR-11: backend/Dockerfile.dev の air pin + apk レイヤ統合

tygo を @latest → v0.2.21 に pin した FE6-1 と同じ理由（再現性・突然の breaking change 防止）で air も pin する。 ついでに 2 回に分かれた apk add を統合しレイヤを削減する。

- RUN apk add --no-cache gcc musl-dev tzdata
+ RUN apk add --no-cache gcc musl-dev tzdata curl

- RUN go install github.com/air-verse/air@latest
+ # 再現性のため pin（FE6-1 の tygo pin と同方針）。更新は明示的な bump コミットで行う
+ RUN go install github.com/air-verse/air@v1.63.0   # 実施時に現行安定版を確認して固定

- RUN apk add --no-cache curl && \
-     curl -sSfL https://raw.githubusercontent.com/golangci/golangci-lint/master/install.sh | \
+ RUN curl -sSfL https://raw.githubusercontent.com/golangci/golangci-lint/master/install.sh | \
      sh -s -- -b $(go env GOPATH)/bin v2.11.4

注意: dev イメージ内の golangci-lint v2.11.4 は scoped lint 運用 （docker compose run --no-deps --entrypoint golangci-lint backend ...）で実際に使われているため削除しない。 バージョンは Makefile の GOLANGCI_LINT_VERSION と二重管理になっている点だけ意識すること（bump 時は両方更新）。

検証: docker compose build backend → make up → air ホットリロード動作確認。

P3 IR-12: frontend/Dockerfile と make build-prod の役割再定義 — A案採用・実施済み（2026-07-11）

矛盾の指摘: make build-prod は frontend/Dockerfile を animal-ekarte-front:latest と「本番」タグ付けするが、中身は COPY . . + CMD ["pnpm", "dev"] — つまりdev サーバを起動するイメージであり、本番ビルド（pnpm build → 静的配信）ではない。 実際の本番 FE は Vercel デプロイであり、このイメージが本番導線に乗っている形跡はない。

選択肢（ユーザー判断待ち）:

案内容推奨度
Amake build-prod から frontend 行を削除し、frontend/Dockerfile も削除（YAGNI。本番は Vercel で完結している）推奨 → 採用
Bマルチステージ（build → nginx 配信)に書き直し、名実ともに本番イメージ化するセルフホスト移行計画があるなら
C現状維持 + Makefile コメントで「dev イメージである」旨を明記最小工数だが矛盾は残る

いずれの案でも IR-9（.dockerignore の .env 除外）は先行して適用する。削除判断が付くまでイメージに .env が焼かれる状態を放置しない。

実施結果（2026-07-11）: ユーザー判断により A案を採用。frontend/Dockerfile を削除し、 make build-prod から frontend 行（旧 docker build -t animal-ekarte-front:latest ./frontend）を除去。 build-prod ターゲット自体は backend 用（animal-ekarte-api:latest）として存続する。 開発用の frontend/Dockerfile.dev（compose 参照）は本施策と無関係で変更していない。

P3 IR-7: OrbStack VM メモリ上限の明示設定（任意）

現状 memory_mib: 0（自動 = ホスト 18GB に対し 9.77GiB）。OrbStack は動的返却するため実害は小さいが、 ホストで重い作業と並走させたいなら上限を明示できる:

orb config set memory_mib 6144   # 6GB に制限
orb config set memory_mib 0      # 戻す場合（自動）

注意: IR-3 の mem_limit 合計（4+2+1=7g）より小さくすると VM 全体で先に頭打ちになる。 make test（全件 -race）や make ci-local を回す日は 0（自動）に戻すのが無難。 IR-1〜4 の効果を見てから判断すればよく、初回スコープからは外してよい。
