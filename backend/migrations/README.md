# DBマイグレーションの追加ルール

**今後のDBスキーマ変更は、`001_init.sql`への追記・編集ではなく、新しいマイグレーションファイルを作成して行います。**

- `001_init.sql`は初期スキーマとして保持します。新しい変更を追記したり、後続のマイグレーションを再統合したりしません。
- `001_init.sql`に限らず、一度コミットされたマイグレーションSQLは変更・削除・リネームしません。唯一の例外は、並行採番の衝突で、staging・本番のどちらにも未適用かつ冪等なファイルの番号だけを改名する場合です（ユーザーの明示判断が必要。経緯は [CLAUDE.md](CLAUDE.md) の「リネームの記録」）。既存の定義やマイグレーションの不具合も、新しいファイルで訂正します。
- 新しいSQLは、このディレクトリ直下に`{既存最大番号+1}_{snake_caseの説明}.sql`として追加します。番号はゼロ埋めの連番とし、最新のmainと作業ブランチを確認して重複を避けます。
- 新規ファイルには、現在のスキーマからの差分を記述します。カラム・テーブル・インデックス・外部キーなどの追加、変更、削除が対象です。

適用済みファイルを変更すると、`schema_migrations`に記録されたchecksumと一致せず、既存DBでマイグレーションが失敗します。新規ファイルを追加することで、既存DBには未適用の差分を、新規DBには`001_init.sql`から順に全変更を適用できます。

## 変更時の確認

1. 既存SQLの内容・ファイル名を変えていないことを差分で確認します。
2. 既存データへの影響と、[CLAUDE.md](CLAUDE.md)の医院分離・制約に関するルールを確認します。
3. [migration-seed-safety](../../.agents/skills/migration-seed-safety/SKILL.md)に従い、承認された隔離DBで新規DBへの全適用と既存スキーマからの差分適用を検証します。
4. マイグレーションを含む変更をpullした開発者は、更新後のアプリを使う前に`make migrate`を手動で実行します。エージェントは無断でDBへの適用やリセットを実行しません。

seedデータの変更手順は[CLAUDE.md](CLAUDE.md)を参照してください。

## 025〜027 の STG 適用前統合（2026-10-09、承認済み例外）

ケージ連結の 025 とその訂正 026・027 は、STG 未適用を確認し、ユーザーの承認により 025 に統合しました。最終的な列・医院単位の複合 FK・複合インデックスは同じです。この統合だけを例外とし、通常の既存 SQL の変更禁止は維持します。`001_init.sql` と 028 以降は変更せず、026・027 の欠番は埋めません。

旧 025〜027 を適用済みのローカル DB は、統合後の `make migrate` が 025 の checksum mismatch で停止します。このケースでは、ローカルデータの破棄を確認したうえで、[LOCAL_DB_RESET.md](../../docs/ops/deploy/seeds/LOCAL_DB_RESET.md) に従いユーザーが手動で `make reset` を実行してください。checksum の書換えで回避しません。STG など共有 DB で旧ファイルが適用されていた場合は、この統合を適用せず中止します。

028 の enum 値追加と、その値を使用する 029 のインデックス作成は、migration ごとのトランザクション境界が必要なため分けたままにします。030 の既存データ移行も独立させます。
