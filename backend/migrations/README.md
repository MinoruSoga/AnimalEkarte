# DBマイグレーションの追加ルール

**今後のDBスキーマ変更は、`001_init.sql`への追記・編集ではなく、新しいマイグレーションファイルを作成して行います。**

- `001_init.sql`は初期スキーマとして保持します。新しい変更を追記したり、後続のマイグレーションを再統合したりしません。
- `001_init.sql`に限らず、一度コミットされたマイグレーションSQLは変更・削除・リネームしません。既存の定義やマイグレーションの不具合も、新しいファイルで訂正します。
- 新しいSQLは、このディレクトリ直下に`{既存最大番号+1}_{snake_caseの説明}.sql`として追加します。番号はゼロ埋めの連番とし、最新のmainと作業ブランチを確認して重複を避けます。
- 新規ファイルには、現在のスキーマからの差分を記述します。カラム・テーブル・インデックス・外部キーなどの追加、変更、削除が対象です。

適用済みファイルを変更すると、`schema_migrations`に記録されたchecksumと一致せず、既存DBでマイグレーションが失敗します。新規ファイルを追加することで、既存DBには未適用の差分を、新規DBには`001_init.sql`から順に全変更を適用できます。

## 変更時の確認

1. 既存SQLの内容・ファイル名を変えていないことを差分で確認します。
2. 既存データへの影響と、[CLAUDE.md](CLAUDE.md)の医院分離・制約に関するルールを確認します。
3. [migration-seed-safety](../../.agents/skills/migration-seed-safety/SKILL.md)に従い、承認された隔離DBで新規DBへの全適用と既存スキーマからの差分適用を検証します。
4. マイグレーションを含む変更をpullした開発者は、更新後のアプリを使う前に`make migrate`を手動で実行します。エージェントは無断でDBへの適用やリセットを実行しません。

seedデータの変更手順は[CLAUDE.md](CLAUDE.md)を参照してください。
