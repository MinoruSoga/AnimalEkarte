## 3. 超過分の帰属（ID band 分析）

clinic ID band: 八王子 [0,10M) / 城東 [10M,20M) / 敷島 [20M,30M) / 箱 [30M,40M)。application 採番域は `id ≥ 1,000,000,000`。

- **staffs 以外の全表**: 超過行はすべて `id ≥ 1e9` の application 採番行で、band 内件数は manifest と完全一致。
  - 例: `medical_records` band 内 = 476,174/757,719/118,582/143,701（exp と一致）、`id ≥ 1e9` は 59 行（Δ +18/+36/+5 と一致）。
  - `owners`/`pets` も同様（band 内 = exp、`id ≥ 1e9` が +6/+5 = 11 行ずつ）。
  - 即ち **UAT 利用で新規作成された業務行**（カルテ・会計・予約・ワクチン等）であり、usage evidence の裏付けにもなる。
- **staffs（§4a 参照）**: 移行分は全員存在。超過は demo catalog（`seeds/003_login`）と staff provisioning 由来。

### 4f. STG 接続に関する環境所見

- リポジトリ直下 `.env.staging` の `DB_HOST` は退役済み RDS ホストで **現行 STG へは接続不可**（`docs/ops/infra/staging/runbook.md` §6 の「DB_HOST は陳腐化」と一致）。実測は `scripts/stg-uat-old-db-handoff.local.env` の PlanetScale ephemeral role で実施。チケット手順の「.env.staging creds → psql」は現状そのままでは動かない点を記録しておく。
- RLS: 接続 role（`pscale_api_*`）は `rolbypassrls=false` で clinic 系全表が `relrowsecurity=t` のため、既定では 0 行に見える。計測は session `SET app.bypass_rls='on'` で実施（session 限定・read 用途のみ）。

## 6. 総合評価（両者受入 readiness）

| 観点 | 判定 |
|---|---|
| 移行層の完全性（loaded vs manifest） | **PASS** — 21表 × 4医院 全セルで band 内件数が manifest と一致。減少・欠損・越境・孤児 0 件 |
| 超過分の説明可能性 | **PASS** — 全差分が `id ≥ 1e9` の UAT 業務行 / seedlogin demo / staff provisioning / UAT マスタ追加で説明可能 |
| 会計整合 | **PASS（設計どおり）** — needs_review 隔離による completed>payments、split 親子 1〜2 |
| マスタ/seed | **PASS+** — 期待件数一致 + UAT 追加分のみ |
| 残判断事項 | ① jouto の bundle 版差異（rehearsal vs trusted/最新）② 本番は formal `make csv-import` lane での再実施が前提 ③ 日付異常は source 持越しの説明資料として提示 |

**結論**: STG の移行データは「投入された bundle どおり完全に存在する」状態で、旧システム↔STG の件数突合としては受入可能な状態。残る差分は全て「移行後の正当な追加（UAT 利用・demo・provisioning）」であり、EMR-129 の A 方式（counts reconciliation）としては **GO**。ただし現行 STG は rehearsal bundle 群で構築されており、**本番受入（両者受入）でどの bundle 版を基準にするかは要 USER 判断**（jouto は特に版差が大きい）。

### 付録: 実測クエリの概要（再現用）

- 接続: `psql "host=ap-northeast-2.pg.psdb.cloud dbname=postgres user=<ephemeral> sslmode=require"`、`SET app.bypass_rls='on'` のうえ SELECT のみ。
- 17 表: `SELECT clinic_id, count(*) FROM <t> GROUP BY clinic_id`。
- 4 子表: 親 FK join（`inquiries`/`clinical_plans` → `medical_records`、`estimate_items` → `estimates`、`exam_results` → `exams`）。
- ID band 検査: `count(*) FILTER (WHERE id>=1000000000)` と 10M band 区間。
- マスタ: `002_master` 各表の全件数 + clinic 別内訳。
- expected 出所: `AnimalEkarte/sensitive-local/csv-import-reports/*-stg-uat-apply.json` の `counts`（manifest SHA-256 で old_db 側 manifest 実ファイルと照合済み）。
