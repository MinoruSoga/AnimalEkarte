# EMR-289 — スタッフ無効化/削除時のログインアカウント同一Tx無効化

## 背景 / 症状

ステージングで `staffs.is_active = false` かつ `accounts.is_active = true` の
不整合行が観測され、その account には無効化後もログイン試行が残っていた。
スタッフが無効化・論理削除されても、紐付くグローバルログインアカウントが
生きたまま残るため、認証境界上の資格情報が棚引きと乖離していた。

## 変更内容（スコープ: backend のみ、マイグレーションなし）

`staffs` 書き込みは `staffRepository` が lint 強制された唯一の write funnel
（`staff_table_write_owner_lint_test.go`）。そのため不変条件は
「散在する個別更新」ではなく funnel 内の単一共有ヘルパ
`deactivateLinkedAccountTx` として実装した。

### `backend/internal/staff/staff_repository.go`

- 新規 private helper `deactivateLinkedAccountTx(tx, staffID)`:
  `accounts.is_active = false` を `staffs.account_id` 経由で副問い合わせして
  in-flight tx 上で更新。`is_active = TRUE` 条件付きのため、account 未紐付け・
  既に無効・削除済みの account は no-op。account はグローバル識別のため
  clinic scope を付けない（`001_init.sql` の RLS 設計どおり）。
- `Update`: `IsActive=false` のコマンドのみ
  `persistence.DBOrTx(...).Transaction(...)`（ambient tx 下では SAVEPOINT）で
  `update` + account 無効化を括る。それ以外の更新経路は不変（既存と同一の
  単一 statement）。`permissionGroupRepository.Update` が既に同じ包み込み
  パターンを採用済み。
- `UpdateForReservation`: `IsActive=false` の PatchStatus コマンドのみ
  同じ包み込みで `UpdateScopedByID` + account 無効化を同一 tx に入れる。
- `Delete`: 既存の soft-delete tx 内で、staff 削除成功直後に
  `deactivateLinkedAccountTx` を実行（副問い合わせは `staffs.account_id` を
  参照するため soft delete 済み行からも正しく解決される）。
- 失敗時は GORM の savepoint/tx rollback で両方巻き戻る（テストで検証済み）。

### `backend/internal/staff/staff_provisioning_apply.go`

- プロビジョニング（`staff-provision` CLI）で manifest `is_active=false` の
  スタッフが `accounts.is_active=true` で作成される同種の不整合を出生時点で
  塞ぐため、作成 account の `IsActive` を `entry.IsActive` に合わせる
  （1 行の整合性修正。active 作成時の挙動は不変）。

### `backend/internal/lintscan/dbortx_inventory_lint_test.go`

- `staffRepository.Update` が `persistence.DBOrTx` を使い始めたため
  `dbOrTxParticipatingMethods` に登録（ゲートが要求する明示 allowlist）。

## 再活性化セマンティクス（非対称・意図的）

- スタッフの `is_active=true` は **account を復活させない**。
  account 再有効化は明示的な別操作（seedlogin upsert `apply.go:115-137` や
  運用ツール）に留める。EMR-289 の要求どおり構造的に保証される
  （無効化パスにのみカスケードが存在する）。
- `seedlogin` の upsert は accounts/staffs 双方を同一 SQL tx で再有効化する
  既存の明示経路であり、非対称セマンティクスと整合。

## 認証側の確認（変更なし）

- `internal/auth/auth_service.go:104` — ログインは `account.IsActive` /
  `DeletedAt` を既に拒否している。既存ユニットテスト
  `auth_service_test.go` の "inactive account" ケース
  （`TestService_Authenticate_InvalidCredentialResponsesAreUniform`、
  `TestService_Authenticate_UnknownAndInactiveAccountsPerformOneCost12Comparison`）
  が通ることを確認。timing-safe の dummy-hash 比較も維持。
- `current_access_staff_reader.go` は account+staff 双方の is_active を
  要求 — 片方だけ無効でもセッション経路は閉じる。

## カバーした経路

| 経路 | エントリ | カスケード実現経路 |
|---|---|---|
| 管理画面 スタッフ更新（is_active=false） | `staffService.Update` → `applyStaffUpdateInTx` | `s.repo.Update` → `staffRepository.Update` 内カスケード |
| 管理画面 スタッフ削除 | `staffService.Delete` | `s.repo.Delete` → `staffRepository.Delete` 内カスケード |
| 予約画面 スタッフ公開/担当状態 PATCH | `reservationStaffService.PatchStatus` → `staffsWriter.Update` | `staffRepository.UpdateForReservation` 内カスケード |
| 予約経由 スタッフ削除 | `ReservationStaffDeleter` → `staffService.Delete` | 同上（Delete に委譲済み） |
| seedlogin 重複アカウント退避 | `seedlogin/apply.go:252-261` | 既存実装で accounts/staffs 同一 tx 無効化済み（変更なし） |

## 対象外 / 未カバー経路と理由

- **CSV カットオーバー投入**（`internal/csvimport`）: `staffs` CSV 列は
  `[id, clinic_id, name, license_number, is_active, reservation_visible]` で
  `account_id` を持たない（COPY による一括 INSERT であり既存行の状態遷移
  ではない）。リンク付き staff を import する経路が存在しないため該当なし。
- **`stg-uat-staff-attach`**（`cmd/`）: `account_id IS NULL` の staff への
  synthetic account 付与 + `is_active=true` 付与は staging UAT fixture 専用の
  **付与/活性化** 方向ツールで、無効化経路ではない。
- **`stg-uat-skeleton/ensure.go`**: staff 非リンクの account INSERT（
  `is_active=true`）のみ。staff 無効化を起こさない。
- **`AttachAccountID`**: 未紐付け staff への account 付与（活性化ではない）。
- **マイグレーション**: スコープ外（`backend/migrations/CLAUDE.md` 準拠）。
- **`staffs.account_id` の 1:N 共有**: カラムに UNIQUE 制約はなくモデル上は
  `Account.Staff` hasOne 前提。複数 staff が同一 account を参照する異常データが
  存在する場合、片方の無効化で他方のログインも止まる。現行ドメインでは 1:1
  を前提としており許容と判断（調査結果として記録）。

## テスト

新規 `backend/internal/staff/staff_account_deactivation_test.go`（実 Postgres
testdb、`-race`）:

- `Update` 無効化 → 同一 tx で account 無効化
- `Update` 無効化が ambient tx と共に rollback（部分コミットしない証明）
- `Update` 再有効化は account を復活させない
- account 未紐付け staff の無効化が正常終了
- profile-only 更新は account に触れない
- `UpdateForReservation` 無効化/再有効化（予約経路 PatchStatus 相当）
- `Delete` が同一 tx で account を無効化 + ambient tx rollback 検証

## デプロイ / カットオーバー考慮

- DB 変更なし、後方互換。デプロイ順序制約なし。
- 既存の不整合行（`staffs.is_active=false` かつ `accounts.is_active=true`）は
  本修正で **遡及修復されない**。必要なら運用で:
  `UPDATE accounts SET is_active=false WHERE id IN (SELECT account_id FROM
  staffs WHERE is_active=false OR deleted_at IS NOT NULL) AND is_active=true`
  （実行は別途手順管理）。
