## 1. Backup 取得（計測値）

### 標準 `pg_dump -Fc` が失敗する理由（設計上の挙動）

`pg_dump`（docker `postgres:18-alpine` 内 18.6、server と同 version）は session 冒頭で `row_security=off` を設定し、RLS 対象表を非 owner・非 BYPASSRLS ロールでは「silent subset にせず fail する」。実測: `ERROR: query would be affected by row-level security policy for table "accounts"` で中断。接続ロール `pscale_api_*` は `rolsuper=f, rolbypassrls=f`。STG は public 130 表中 **118 表が RLS enabled**（`FORCE` なし）。

### 採用した代替 backup 手順（リハーサル実施済み・承認記録は未）

1. `pg_dump -Fc --schema-only` → `schema.dump`（DDL・index・constraint・RLS policy を含む完全スキーマ）
2. テーブル毎に新規接続で `SET row_security=on; set_config('app.bypass_rls','on',false)` のうえ `\copy (SELECT * FROM t) TO file WITH (FORMAT binary)`。`app.bypass_rls` は migration `006_accounts_rls_ops_bypass` / `001_init` の ops bypass contract で、全 policy が `bypass_rls()` 直接または `has_clinic_access()` 経由で honor する（実測: bypass off=0 行 / on=全行）。60s 無成長 watchdog + 3 回 retry 付き。
3. sequence 状態: 123 sequences の `last_value`/`is_called` を取得し `setval.sql` 化。

### 計測値

| 項目 | 値 |
|---|---|
| schema dump | **19s** / 788,585 B（custom format・gzip 圧縮） |
| data export 全体 | wall-clock 約 **45 分**（20:13:29–20:58:28 JST。内訳: 初回 run 約 24 分で 46 表完了後に `inquiries` COPY が proxy stall、診断のうえ kill → per-connection 手順へ再構成し resume run が残 84 表 + retry を **1,208s** で完了） |
| data export 純転送ペース | 84 表・約 20 分（stall 除く）。`pets` で 1 回 stall → watchdog が自動 retry し成功 |
| artifact 総量 | **4,881,300,349 B**（schema.dump 788,585 + `data/*.bin` 4,880,502,784 + setval.sql 8,980。manifest/checksum 付随） |
| 行数 | **25,134,269 行 / 130 表**（COPY count 集計） |
| SHA-256 | per-file `SHA256SUMS`（133 entry）を生成。file digest = `a579eec80c860adcc4eb5d2427873f8625c83924f85ab0854311b809edd80f52` |

### 転送リスクの観測

PlanetScale 前面 proxy 経路で大きな COPY stream が不定期に flow-control stall（server=`ClientWrite` 待機・client=read 待機・TCP ESTABLISHED 維持）。対策は「テーブル毎接続 + 無成長 watchdog + retry」で機能した。prod 本番 backup でも同対策を手順化するか、DB 近接 runner/provider snapshot を使うべき。

## 4. 追加観測（managed backup 稼働状況）

- `pscale backup list animalekarte-stg main` で **managed backup が稼働中** を確認: 直近 4 件 success・各 ~1.7B・約 12 時間隔（例: 2026-10-04 10:07 作成 `q00m563wht12`）・**expiry 約 1 日**。retention が短く、cutover 日前後は `protected` 指定か別保持の検討が要。
- `pscale backup restore` は新 branch への restore で、branch 作成は provider provisioning（権限・課金）のため本リハーサルでは未実施。正式手順に採用する場合は承認のうえ新 branch で rehearsal を行う。
- `pscale database dump/restore-dump` は Vitess 専用で Postgres 非対応。

## 5. 正直な制限事項

- データ export は per-table COPY のため**表間の snapshot consistency は非 atomic**（pg_dump 単一 tx snapshot ではない）。FK 検査は load 時 `replica` で迂回済みで件数一致は PASS だが、本番は単一 snapshot（BYPASSRLS ロール下の `pg_dump` か provider snapshot）を使うべき。
- backend アプリを復元 DB に接続する smoke は未実施（schema・data・RLS・sequence 復元と件数一致まで）。
- restore 経路は 2 段手順であり、single artifact `pg_restore` 経路とは別物。
- 期間中の STG 書き込みドリフトは未考慮（export 中の書き込みは別 snapshot）。

## 6. 10/20 本番 backup 手順への推奨

1. **BYPASSRLS 属性の ops ロール**を provision し `pg_dump -Fc` 単一 artifact + 単一 snapshot を可能にする（`app.bypass_rls` GUC は SELECT に効くが `pg_dump` の `row_security=off` 設計には無力）。または table owner ロールでの pg_dump。
2. 代替: PlanetScale managed backup + 新 branch restore を正式手順にし、rehearsal を新 branch で実施（branch provisioning 権限と retention/protected 設定を承認のうえ）。
3. acquisition record の各項目（owner/method/destination/receipt/retention）を go-live 前に記入。現状 runbook の「未記入=HOLD」に該当。
4. 大容量転送 stall 対策（接続分割・watchdog・retry・DB 近接 runner）を runbook 手順へ明記。
5. artifact は repo 外保護領域・圧縮+暗号化・SHA-256・expiry を同日ログへ記録。資格情報は GitHub secrets/`STG_DB_*` 系統を正本とし `.env.staging` の陳腐化注意書き運用を継続。
