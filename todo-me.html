P0 — 今すぐ（CI/デプロイ解錠）2 タスク

Phase 5 のコード実装（4a9ad331）は完了済み。この2件を実施するだけで STG の CI/CD が Cloudflare 経路へ切り替わる。他タスクの前提にはならないため、依存なしで即着手可能。

GitHub Secrets 登録（CLOUDFLARE_API_TOKEN 他）

CI（backend-deploy.yml）が wrangler deploy でデプロイできるよう、Repository Secrets に4つの値を登録する。

前提

Cloudflare ダッシュボードで デプロイ専用の最小スコープトークンを新規発行すること（STG検証で使った統合トークンをそのまま使い回さない）。スコープ目安: Workers Scripts Edit / Workers Containers Edit / Account Settings Read。

手順

  1. Cloudflare ダッシュボードで CI 用 API Token を新規発行（上記スコープ）
  2. 以下を登録（値はプレースホルダ。実値はシェル履歴に残さないよう先頭スペースかヒアドキュメントを使う）: 
    gh secret set CLOUDFLARE_API_TOKEN --repo <owner>/<repo>
gh secret set MIGRATE_RUN_SECRET --repo <owner>/<repo>   # wrangler secret put 投入時と同一値
gh secret set STG_DEMO_EMAIL --repo <owner>/<repo>      # 任意（P5-4 optional smoke 用）
gh secret set STG_DEMO_PASSWORD --repo <owner>/<repo>   # 任意

完了条件

CLOUDFLARE_API_TOKEN / MIGRATE_RUN_SECRET の必須2件（+ 任意2件）が Repository Secrets に登録済み。

関連: infra/cloudflare/README.md §CIデプロイ

CI デプロイ2回連続成功の確認

Secrets 投入後、通常デプロイとマイグレーション込みデプロイが2回連続で成功することを確認する。External write境界のため人間承認後に実行。

前提

P5-2 完了（Secrets登録済み）。未設定のまま実行すると Verify Cloudflare credentials / Run database migration ステップが明示的に fail する設計（サイレント成功はしない）。

手順

gh workflow run backend-deploy.yml --ref staging
# 完了を待って結果確認
gh run list --workflow=backend-deploy.yml --branch=staging --limit 1
gh run view <run-id> --log-failed   # 失敗時のみ

# 直後にもう一度実行し、migrate ステップが冪等（exit 0）で成功することを確認
gh workflow run backend-deploy.yml --ref staging

完了条件

2回連続で backend-deploy.yml が成功（migrate ステップは2回とも exit 0＝冪等）。

関連: infra/cloudflare/README.md §CIデプロイ検証

P1 — インフラ apply（承認境界）2 タスク

コードは準備済み。terraform apply と git push は External write 境界のため、内容確認と明示承認が必要。

通知ポリシー（cloudflare_notification_policy）の apply

infra/cloudflare/notifications.tf は terraform validate/plan まで完了済み（1 to add, 1 to change＝無関係なHyperdrive credential drift, 0 to destroy）。apply には運用担当者の実メールアドレス供給と明示承認が必要。

前提

  • notification_email 変数は default 無し（未供給時は plan が変数未設定エラーで意図的に失敗する設計）
  • Cloudflare の通知メール送信先はダッシュボードの Notification Settings で確認リンク経由の事前検証が必要な可能性がある（未検証の制約。terraform plan では検出できない）

手順

export TF_VAR_notification_email="<運用担当者の実メールアドレス>"
cd infra/cloudflare
terraform plan -out=tfplan   # 内容を確認
# ここで承認者自身が確認・承認
terraform apply tfplan
# apply後、送信先メールに確認リンクが届いていればクリックして検証を完了する

完了条件

terraform apply 成功。送信先メールアドレスが verified 状態になっている（要ダッシュボード確認）。

関連: infra/cloudflare/README.md §P6-3 通知ポリシー apply の前提 / migration-cloudflare.md Phase 6

ローカル main を origin へ push（明示承認時のみ）

Phase 5/6 の実装コミットがローカル main に積まれた状態で origin 未反映（4a9ad331 等）。push は External write 境界のため、内容レビュー後の明示承認が必要。

手順

git log origin/main..HEAD --oneline   # push対象コミットをレビュー
# 承認後
git push origin main

完了条件

git log origin/main..HEAD が空になる（origin/main がローカル main に追従）。

P2 — Phase 7 前 Go/No-Go4 タスク

PlanetScale ログ機能の同等性確認（RDS CloudWatch Logs代替）

現行 RDS の enabled_cloudwatch_logs_exports=["postgresql"]（クエリログの CloudWatch Logs エクスポート）に相当する機能が PlanetScale 側にあるかを実機確認する。CloudWatch依存6項目の棚卸しで唯一未検証・代替不能と判定された項目。

前提

運用原則によりダッシュボード操作は本来避けるべきだが、PlanetScale のログ/Insights 機能はダッシュボードでの目視確認が前提（Terraform/CLIで代替できない）。

手順

  1. PlanetScale ダッシュボードで animalekarte-stg データベースのクエリログ/Insights 機能を確認
  2. RDS の CloudWatch Logs エクスポートで確認していた項目（スロークエリ・接続ログ等）が同等に取得できるか判定
  3. 結果を migration-cloudflare.md §9 リスク登録簿に追記

完了条件

同等性 PASS/FAIL の判定が記録され、FAIL の場合は代替運用（監視ツール追加等）の要否が判断されている。

関連: migration-cloudflare.md 「2026-07-07 Phase 6 残件」P6-5 対応表

DB データ移行リハーサル + 本切替（RDS → PlanetScale）

private RDS への接続経路が必要なためエージェント単独では未実施。凍結ウィンドウ内でリハーサル→本切替を行う。

前提
