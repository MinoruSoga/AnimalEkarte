# BUG-030: マスタ削除時の依存チェック未実装（サービス種別/スタッフ/ケージ）

## 種類
バグ（バックエンド — 削除時の依存データチェック未実装）

## 重要度
高

## 発見日
2026-03-28

## 再現手順
### サービス種別（500 エラー）
1. `/settings/service-types` で既存のサービス種別（予約データが紐付いているもの）の「削除」をクリック
2. 削除確認ダイアログで「削除する」をクリック

### スタッフ（依存データありでも削除成功）
1. `/settings/staffs` でシフト・予約データが紐付いているスタッフの「削除」をクリック
2. 削除確認ダイアログで「削除する」をクリック

### ケージ（入院データありでも削除成功）
1. `/settings/cages` で入院データが紐付いているケージの「削除」をクリック
2. 削除確認ダイアログで「削除する」をクリック

## 期待動作
- 依存データが存在する場合は「このサービス種別は予約データで使用中のため削除できません」等のエラーメッセージを返す
- バックエンドが HTTP 409 Conflict を返し、フロントエンドにエラートーストが表示される

## 実際の動作
- **サービス種別**: FK制約違反で HTTP 500 Internal Server Error（適切なエラーハンドリングなし）
- **スタッフ**: HTTP 204 で削除成功（FK制約・依存チェックなし）。既存の doctor_id 等が孤立
- **ケージ**: HTTP 204 で削除成功（FK制約・依存チェックなし）。入院データの cage_id が孤立

## 影響
- スタッフ削除時: 既存の予約・シフト等の doctor_id/staff_id が孤立し、データ不整合が発生
- ケージ削除時: 入院データの cage_id が孤立し、データ不整合が発生
- サービス種別削除時: サーバーエラーが発生しUIにエラーが表示されない（UX不良）

## 修正方針
### バックエンド（3箇所共通）
- 各マスタの DELETE ハンドラで、削除前に依存データの存在確認を実施
- 依存データがある場合は `errors.ErrConflict` を返し HTTP 409 Conflict でレスポンス
- `backend/internal/service/` の各 service に依存チェック処理を追加

### フロントエンド
- HTTP 409 Conflict を受け取った場合に適切なエラートーストを表示

## 対象ファイル（推定）
- `backend/internal/service/service_type_service.go`
- `backend/internal/service/staff_service.go`（または masters_service.go）
- `backend/internal/service/cage_service.go`（または masters_service.go）
