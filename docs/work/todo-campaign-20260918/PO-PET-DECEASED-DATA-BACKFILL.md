# PO-PET-DECEASED-DATA-BACKFILL: 死亡日限定訂正の机上計画

状態: **机上設計のみ**。実データの読取・件数集計・訂正、DB 操作、migration、STG/本番での検証、医院 UAT は未実施。

## 根拠と適用境界

- [現行課題](../../../todo-issue.md#po-pet-deceased-data-backfill) は、根拠のある死亡日だけを訂正し、根拠のない個体を残件として維持する方針を示す（現行 `todo-issue.md:73-75`）。[修復計画](../../../bug.md#plan-po-pet-deceased-data-backfill) は、PO の定義、承認後の読取集計、dry-run、監査、復旧、医院別照合を要求する（`bug.md:380-389`）。既存メモの件数は現在の件数ではない。
- 旧 `old_db/sql/migration/030_stage.sql:445-455` は、`deceased_date IS NOT NULL` **または** `life_status_kbn IN ('2','02','9','09')` なら stage `status='deceased'` とする。一方、`deceased_at` は `deceased_date > '1900-01-01'` の場合だけ日時へ変換し、それ以外は `NULL` とする。したがって死亡フラグのみ、または非 NULL の番兵日付からも `status='deceased', deceased_at=NULL` が生じる。この SQL の変換結果だけでは実際の死亡日時の根拠を証明できない。
- stage `pets` は `clinic_id`, `owner_id`, `source_table`, `source_pk`, `legacy_owner_no`, `legacy_pet_no`, `migration_run_id`, `mapping_status` を保持する（旧 SQL `:392-418,420-425,456-479`）。`owner_key` 欠落、個体と飼主の旧医院枝番不一致などは `needs_review` であり、自動訂正対象にしない（同 `:466-479`）。現行 [AE pets CSV 契約](../../../backend/internal/csvimport/cutover_contract.go) は `clinic_id`, `owner_id`, `status`, `deceased_at` を含む（`:203-209`）。`source_table/source_pk` は stage 側の照合情報であり、AE pets CSV の列ではない。
- 本票は死亡ガードの製品修正を再開しない。実際の対象医院、環境、正本、日付原票、対象個体、現在件数は **UNKNOWN**。旧 SQL の `clinic_id=1` を対象医院の決定や全医院への適用根拠にしない。
- 旧 DB の `old_db/docs/migration/data-migration-column-target-checklist.csv:46` は `PetLorD_Kbn=3` を「不明・要確認」と記す。現在の stage SQL は日付 NULL で `3/03` なら `alive` に落ちる。これは死亡判定の正本が未確定であることを示す差異として扱い、この票から `alive` への訂正や死亡日補完を指示しない。現行 [臨床 write ガード](../../../backend/internal/sharedkernel/pet_not_deceased.go) は `status=deceased` または `deceased_at` 非 NULL を拒否する（`:16-29`）。

## 合成ケースと判断規則

以下は実在個体・実件数を表さない。`有効日` は旧 SQL の `>1900-01-01` 条件を満たすだけであり、訂正の採用には個体と日付を結ぶ独立した原票・正本の確認がさらに必要である。

| 合成例 | 旧 `deceased_date` / `life_status_kbn` | stage の帰結 | 訂正判断 |
|---|---|---|---|
| E1 根拠あり | 有効日 / 死亡コード | `deceased` / 旧日付由来の日時 | 医院・個体・飼主・原票が一意に一致し、PO 承認済みなら現値との差分候補。原票日を推測で変えない。 |
| E2 フラグのみ | NULL / 死亡コード | `deceased` / NULL | 死亡表示と新規 write 拒否を維持。日付は作らず、日時不明として要確認。 |
| E3 番兵日付 | `1900-01-01` 以下 / 死亡コードまたは非死亡コード | 非 NULL 日付なら `deceased` / NULL | 番兵を死亡日とみなさず要確認。フラグ非死亡でも SQL の非 NULL 条件で `deceased` になる。 |
| E4 矛盾 | 有効日 / 非死亡コード、または原票と stage/AE の日付が異なる | SQL 上は `deceased` / 旧日付由来の日時 | どちらが正本か未決なら更新停止。差異と各根拠を別記し、PO 判断へ渡す。 |
| E5 重複系譜 | 同じ旧個体が複数 stage/AE 候補へ結び付く | 行ごとの変換値だけでは帰属不能 | `source_table/source_pk`, 旧個体番号、run、AE 側対応を照合し、一意化まで全候補を除外。 |
| E6 訂正済み | 根拠日と現行 AE 値が一致 | 追加差分なし | idempotent skip。監査上はスキップ件数にのみ計上し、更新しない。 |
| E7 医院・飼主不一致 | 日付の有無を問わず `clinic_id`/owner/旧医院枝番が不一致 | stage `needs_review` の可能性 | 対象医院・個体・飼主が同一系譜と証明されるまで停止。別医院への書込みを許さない。 |
| E8 状態不明コード | NULL / `3` または `03` | 現行 SQL では `alive` / NULL | 旧列判断表との不一致を別バケットへ隔離。PO の死亡判定正本が確定するまで生死・日付を訂正しない。 |

`life_status_kbn` の死亡コードは死亡**状態**の根拠候補であり、死亡**日付**の根拠にはしない。日付が欠けるときに現在日時を代入せず、全件を `alive` に戻さない。既存の `status='deceased'` と死亡 write 拒否は維持する。複数の候補・矛盾・既存の手修正がある行は、一律上書きせず個別の承認待ちにする。

## 将来の承認後 read / dry-run

1. PO が死亡判定の正本、日時不明の表現、対象環境、単一の対象医院、対象期間と原票の権限、氏名で特定した修復責任者を確定する。読取担当・保存先・アクセス期間を承認し、原票や個体識別子はアクセス制限下に置く。共有報告には医院別・証拠区分別の匿名集計と証拠参照だけを残す。
2. 読取専用で、対象医院の AE 個体と旧 `source_table/source_pk`・`legacy_pet_no`・`migration_run_id` を対応させる。旧個体→stage→AE、stage owner→AE owner の一意性、`clinic_id`、飼主の医院、旧医院枝番を照合する。欠落・重複・医院越境・`needs_review` は更新候補から除外する。別医院の同番号を同一個体とみなさない。
3. 旧 `deceased_date` と `life_status_kbn` を別々に読取り、旧 SQL の状態・日時変換を再現する。重複・医院/飼主不一致を先に隔離し、残りを根拠ありの変更候補、日時不明/番兵、矛盾、状態不明コード、訂正済み skip の**排他的な最終区分**へ割り当てる。根拠原票の発行者・日付・個体との結び付きが確認できない場合は日時不明に残す。分類前後の候補数を医院別・区分別に照合し、分類不能や件数不一致なら停止する。
4. dry-run は個体ごとに、医院、証拠参照、現行 `status/deceased_at` と提案値、変更理由、除外理由、予定監査イベント、復旧用の変更前値を制限付き出力へ記録する。訂正済み行は skip として明示する。実識別子・原票本文を共有台帳へ転記しない。対象集合と差分の固定版に対して、修復責任者と承認者が適用前に明示承認する。

## 将来の適用・監査・復旧ゲート

- 適用は**別承認のデータ操作**。対象環境・医院・固定した dry-run 差分・更新可能な個体集合を限定する。各行の `clinic_id`, pet/owner 系譜、旧値またはバージョンを同一トランザクション内で再検証し、並行更新で値が変わった行は停止・再調査する。根拠のない日付や別医院の行に波及させない。
- 変更と同じ整合性境界で、既存の死亡状態変更監査を迂回せず、変更前後・根拠参照・実施者・承認参照を `audit_logs` など PO/実装で確定した監査 sink に残す。監査記録失敗時の更新確定は許さない。実際の sink とトランザクション境界は実施手順で確認する。
- 再実行時は既に提案値と一致する行を skip し、差分・監査を重複させない。部分失敗時は医院単位で処理を停止し、変更前値・監査参照・バックアップに基づく復旧/補償手順を責任者が承認する。復旧でも別の並行変更を上書きせず、対象行と条件を再照合する。
- 適用後は医院別・証拠区分別に、対象、更新、skip、除外、未解決、競合、監査、復旧の件数を突き合わせる。対象集合 = 更新 + skip + 除外/未解決 + 競合等の排他的帰属を確認し、予約の死亡 write 拒否結果も合成・承認済みの範囲で別途照合する。未解決の件数・担当が残る限り、データ訂正全体を完了扱いにしない。
