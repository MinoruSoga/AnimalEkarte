### 0.1 連携の基本責任分担

```
カルテシステム：判定する場所
  ・顧客状態（CPM、上位20%、休眠予備軍）の判定
  ・健診/予防/専門検診の履歴管理
  ・売上・来院・会計の管理

Lステップ：配信する場所
  ・カルテからのタグを受け取る
  ・タグを使ってセグメント配信
  ・ファネル分析・クロス分析を実行

突き合わせ：効果を見る場所
  ・配信履歴と来院履歴の突き合わせ（四半期実施）
```

Lステップで顧客状態を再計算しない。カルテで判定した結果を Lステップにタグとして渡す設計。

## 2. 連携アーキテクチャ

### 2.1 タグ連携方式

カルテイベント発生時、カルテ BE で対象者・状態を判定し、Lステップ API でタグを付与・解除する。

```
カルテイベント発生
  -> カルテ BE で対象者・状態を判定
  -> Lステップ API でタグ付与・解除
  -> Lステップ側のタグ条件でシナリオ起動・停止・配信制御
```

- カルテ側の診療データをそのまま Lステップに渡す方式ではない。
- 自動配信の本文・シナリオ順序・配信タイミングは Lステップ側で管理。

### 2.2 個別メッセージ送信方式

```
カルテ画面でスタッフが送信操作
  -> カルテ BE
  -> LINE Messaging API Push Message
  -> 飼い主の LINE に個別送信
```

- Lステップ API 経由ではなく、LINE Messaging API 直送。
- PDF・画像はファイル本体ではなく、アクセス可能な URL をメッセージに含める。

### 2.3 配信制御の責任分担

| 領域 | 責務 |
|------|------|
| カルテ側 | イベント検知、対象者判定、Lステップタグの付与・解除、Messaging API 個別送信、監査ログ |
| Lステップ側 | タグ条件に基づくシナリオ起動・停止・配信順序・配信本文・配信タイミング |

Lステップの「1人に対して複数シナリオを同時に走らせにくい」制約は、カルテ側がシナリオ枠を直接使わずタグ操作に限定することで回避する。

## 4. 連携タグ一覧（仕様書 §3-1）

正本仕様書は「合計23個」と記載しているが、列挙されているタグは 24 個（5+2+4+2+1+7+3）である。
タグ総数の正式表記は SPEC-002 Q1 のタグ命名方式確認と合わせて確定する。

### 4.1 タグ名の命名方式

新仕様書（2026-04-30 受領）は接頭辞方式（CPM_、LTV_、VISIT_、PET_、HLTH_、PREV_、EXCL_）を採用する。

```
【CPMステージタグ】（5個）
CPM_01_出会い
CPM_02_これから
CPM_03_コア
CPM_04_スポット
CPM_05_ノア

【LTV関連タグ】（2個）
LTV_上位20
LTV_フード購入あり

【来院・休眠タグ】（4個）
VISIT_120日超
VISIT_180日超
VISIT_220日超
VISIT_240日超

【動物種タグ】（2個）
PET_犬あり
PET_猫あり

【年齢区分タグ】（1個）
PET_シニア対象

【健診・予防タグ】（6個）
HLTH_健診あり
HLTH_健診未受診
HLTH_年4回候補
PREV_ワクチン期限
PREV_フィラリア未完了
PREV_ノミダニ対象

【管理タグ】（3個）
EXCL_配信停止
EXCL_配信注意
EXCL_カルテ連携エラー
```

接頭辞方式採用の理由:
- Lステッププロプランのクロス分析機能でタグを探しやすくする
- 配信時のセグメント条件を整理しやすくする
- 将来タグが増えた時も管理しやすい構造を維持する

### 4.2 タグ付与ルールサマリー

| カテゴリ | タグ | 付与タイミング | 保持ルール |
|----------|------|--------------|------------|
| CPM | CPM_01〜CPM_05 | 日次バッチ or 来院完了後 | 同時に1つのみ保持（排他） |
| LTV | LTV_上位20 | 月次バッチ | 対象外になったら解除 |
| LTV | LTV_フード購入あり | 日次バッチ | 365日以内に再購入なければ解除 |
| VISIT | VISIT_120日超〜240日超 | 日次バッチ | 来院復帰時に全解除。段階タグは重複付与可 |
| PET | PET_犬あり / PET_猫あり | ペット登録・更新・死亡 | 生存ペット構成で再計算（非排他） |
| PET | PET_シニア対象 | 日次バッチ | 7歳未満になることはないため基本保持 |
| HLTH | HLTH_健診あり / HLTH_健診未受診 | 日次〜月次バッチ | 排他制御 |
| HLTH | HLTH_年4回候補 | 月次バッチ | 条件非該当になったら解除 |
| PREV | PREV_ワクチン期限 | 日次バッチ | 接種済みで解除 |
| PREV | PREV_フィラリア未完了 | 日次〜月次 | 完了実績で解除 |
| PREV | PREV_ノミダニ対象 | 日次〜月次 | 処方実績で解除 |
| EXCL | EXCL_配信停止 | リアルタイム or 日次 | opt-out / 死亡 / 転院で付与。復帰時に解除 |
| EXCL | EXCL_配信注意 | 手動 or 日次 | 慎重対応フラグ |
| EXCL | EXCL_カルテ連携エラー | API エラー時 | エラー解消確認後に解除 |

### 4.3 ⚠️ タグ名バリデーション衝突

**`docs/API_SPEC.md` と仕様書のタグ名命名方式が衝突している。**

| 項目 | API_SPEC.md 現行 | 新仕様書 |
|------|-----------------|---------|
| タグ名文字種 | 英数字・アンダースコア・ハイフンのみ | 日本語を含む接頭辞方式（例: `CPM_01_出会い`） |
| 例 | `cpm_encounter`, `has_dog` | `CPM_01_出会い`, `PET_犬あり` |

この衝突は **SPEC-002 Q1** として未確定事項に登録済みである。

処理方針（Q1 確定まで）:
- カルテ側の内部論理タグ名は新仕様書命名（日本語接頭辞）で実装する
- API_SPEC.md の `tag_name` バリデーション制約を、日本語 Unicode 文字を許容する形に変更が必要
- 既存実装（`cpm_encounter`, `has_dog/has_cat`, `dormant_*`）はデプリケートタグとして並列運用し、Q1 確定後に切り替える
- Lステップ側の登録済みタグ棚卸しが先行作業として必要

## 5. CPM ステージ管理

### 5.1 CPM V2 ステージ定義（仕様書 §2-2 A / 仮ロジック）

> **注**: 以下は仮ロジックである。判定基準の細部（CPM3/CPM4の境界、CPM5の主従関係等）は林先生確認後に確定。SPEC-002 Q2 参照。

| ステージタグ | 判定基準（仮） |
|------------|------------|
| `CPM_01_出会い` | 初診から30日以内、来院1回 |
| `CPM_02_これから` | 来院2〜3回 / 365日、健診履歴0〜1回 |
| `CPM_03_コア` | 来院3〜5回 / 365日、健診履歴あり |
| `CPM_04_スポット` | 来院1〜2回 / 365日、最終来院90〜220日 |
| `CPM_05_ノア` | 来院6回以上 / 365日、または年4回健診達成、または `LTV_上位20` 該当 |

判定頻度: 日次または週次。

### 5.2 CPM V1 との共存

既存実装 `CalculateCPMStage`（LTV 金額・在籍日数ベース）は `CalculateCPMStageV1` として保持する。
新ロジックは `CalculateCPMStageV2` として追加し、SPEC-002 Q2 確定後に V2 を正式採用する。

### 5.3 休眠予備軍タグ（VISIT_*）

最終来院日からの経過日数で4段階のタグを付与。日次バッチで評価。

| 経過日数 | 付与タグ |
|---------|---------|
| 120日超 | `VISIT_120日超` |
| 180日超 | `VISIT_180日超` |
| 220日超 | `VISIT_220日超` |
| 240日超 | `VISIT_240日超` |

- タグは重複付与可（180日超 → VISIT_120日超 と VISIT_180日超 両方付与）
- 来院復帰時（会計確定または来院完了）に全 VISIT_* タグを解除
- 閾値（120/180/220/240日）は定数として定義し、設定変更に備える（SPEC-002 Q4）

### 5.4 LTV 上位20%

| 項目 | 仕様 |
|------|------|
| 判定軸 | 過去365日の累計診療費（直近365日 / ローリング） |
| 判定単位 | 飼い主単位（初期実装は clinic_id スコープ） |
| 判定頻度 | 月次 |
| 連携タグ | `LTV_上位20` |

複数拠点の合算ルールは SPEC-002 Q3 で未確定。初期実装は `clinic_id` スコープで単一拠点。

### 6.2 配信時の除外条件

| 対象 | 除外条件 |
|------|---------|
| 全トリガー共通 | `EXCL_配信停止` タグが付いている飼い主 |
| 全トリガー共通 | `delivery_excluded=true` の飼い主 |
| 再診リマインド（#4） | すでに予約済みの場合 |
| 休眠予防（#8/9/10） | 次回来院推奨日がすでに登録されている場合 |
| 健診後フォロー（#5） | `EXCL_配信注意` タグが付いている場合 |
| ワクチン期限通知（#6） | `PREV_ワクチン期限` タグが解除されている（接種済み）場合 |
| フィラリア予防案内（#11） | `PREV_フィラリア未完了` タグが解除されている場合 |
| ノミダニ予防案内（#12） | `PREV_ノミダニ対象` タグが解除されている場合 |
| フード継続購入リマインド（#13） | フード購入から30日以内に再購入があった場合 |
| サプリメント継続案内（#14） | サプリメント購入から指定期間内に再購入があった場合 |

### 6.3 配信衝突の優先順位

複数トリガーが同日に発火する場合の優先順位ルール（仕様書 §4-3）:

| 優先度 | 配信タイプ | 具体例 |
|------|----------|------|
| 1（最優先） | 治療・予防関連 | 再診リマインド、ワクチン期限通知 |
| 2 | 休眠予防 | 休眠220日 > 休眠180日 > 休眠120日 |
| 3 | 予防・物販関連 | フィラリア・ノミダニ・フード・サプリ |
| 4 | 関係性維持 | 個別誕生日 |
| 5 | 既存の一斉配信 | プレミアムフライデー・季節健診告知等 |

衝突時の処理ルール:
- **同一飼い主に1日複数配信が発火する場合、上位優先度のみ残す**
- **優先度1〜4が発火したら、優先度5の同日配信は翌日以降に延期**
- **優先度1が複数発火した場合は両方配信**（緊急性が高いため）
- **休眠予防は最も日数が長いものを採用**（220日と180日が同時なら220日のみ）
- **予防・物販関連は1日に複数発火した場合は1つに絞って配信**

実装方式は SPEC-002 Q9 で未確定。Q9 確定前は衝突制御なし（全トリガーを独立実行）で先行実装可能。

### 6.4 配信時間帯

| 配信タイプ | 配信時間 |

| 個別自動配信（全14種） | **朝10時固定（JST）** |

## 8. カルテイベントと Lステップアクション

| カルテ側イベント | カルテ側処理 | Lステップ側アクション |
|------------------|--------------|------------------------|
| 新規飼い主登録 | LINE ID 未連携なら連携待ち状態にする | なし（初診診療記録作成時に配信タグ付与） |
| LINE User ID 連携 | 飼い主に LINE User ID を紐付ける | 初回同期対象にする |
| `medical_records` 作成（`visit_type=初診`） | 初診記録の作成。初診日を `owners.first_visit_date` に設定 | `CPM_01_出会い` 付与。初診お礼配信タグ付与 |
| 新規ペット登録 | 生存ペット構成を再計算 | `PET_犬あり/PET_猫あり`、`PET_シニア対象` タグを更新 |
| ペット死亡登録 | 死亡ペット由来のタグを解除し、生存ペットで再計算 | ペット関連配信を停止。全ペット死亡時は `EXCL_配信停止` 付与 |
| 来院完了を記録 | 最終来院日・年間来院回数・CPM を再集計 | `VISIT_*` 解除、`CPM_*` 更新 |
| 会計確定 | 累計診療費・LTV区分・CPM を再集計 | `CPM_*`、`LTV_上位20` 候補フラグ更新（月次バッチで確定） |
| 獣医師が次回来院推奨日を設定 | 推奨日を保存 | 再診リマインドバッチの除外対象から除く処理 |
| 健診を実施 | 健診種類・実施日・次回推奨日を保存 | 健診後フォローバッチが翌日に発火。`HLTH_健診あり` 更新 |
| ワクチン接種を記録 | 種類・接種日を判定 | `PREV_ワクチン期限` タグの次回評価タイミングを更新 |
| 飼い主が配信停止を希望 | `delivery_excluded=true` を保存 | `EXCL_配信停止` 付与。自動タグ付与と個別送信を停止 |
| Lステップ API エラー | エラーをログに記録 | `EXCL_カルテ連携エラー` を付与 |

## 9. 健診・検診対象者抽出

健診・検診対象者はカルテ側で抽出して Lステップに一括連携する。タグを「種類 × 犬猫」で大量に作る方式は採用しない。

### 9.1 抽出条件

- 健診・検診の種類、対象動物種、最終実施日
- 年齢、慢性疾患の有無、最終来院日
- CPM ステージ、累計診療費、年間来院回数
- LINE User ID 連携済み、opt-out ではない、生存ペットがいる

### 9.2 連携方式

```
カルテ側で対象者リストを抽出
  -> 飼い主 LINE User ID を解決
  -> 対象外理由を判定
  -> 対象タグを一括付与
  -> Lステップ側で健診案内シナリオを配信
```

### 9.3 健診・検診種別

| 種類 | 対象 | 論理type候補 |
|------|------|--------------|
| 春の健診 | 犬・猫 | `spring` |
| 夏の健診 | 犬・猫 | `summer` |
| 秋の健診 | 犬・猫 | `fall` |
| 冬の健診 | 犬・猫 | `winter` |
| 歯科検診 | 犬・猫 | `dental` |
| 皮膚・耳検診 | 犬・猫 | `skin_ear` |
| 眼科検診 | 犬・猫 | `eye` |
| 腎臓ドック | 犬・猫 | `kidney` |

## 10. 飼い主 LINE User ID 管理

### 10.1 必須要件

- 飼い主ごとに LINE User ID を保持する（現フェーズは 1:1）
- LINE User ID 未連携の飼い主は、タグ連携・個別送信・一括配信対象から除外する
- LINE User ID は個人情報として扱い、ログでマスク処理する

| B. LINE webhook（友達追加イベント） | フェーズ2以降の別タスク |
| C. QRコード経由（LIFF パラメータ付き URL） | 将来検討 |

## 11. opt-out・ペット死亡・安全制御

### 11.1 opt-out

- 飼い主単位で `delivery_excluded=true` を保持
- opt-out 中はタグ付与バッチ・一括タグ付与・個別送信の対象外
- `EXCL_配信停止` タグを Lステップ側にも付与
- opt-out 理由・実行者・実行日時を監査ログに記録

### 11.2 ペット死亡

- 死亡ペットは犬猫分類・CPM判定・健診対象の集計から除外
- 複数頭飼いの場合は生存ペットのみで再計算
- 全ペット死亡時は `EXCL_配信停止` を付与し、自動配信対象から除外

### 11.3 複数頭飼いのタグ方針

| タグ種別 | 方針 |
|----------|------|
| PET_犬あり / PET_猫あり | 生存ペット全頭で論理和を取る（非排他） |
| PET_シニア対象 | 生存ペットに犬猫7歳以上が1頭でもいれば付与 |

## 13. 監査ログ

以下の操作をすべて監査ログに記録する。

- Lステップタグ付与・解除・一括付与
- LINE 個別送信・ファイル URL 発行
- 健診対象者抽出・LTV/CPM 対象者抽出
- 休眠判定バッチ・ノーショウ検知バッチ
- 配信トリガー発火・スキップ・除外
- API エラー・LINE ID 未連携スキップ・opt-out スキップ・ペット死亡除外

ログ必須項目: 実行日時、実行者/自動処理/バッチの区別、対象飼い主、対象ペット、付与・解除したタグ、API 応答結果、エラー内容、対象外理由。

LINE User ID はログ表示時にマスクする。

## 14. 設計原則・制約

| 原則 | 内容 |
|------|------|
| イベント駆動 | カルテイベント発生時にタグ付与・解除。明示イベントがないものはバッチで扱う |
| タグ競合回避 | 同一カテゴリのタグは原則1つのみ保持。新タグ付与前に旧タグを解除 |
| 冪等性 | 同じイベントが複数回処理されても同じ結果になるようにする |
| 拡張性 | タグ名・付与条件・解除条件・既存タグマッピングを設定化する |
| LINE ID 未連携 | LINE User ID がない飼い主はスキップ（エラーではなく警告ログ） |
| opt-out 尊重 | 配信停止希望の飼い主には自動タグ付与と個別送信を行わない |
| ペット死亡時の停止 | 死亡ペット由来のタグを解除し、全ペット死亡時は配信タグを解除する |
| タイムゾーン | 日付・時刻処理は JST（`Asia/Tokyo` / UTC+9）に統一する |
| Lステップ制約回避 | カルテ側はシナリオを直接動かさず、タグ操作だけを行う |
| 個人情報保護 | LINE User ID・ファイル URL・医療情報は必要最小限に表示し、ログではマスクする |
| 拠点有効化制御 | `is_sync_enabled=false` の拠点は全 Sync 処理をスキップ（FEAT-375） |

## 15. 既存運用からの移行戦略

ノア動物病院では、犬54件・猫52件のワクチンリマインダが既に Lステップで稼働している。

### Phase A: 並行稼働

- 既存 Lステップリマインダは停止しない
- カルテ起点の新タグは既存タグと衝突しない命名で付与（SPEC-002 Q1 確定まで新旧並列）
- テスト対象者を絞って配信精度を確認

### Phase B: タグ統一

- 既存タグ（`cpm_encounter`, `has_dog/has_cat`, `dormant_*` 等）と新タグの対応を確定
- カルテ側のタグマッピング設定を本番タグ名に切り替え

### Phase C: 既存リマインダ停止

- 犬54件・猫52件の既存ワクチンリマインダを段階的に停止
- 移行後1〜2か月は配信漏れと二重配信を監視

### 実装制約注記（2026-05-03 追加）

SPEC-002 Q7 確定（**2026-05-03**）により、§6-2 の元要求「Lステップ → カルテ／集計DBへの戻し」は **Lステップ API/Webhook の仕様上、完全な実装が不可能**であることが判明した。

#### 現実装可能範囲（FEAT-385 Path D）

| §6-2 元要求 | 実装範囲 | 実現方法 |
|-----------|---------|---------|
| 配信履歴の戻し | ✅ 実装 | カルテ側 `lstep_delivery_trigger_log` から再構築 |
| 友だち属性同期 | ✅ 実装 | 月次 CSV インポート（管理画面手動エクスポート） |

| フォーム回答の戻し | ❌ 運用回避 | Lステップ管理画面で確認 |
| 配信レポート（開封率・クリック率） | ❌ 運用回避 | Lステップ管理画面で確認 |

#### 運用方針

- **カルテ側で完結する分析**: 配信履歴（誰にいつ何のトリガーが発火したか）、友だち属性スナップショット（タグ・シナリオ・流入経路）
- **Lステップ管理画面で確認する分析**: クリック率、開封率、フォーム回答内容、配信効果

#### 後続課題

- `FEAT-385-supplement-Webhook.md`: 公式サポートにクリック/フォーム回答 Webhook の有無確認後に着手
- `FEAT-385-supplement-DeliveryReport.md`: 配信レポート CSV の存在確認後に着手
