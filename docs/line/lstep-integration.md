# Lステップ連携 実装仕様

Ekarte からLステップへの患者情報タグ連携・セグメントDM配信基盤の技術仕様。

> **最終更新**: 2026-04-20（クライアント要件書 `lstep_karte_spec.docx` 反映）

---

## 1. 現在のLステップ運用における課題

クライアント（ノア動物病院）が共有した課題。連携によって解決される前提。

| # | 課題 | 内容 |
|---|------|------|
| 1 | **ワクチンリマインダの手動運用** | 犬54件・猫52件のリマインダが稼働中。接種日起点で2週間ごとに手動コピー・作成が必要で作業負荷が大きい |
| 2 | **タグ付けが飼い主キーワード入力に依存** | スタッフが「○○と打ってください」と口頭説明。未入力の飼い主はセグメントから漏れる |
| 3 | **検査結果・証明書の個別送信** | PDFを1件ずつLステップメディアにアップロードし手動送信。日常的な業務で効率化が必要 |

---

## 2. 概要

| 項目 | 内容 |
|------|------|
| 連携方向（基本） | Ekarte → Lステップ（一方向同期） |
| 逆流（限定） | 友だち追加・ブロック・同意状態のみ Lステップ → Ekarte (Webhook) |
| 連携キー | `line_customers.line_user_id`（主キー）、Lステップ顧客ID（補助キー） |
| 同期方式 | イベント駆動（即時 + 再試行付き非同期キュー） |

---

## 3. スコープ

### In Scope
- **①カルテ連携**: Ekarteに登録された患者情報（飼い主・ペット）をLステップのタグへ紐づける
- **②セグメントDM配信**: タグ条件で対象を絞り込んだ配信対象制御・配信停止/同意フラグ管理

### Out of Scope
- Lステップ上のシナリオ設計・配信文面の作成（院内運用）
- Lステップ管理画面の操作・設定代行
- 配信結果レポート・分析基盤

## 5. カルテから連携するデータ（優先度順）

### 優先度：最優先

| データ | 用途 | 備考 |
|--------|------|------|
| ワクチン接種日（犬/猫別） | 次回接種時期のリマインダ自動起動 | 現在手動で運用中。最も作業負荷が高い部分 |
| 最終来院日 | 未来院リカバリー配信のトリガー | 6ヶ月・1年以上未来院の飼い主への来院促進 |
| 犬/猫/両方の分類 | 配信セグメントの基本分類 | カルテのペット登録情報から自動判定 |
| 次回来院推奨日 | 次回来院リマインダ | 獣医師が診察時に設定する「○ヶ月後」の日付 |
| 累計診療費・年間来院回数（LTV） | 顧客ランク管理・LTV別ソート | 上位顧客向け特別配信、LTV順抽出に使用 |
| 初診日 | 在籍期間の計算・CPMステージ判定 | CPMステージ移行条件に必須 |

### 優先度：高

| データ | 用途 | 備考 |
|--------|------|------|
| ペット基本情報（犬種/猫種、性別、生年月日、避妊去勢有無） | 年齢別・種別の配信セグメント | 誕生日配信、シニア向け健診案内、避妊去勢適齢期案内等 |
| 健診・検診の種類別受診履歴 | 種類別の次回案内・配信対象の抽出 | 健診（春夏秋冬）、検診（歯科、皮膚・耳、アドプリット、眼科）、腎臓ドック等を犬猫別に最終実施日管理 |
| 処方薬情報（処方日、投薬期間） | 薬の補充案内 | 投薬期間終了前にリマインド配信 |
| 慢性疾患フラグ | 疾患別の定期受診案内 | CKD、心疾患、皮膚疾患等 |

### 優先度：中

| データ | 用途 | 備考 |
|--------|------|------|
| 予約キャンセル・ノーショウ | 再予約促進配信 | キャンセル後のフォロー |

## 6. CPMステージ管理（Lステップ側での自動判定）

> **方針**: カルテからデータを連携し、Lステップ側でステージを自動判定・タグ切り替え。カルテ画面への表示・レポート機能はカルテシステム完成後に別途検討。

### ステージ定義

| ステージ | 判定基準 | 必要なデータ |
|---------|---------|------------|
| **出会いファミリー** | 来院1回のみ / 最終来院から240日未満 / 累計医療費2万円未満 | 来院回数、最終来院日、累計医療費 |
| **これからファミリー** | 来院2〜3回 / 初診から90日以内に再来院あり / 累計医療費2万〜5万円未満 / 離脱240日未満 | 来院回数、初診日、最終来院日、累計医療費 |
| **コアファミリー** | 年間2回以上来院 / 在籍180日以上 / 累計医療費5万円以上 / 離脱240日未満 | 年間来院回数、初診日、最終来院日、累計医療費 |
| **スポットファミリー** | 高額単発（3万円以上） / 90日以内再来院なし / キャンペーン・緊急中心 | 来院回数、診療費、最終来院日 |
| **ノアファミリー** | 在籍1年以上 / 年3回以上来院 / 累計医療費8万円以上 / 予防・健診継続 / 紹介実績or定期購入あり | 初診日、年間来院回数、累計医療費、健診受診履歴、紹介実績 |

### ステージ移行ロジック

| 移行 | 条件 | 自動配信 |
|------|------|---------|
| 出会い → これから | 初診から90日以内に再来院 | タグ昇格、フード・予防案内の配信開始 |
| これから → コア | 年2回来院到達かつ累計医療費5万円超 | 健診教育ステップ配信開始 |
| コア → ノア | 年3回以上来院、在籍12ヶ月超、累計医療費8万円以上 | 院長メッセージ、限定案内配信 |
| スポット → これから/コア | 90日以内に再来院 | 通常の来院フォロー配信へ移行 |
| 240日未接触（全ステージ共通） | 最終来院日から240日経過 | 再活性ステップ配信（180日/210日/240日段階的リマインド）。復帰後に来院データからステージ再判定 |

## 7. イベント → Lステップアクション マッピング

| カルテ側のイベント | Lステップ側のアクション |
|-----------------|----------------------|
| ワクチン接種を記録 | 次回接種時期の2ヶ月前からリマインダ配信を自動起動 |
| 来院完了を記録 | 最終来院日タグを更新 |
| 健診を実施 | 健診受診タグ付与＋次回健診推奨日を設定 |
| 予約が登録される | 前日リマインダーを配信 |
| 予約がキャンセルされる | キャンセルタグ付与＋再予約促進配信 |
| 処方薬を記録 | 補充推奨日タグを設定 |
| 新規飼い主・ペット登録 | ペット基本情報タグを自動付与（犬猫分類、犬種、生年月日等） |
| 来院・会計データの更新 | CPMステージの自動再判定（累計医療費・来院回数・在籍期間） |

```sql
CREATE TYPE lstep_sync_event AS ENUM (
    'tag_add',
    'tag_remove',
    'attr_update'
);

CREATE TYPE lstep_sync_status AS ENUM (
    'pending',
    'success',
    'failed'
);

CREATE TABLE line_sync_logs (
    id             bigserial   PRIMARY KEY,
    clinic_id      bigint      NOT NULL REFERENCES clinics(id),
    line_user_id   text        NOT NULL,
    event_type     lstep_sync_event NOT NULL,
    payload        jsonb       NOT NULL,
    status         lstep_sync_status NOT NULL DEFAULT 'pending',
    retry_count    int         NOT NULL DEFAULT 0,
    error_message  text,
    created_at     timestamptz NOT NULL DEFAULT now(),
    updated_at     timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_line_sync_logs_clinic_status
    ON line_sync_logs(clinic_id, status)
    WHERE status IN ('pending', 'failed');

CREATE INDEX idx_line_sync_logs_line_user
    ON line_sync_logs(line_user_id, created_at DESC);
```

## 11. タグ設計

> **前提**: Lステップ管理画面でのタグ作成は完了済み。タグ一覧はLステップAPI（`GET /v1/tags`）から取得し、Ekarteイベントと紐づける。手動共有は不要。

### 11.1 イベント駆動タグ

| イベント | 付与するタグ | 解除するタグ |
|---------|------------|------------|
| 予約作成（初回） | `予約あり` `来院予定` `初診` | — |
| 予約作成（2回目以降） | `予約あり` `来院予定` `再診` | `初診` |
| 予約キャンセル | `キャンセル歴あり` | `予約あり` `来院予定` |
| 来院完了（受付終了） | `来院済` `フォロー対象` `再診候補` | `来院予定` |
| ワクチン接種記録 | `ワクチン接種済` `次回案内対象` | — |
| 健診実施記録 | `健診済` `定期案内対象` | — |
| 次回案内期限切れ | — | `次回案内対象` `定期案内対象` |
| 友だち追加 (Webhook) | `LINE連携済` | — |
| 配信停止 | `配信停止中` | すべての配信対象タグ |

### 11.2 属性タグ（患者情報から静的付与）

| 条件 | タグ |
|------|------|
| `pets.species = '犬'` | `犬` |
| `pets.species = '猫'` | `猫` |
| `pets.species = その他` | `その他` |
| 年齢 < 1歳 | `子犬・子猫` |
| 1歳 ≤ 年齢 < 7歳 | `成犬・成猫` |
| 年齢 ≥ 7歳 | `シニア（7歳以上）` |
| `pets.gender = 'male'` | `オス` |
| `pets.gender = 'female'` | `メス` |
| ワクチン記録あり | `ワクチン管理対象` |
| 健診記録あり | `健診管理対象` |

> **ペット複数頭の場合**: 該当する全ペットのタグを飼い主アカウントへ付与する（→ **確認事項 #7**）

### 12.1 Lステップ API（Ekarte → Lステップ）

| 操作 | メソッド・パス | タイミング |

## 13. エラーハンドリング・再試行

### フロー

```
API呼び出し失敗
    ↓
line_sync_logs に status='failed', retry_count++ で記録
    ↓
retry_count < 3 → 指数バックオフで再試行（1分 / 5分 / 30分）
    ↓
retry_count = 3 → status='failed' で停止
    ↓
管理画面から手動再同期 or バッチで再試行
```

### 再試行バッチ

```go
// 失敗レコードを定期的にリトライ（cronジョブ）
func (s *LstepSyncService) RetryFailedSyncs(ctx context.Context, clinicID uint64) error {
    logs, err := s.repo.FindFailedSyncLogs(ctx, clinicID, maxRetry)
    // ...
}
```

## 14. セグメントDM配信

Lステップ側のセグメント配信機能を使用する。Ekarte側はタグを正確に管理することで配信対象を間接制御する。

### セグメント例

| 配信目的 | タグ条件 |
|---------|---------|
| 猫ワクチン案内 | `猫` ＋ `次回案内対象` |
| 高齢犬の健診推奨 | `犬` ＋ `シニア（7歳以上）` ＋ `定期案内対象` |
| 初回来院フォロー | `初診` ＋ `来院済` |
| 再来院促進 | `再診候補` |
| 一斉配信（全体） | `LINE連携済` ＋ `配信停止中` 除外 |

### 配信除外条件（必須）

- `is_consent = false`（同意未取得）
- `is_blocked = true`（配信停止）
- `配信停止中` タグ付き

### Q1. タグ連携の方式

**質問**: タグ連携はカルテ側のデータをLステップのAPIに渡す形になるか？ それとも別の連携方法を想定しているか？

**回答案**: Lステップ API（`POST /v1/contacts/{userId}/tags`）経由でタグ付与・解除を行う方式で実装する。カルテ側でイベントを検知し、非同期キュー経由でLステップAPIを呼び出す設計（セクション4参照）。Webhook連携は友だち追加・ブロック・同意状態の受信のみに限定する。

### Q2. スタッフ個別送信の経路

**質問**: カルテからLINEへの個別メッセージ送信（②スタッフ個別送信）は、LステップのAPI経由か？ それともLINE公式アカウントのAPI直接か？

**回答案**: **Lステップ API経由を推奨する**。理由は2点。①既存の顧客タグ・シナリオ管理をLステップ上に一元化できる。②LINE公式API直接の場合、Lステップ側の送信履歴に記録されずオペレーション上の分断が生じる。ただし確認事項Q3（配信数カウント）の結果によっては再検討する。

### Q3. 個別送信と月間配信数

**質問**: カルテからの個別送信（②）は、LINE公式アカウントの月間配信数にカウントされるか？

**回答案**: Lステップ API経由の場合、Lステップ側の配信数にカウントされる（LINE公式アカウントの月間上限とは別枠）。LINE公式API直接の場合は月間配信数にカウントされる。個別送信件数が多い場合はLステップ側の料金プランを確認する必要がある。**クライアント側でLステップサポートへ確認を依頼する。**

### Q6. 既存タグの自動付与・切り替え

**質問**: 現在Lステップで運用中のタグ（健診の季節別タグ、証明書送付済タグ等）を、カルテ側の操作をトリガーに自動で付与・切り替えする連携は可能か？

### Q7. 健診種別の配信対象抽出方式

**質問**: 健診・検診の種類ごとの最終実施日に基づく配信対象の抽出は、カルテ側で行ってLステップに連携する設計が可能か？（タグを種類×犬猫で大量に作るのではなく、カルテ側で対象者リストを抽出して渡す方式）

**回答案**: **可能。** カルテ側（`billings` / `medical_records` テーブル集計）で累計診療費・来院回数を計算し、CPMステージタグとしてLステップに連携する（セクション6参照）。上位顧客への絞り込みはLステップ側でCPMステージタグ条件を使ってセグメント配信する運用を想定。直接のソート・リスト出力が必要な場合はカルテ管理画面側に一覧機能を追加することも検討可能。

### Q9. Lステップ複数シナリオ制約の回避

**質問**: カルテからの配信がLステップのシナリオ枠を使わない方式であれば、1人に複数シナリオが同時に走れない制約を回避できるか？

**回答案**: **回避可能。** カルテ側からLステップ APIでタグ付与・属性更新を行う方式は、Lステップのシナリオを直接起動するのではなく、タグ条件を満たした際にシナリオが起動するトリガー型となる。そのため、シナリオ枠の制約はLステップ側の設定（同時実行するシナリオの優先順位）で管理できる。具体的な回避設計はLステップのシナリオ設計段階で詳細化する。

**状態**: 未確認
