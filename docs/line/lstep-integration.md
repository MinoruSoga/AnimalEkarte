## 0. 文書の位置づけ

本書は、ノア動物病院から提示された「Lステップ × 電子カルテ連携 実装要件書」と、その後のQ&Aを、開発・テスト・受入確認に使える要件として整理したものである。

本書では、原文に明記されたクライアント要望を「原文要件」、Q&Aで確定した回答を「確定方針」、安全性・運用性のために開発側で補完すべき内容を「実装補完要件」として扱う。

| 区分 | 内容 | 扱い |
|------|------|------|
| 原文要件 | 現在の課題、連携したいデータ、CPM、トリガー、DM配信、シナリオ優先度、確認事項 | 必須要件 |
| Q&A確定事項 | Q1〜Q9で確定したタグ連携方式、個別送信方式、配信数、フェーズ分け、拡張方針、対象者抽出方針 | 実装方針として採用 |
| 実装補完要件 | LINE User ID管理、opt-out、ペット死亡時停止、監査ログ、ファイルURL、移行戦略、冪等性 | 誤配信・情報漏えい・運用事故を防ぐため必須 |

### 0.1 Q&Aで確定した最終方針

- カルテ側のデータをそのままLステップへ送るのではなく、カルテイベントを起点にLステップのタグを付与・解除する。
- 自動配信の本文、シナリオ順序、配信タイミングはLステップ側で管理する。
- カルテ側は配信対象の判定、タグ付与・解除、スタッフ個別送信の起点を持つ。
- スタッフ個別送信はLステップAPIではなく、LINE公式アカウントのMessaging APIで直接送信する。
- Messaging API経由のPush / Multicast / Broadcast / Narrowcastは、LINE公式アカウントの月間配信数にカウントされる。
- LINE公式アカウントのチャット画面でスタッフが手動送受信するチャットメッセージは、Messaging API送信とは別扱いである。
- 実装は最優先タグ連携から段階的に進める。
- タグや配信シナリオは、病院側の施策追加に合わせて後から追加・変更できる設計にする。
- 既存Lステップタグも、カルテ側操作をトリガーに自動付与・切り替えできる対象にする。
- 健診・検診対象者はカルテ側で抽出し、Lステップへ一括連携する。
- 累計診療費・来院回数によるソート、抽出を実装する。
- Lステップの「1人に対して複数シナリオを同時に走らせにくい」制約は、カルテ側がシナリオを直接起動せずタグ操作に徹することで回避する。

## 1. 背景と目的

ノア動物病院では、LINE公式アカウントの配信ツールとしてLステップを運用している。現状は電子カルテとLステップが連携していないため、タグ付け、配信対象抽出、リマインダ起動、個別ファイル送信がスタッフの手作業に依存している。

本連携の目的は、カルテに記録された事実をLステップのタグやLINE個別送信に反映し、飼い主へのリマインダ、フォロー、セグメント配信を効率化することである。

### 1.1 現在の運用課題

| # | 課題 | 現状 | 本連携で解決すること |
|---|------|------|----------------------|
| 1 | ワクチンリマインダの手動運用 | 犬54件、猫52件のワクチン接種リマインダをLステップのリマインダ機能で運用している。接種日を起点に約1年後の接種時期の2か月前から段階的に配信する仕組みだが、2週間ごとに手動コピー・作成している | ワクチン接種記録を起点に、犬/猫/狂犬病ごとのタグを自動更新し、Lステップ側のリマインダを自動起動できるようにする |
| 2 | タグ付けが飼い主のキーワード入力に依存 | スタッフが「LINEのトーク画面で特定キーワードを入力してください」と毎回案内している。飼い主が入力しない場合、タグが付かず配信セグメントから漏れる | ペット登録、来院、診療、会計、健診、処方などのカルテ情報から自動でタグを付与・切り替えする |
| 3 | 検査結果・証明書の個別送信が手動 | 健診検査結果PDFやワクチン証明書を、スタッフが1件ずつLステップのメディアへアップロードし、個人トークで手動送信している | カルテ画面からPDF/画像URLまたはテキストをLINE Messaging APIで個別送信する |

### 1.2 成功条件

- 最優先のタグ連携が、飼い主のLINE入力に依存せず自動で行われる。
- ワクチン、狂犬病、健診、未来院リカバリーなどの主要シナリオが、カルテイベントを起点に漏れなく起動できる。
- 予約前日リマインダー、キャンセル後フォロー、ノーショウ後フォローをLステップ側の配信条件で扱える。
- スタッフが検査結果PDF、ワクチン証明書、術後・退院後フォロー、治療経過フォローをカルテ画面から個別送信できる。
- LTV、年間来院回数、CPMステージ、健診履歴、慢性疾患などで配信対象を抽出できる。
- 既存Lステップ運用から段階的に移行でき、既存タグや既存リマインダと競合しない。
- LINE User ID未連携、opt-out、ペット死亡、全ペット死亡などの誤配信リスクを制御できる。
- 監査ログにより、タグ操作、個別送信、バッチ抽出、APIエラーを追跡できる。

## 3. 連携アーキテクチャ

### 3.1 タグ連携方式

Q1の回答により、タグ連携は次の方式で確定する。

```text
カルテイベント発生
  -> カルテバックエンドで対象者・状態を判定
  -> LステップAPIでタグ付与・解除
  -> Lステップ側のタグ条件でシナリオ起動・停止・配信制御
```

カルテ側の診療データ、会計データ、ペット情報をそのままLステップに送る方式ではない。カルテ側でイベントや状態を判定し、Lステップ上の該当タグを付与・解除する。

### 3.2 個別メッセージ送信方式

Q2の回答により、スタッフ個別送信は次の方式で確定する。

```text
カルテ画面でスタッフが送信操作
  -> カルテバックエンド
  -> LINE Messaging API Push Message
  -> 飼い主のLINEに個別送信
```

- LステップAPI経由ではなく、LINE公式アカウントのMessaging API直送とする。
- PDFや画像はLINEへファイル本体を直接持たせるのではなく、アクセス可能なURLをメッセージ本文またはLINEメッセージ内に含める。
- 検査結果、ワクチン証明書、術後・退院後フォロー、治療経過フォローはこの方式で扱う。
- 個別送信はスタッフ判断を残す。完全自動配信にしないものは、送信前にスタッフが内容と対象者を確認する。

### 3.3 月間配信数の扱い

Q3の回答により、Messaging API経由の送信はLINE公式アカウントの月間配信数にカウントされる。

| 送信方法 | 月間配信数へのカウント |
|----------|------------------------|
| Messaging API Push | カウントされる |
| Messaging API Multicast | カウントされる |
| Messaging API Broadcast | カウントされる |
| Messaging API Narrowcast | カウントされる |
| LINE公式アカウントのチャット画面からの手動送信 | カウントされない |

カルテからの個別送信はMessaging API Push Messageに該当するため、月間配信数に含まれる。スタッフ個別送信UIには、配信数を消費する旨を表示する。

根拠:

- https://help2.line.me/official_account_jp/web/?contentId=20011745
- https://help2.line.me/official_account_jp/web/?contentId=20013941

### 3.4 配信制御の責任分担

Q9の回答により、配信の重なり対策は次の責任分担で行う。

| 領域 | 責務 |
|------|------|
| カルテ側 | イベント検知、対象者判定、Lステップタグの付与・解除、Messaging API個別送信、監査ログ |
| Lステップ側 | タグ条件に基づくシナリオ起動、停止、配信順序、配信本文、配信タイミング |

Lステップでは「1人に対して複数シナリオを同時に走らせにくい」制約がある。カルテ側がシナリオ枠を直接使わず、タグ操作に限定することで、配信制御はLステップ側のタグ条件へ集約する。

スタッフ個別送信はLINE Messaging API直送のため、Lステップのシナリオ枠は使用しない。自動配信についてはLステップ側のシナリオ設計に依存するため、タグ条件、除外条件、停止条件をLステップ管理画面側で明確に設定する。

### 3.5 拡張性

Q5、Q6の回答により、タグと配信シナリオは後から追加・変更できる設計にする。

- タグ名、タグカテゴリ、付与条件、解除条件はハードコードせず、設定ファイルまたはDBで管理できる構造にする。
- 既存Lステップタグの名称を棚卸しし、カルテ側イベントとのマッピングを設定化する。
- 新しい施策、腎臓ドック、新キャンペーンなどを追加しても、既存コードの大規模修正なしにタグ連携を追加できるようにする。
- Lステップ側の配信シナリオ本文や配信時刻は、病院側がLステップ管理画面で追加・変更できる前提にする。

## 4. 実装フェーズ計画

Q4では「まず最優先のタグ連携から実装する」と確定している。原文の最優先項目には、Q4で例示された4項目に加えてLTV・初診日も含まれるため、本書ではPhase 2を初期スコープと最優先完成スコープに分ける。

| フェーズ | 内容 | 優先度 | 備考 |
|----------|------|--------|------|
| Phase 0 | 前提確認 | 最優先 | LステップAPIオプション、LINE User ID取得方式、APIキー、既存タグ棚卸し |
| Phase 1 | 連携基盤 | 前提 | APIクライアント、設定保存、監査ログ、飼い主LINE ID管理、エラー処理、opt-out |
| Phase 2A | Q4明示の初期タグ連携 | 最優先 | ワクチン接種日、最終来院日、犬猫分類、次回来院推奨日 |
| Phase 2B | 最優先タグ連携の完成 | 最優先 | 狂犬病翌年案内、累計診療費、年間来院回数、初診日 |
| Phase 3 | 高優先・業務配信連携 | 高 | ペット基本情報、健診対象者抽出、処方薬補充、予約前日リマインダー、キャンセル |
| Phase 4 | CPM・慢性疾患・休眠 | 高 | CPMステージ自動判定、慢性疾患フラグ、180/210/240/365日休眠判定 |
| Phase 5 | スタッフ個別送信 | 高 | 検査結果PDF、ワクチン証明書、術後・退院後フォロー、治療経過フォロー |
| Phase 6 | 分析・運用拡張 | 中 | LTV/CPMダッシュボード、健診対象者抽出UI、月次レポート |

実装順の原則:

- Phase 0、Phase 1が完了しない限り、Lステップタグ連携とLINE個別送信は本番運用できない。
- Q4で明示された4項目はPhase 2Aとして最短で実装する。
- 予約前日リマインダーは業務優先度として最優先だが、予約機能・送信時刻設計に依存するためPhase 3で扱う。
- スタッフ個別送信は業務上の負荷が高いが、ファイルURL、監査ログ、月間配信数表示が必要なためPhase 5で扱う。

## 6. カルテイベントとLステップアクション

| カルテ側イベント | カルテ側処理 | Lステップ側アクション | フェーズ |
|------------------|--------------|------------------------|----------|
| 新規飼い主登録 | LINE ID未連携なら連携待ち状態にする | なし | Phase 1 |
| LINE User ID連携 | 飼い主にLINE User IDを紐付ける | 初回同期対象にする | Phase 1 |
| 新規ペット登録 | 生存ペット構成を再計算 | 犬猫分類、犬種・猫種、生年月日、避妊去勢タグを更新 | Phase 2A / Phase 3 |
| ペット情報更新 | 生存ペット構成、年齢、避妊去勢状態を再計算 | 関連タグを付与・解除 | Phase 3 |
| ペット死亡登録 | 死亡ペット由来のタグを解除し、生存ペットで再計算 | ペット関連配信を停止。全ペット死亡時は配信対象タグを解除 | Phase 1以降必須 |
| ペット死亡解除 | 生存ペットとして再集計 | 必要タグを再同期。ただし過去に解除したタグの自動復元範囲は運用で決める | Phase 1以降必須 |
| ワクチン接種を記録 | 種類、動物種、接種日を判定 | 次回接種時期の2か月前からのリマインダ対象タグを更新 | Phase 2A |
| 狂犬病ワクチン接種を記録 | 接種日を判定 | 翌年案内対象タグを更新 | Phase 2B |
| 来院完了を記録 | 最終来院日、年間来院回数、CPMを再集計 | 最終来院日、来院回数、CPM、休眠解除タグを更新 | Phase 2A / Phase 4 |
| 会計確定 | 累計診療費、LTV区分、CPMを再集計 | LTV、CPMタグを更新 | Phase 2B / Phase 4 |
| 獣医師が次回来院推奨日を設定 | 推奨日を保存 | 次回来院推奨日タグを更新 | Phase 2A |
| 予約を登録 | 予約日時を保存 | 前日リマインダ対象タグを付与 | Phase 3 |
| 予約を変更 | 予約日時を更新 | 古い予約タグを解除し、新しい予約タグを付与 | Phase 3 |
| 予約をキャンセル | キャンセル状態を保存 | キャンセルタグを付与し、予約タグを解除 | Phase 3 |
| 予約日時から一定時間経過しても来院なし | バッチでノーショウ検知 | ノーショウタグを付与し、予約タグを解除 | Phase 3 |
| 健診を実施 | 健診種類、実施日、次回推奨日を保存 | 健診受診タグを付与。次回健診案内の対象者選定はカルテ側抽出で行う | Phase 3 |
| 処方薬を記録 | 処方日、投薬期間、補充推奨日を計算 | 補充案内タグを更新 | Phase 3 |
| 慢性疾患を診断 | 疾患フラグを保存 | 疾患別フォロータグを付与 | Phase 4 |
| 慢性疾患を解除 | 疾患フラグを解除 | 疾患別フォロータグを解除 | Phase 4 |
| 飼い主が配信停止を希望 | opt-outを保存 | 自動タグ付与と個別送信を停止し、必要に応じて配信タグを解除 | Phase 1以降必須 |
| スタッフが個別送信 | 送信内容、添付URL、送信者を記録 | LINE Messaging APIでPush送信 | Phase 5 |

## 7. タグ設計

### 7.1 基本方針

- 本書のタグ名はカルテ側の論理タグ名である。
- 実際のLステップタグ名は、既存タグ棚卸し結果に合わせてマッピングできるようにする。
- 同一カテゴリで排他になるタグは、原則として新タグ付与前に旧タグを解除する。
- 日付タグはタグ数が増えやすいため、保持方針をカテゴリごとに定義する。
- 手動タグと自動管理タグを区別する。自動管理タグはスタッフが誤って削除・変更しないUI制御を検討する。

### 7.2 タグカテゴリと保持ルール

| カテゴリ | 論理タグ例 | 付与トリガー | 解除・保持ルール |
|----------|------------|--------------|------------------|
| 動物種別 | `has_dog`, `has_cat`, `has_both` | ペット登録・更新・死亡 | 生存ペット構成で再計算。排他制御 |
| 犬種・猫種 | `breed_dog_shiba`, `breed_cat_mix` | ペット登録・更新 | 代表ペット方針に従う。変更時は旧タグ解除 |
| 性別 | `sex_male`, `sex_female`, `sex_unknown` | ペット登録・更新 | 代表ペット方針に従う。排他制御 |
| 生年月日・誕生日 | `birthday_MM-DD`, `birth_month_MM`, `age_senior` | ペット登録・更新 | 複数ペット分を許可するかはタグ設計で決める |
| 避妊去勢 | `spay_neutered`, `intact` | ペット登録・更新 | 生存ペットで再計算。排他制御 |
| ワクチン | `vaccine_dog_YYYY-MM-DD`, `vaccine_cat_YYYY-MM-DD`, `vaccine_rabies_YYYY-MM-DD` | ワクチン接種記録 | 同一種別の古い接種日タグを解除 |
| 来院 | `first_visit_YYYY-MM-DD`, `last_visit_YYYY-MM-DD`, `next_visit_YYYY-MM-DD` | 来院完了、次回来院推奨日設定 | 同一カテゴリの古い日付タグを解除 |
| LTV | `ltv_amount_0`, `ltv_amount_2`, `ltv_amount_5`, `ltv_amount_8` | 会計確定 | LTVカテゴリは1つだけ保持 |
| 年間来院回数 | `visit_count_annual_1`, `visit_count_annual_2`, `visit_count_annual_3`, `visit_count_annual_5`, `visit_count_annual_10` | 来院完了 | 来院回数カテゴリは1つだけ保持 |
| CPM | `cpm_encounter`, `cpm_growing`, `cpm_core`, `cpm_spot`, `cpm_noah`, `cpm_dormant` | 来院完了、会計確定、休眠判定 | 通常CPMは1つだけ保持。休眠時は `cpm_dormant` を優先 |
| 休眠 | `dormant_180d`, `dormant_210d`, `dormant_240d`, `dormant_365d` | 休眠判定バッチ | 段階に応じて最新状態へ更新。来院復帰時に解除 |
| 健診・検診 | `checkup_done_{type}_{YYYY-MM}` | 健診実施 | 同一typeの古い健診タグを解除 |
| 処方薬 | `refill_due_YYYY-MM-DD`, `refill_due_{medicine}_{YYYY-MM-DD}` | 処方薬記録 | 同一薬剤または同一補充カテゴリの古いタグを解除 |
| 予約 | `reserved_YYYY-MM-DD` | 予約登録・変更 | 予約変更時は旧予約タグ解除 |
| キャンセル | `canceled_visit`, `canceled_visit_YYYY-MM-DD` | 予約キャンセル | 再予約または来院完了で解除 |
| ノーショウ | `no_show_visit`, `no_show_YYYY-MM-DD` | ノーショウ検知 | 再予約または来院完了で解除 |
| 慢性疾患 | `chronic_ckd`, `chronic_heart`, `chronic_skin` | 慢性疾患診断 | 疾患状態が解除された場合にタグ解除 |
| 個別送信後 | `certificate_sent`, `test_result_sent`, `post_op_follow_sent` | スタッフ個別送信 | 既存タグがある場合は送信後に自動付与できるようにする |
| 配信停止 | `lstep_opt_out` 相当 | opt-out | opt-out中は自動タグ付与と個別送信を行わない |

### 7.3 タグバリデーション

カルテ側の論理タグ名は、設定ミスを防ぐため以下でバリデーションする。

- 1〜100文字を基本とする。
- 英数字、アンダースコア、ハイフンのみを基本とする。
- 実際のLステップタグ名が日本語の場合は、マッピング設定で吸収する。
- カテゴリ内で同時に保持できるタグ数を定義する。
- Lステップ側のタグ数上限、タグ名文字数上限、APIレート制限は別途確認する。

## 8. CPMステージ管理

### 8.1 最終方針

原文では「Lステップ側でCPMステージを自動判定」する想定が記載されている。一方、Q&Aではカルテ側はタグ操作を行い、配信制御はLステップ側のタグ条件で行う方針が確定している。

最終方針は次のとおりとする。

- CPM判定に必要な累計診療費、来院回数、在籍期間、最終来院日、健診受診履歴などはカルテ側で保持・集計する。
- CPMステージの判定はカルテ側で行い、判定結果をLステップのCPMステージタグとして付与・解除する。
- Lステップ側はCPMステージタグを条件に、ステージ別シナリオを起動・停止する。
- 将来的なカルテ画面へのCPM表示、240日アラート、月次レポートは別途拡張として扱う。

この方針により、複雑な判定ロジックをカルテDB上で一貫して計算でき、Lステップ側には配信制御に必要なタグだけを渡せる。

### 8.2 ステージ定義

| ステージ | 判定基準 | 必要なカルテデータ |
|----------|----------|--------------------|
| 出会いファミリー | 来院1回のみ、最終来院から240日未満、累計医療費2万円未満 | 来院回数、最終来院日、累計医療費 |
| これからファミリー | 来院2〜3回、初診から90日以内に再来院あり、累計医療費2万円〜5万円未満、離脱240日未満 | 来院回数、初診日、最終来院日、累計医療費 |
| コアファミリー | 年間2回以上来院、在籍180日以上、累計医療費5万円以上、離脱240日未満 | 年間来院回数、初診日、最終来院日、累計医療費 |
| スポットファミリー | 高額単発3万円以上、90日以内再来院なし、キャンペーン・緊急中心 | 来院回数、単回来院費、最終来院日 |
| ノアファミリー | 在籍1年以上、年3回以上来院、累計医療費8万円以上、予防・健診継続、紹介実績または定期購入あり | 初診日、年間来院回数、累計医療費、健診受診履歴、紹介実績、定期購入 |

### 8.3 ステージ移行ロジック

| 移行 | 条件 | タグ操作 | Lステップ側の配信 |
|------|------|----------|------------------|
| 出会い -> これから | 初診から90日以内に再来院 | `cpm_encounter` 解除、`cpm_growing` 付与 | フード・予防案内 |
| これから -> コア | 年2回来院到達、かつ累計医療費5万円超 | `cpm_growing` 解除、`cpm_core` 付与 | 健診教育ステップ |
| コア -> ノア | 年3回以上来院、在籍12か月超、累計医療費8万円以上 | `cpm_core` 解除、`cpm_noah` 付与 | 院長メッセージ、限定案内 |
| スポット -> これから/コア | 90日以内に再来院 | `cpm_spot` 解除、条件に応じたCPMタグを付与 | 通常の来院フォロー |
| 全ステージ -> 休眠 | 最終来院日から240日経過 | `cpm_dormant` 付与 | 再活性ステップ |
| 休眠 -> 復帰 | 休眠後に来院 | `cpm_dormant` 解除、来院データで再判定 | 来院フォローへ復帰 |

### 8.4 休眠・未来院リカバリー

原文には「6か月・1年以上未来院の飼い主への来院促進」と「240日未接触」が併記されている。要件としては以下のように整理する。

| 経過日数 | 目的 | タグ例 | 備考 |
|----------|------|--------|------|
| 180日 | 6か月未来院リカバリー | `dormant_180d` | 初回の来院促進 |
| 210日 | 240日前の追加接触 | `dormant_210d` | 段階的リマインド |
| 240日 | CPM上の休眠扱い | `dormant_240d`, `cpm_dormant` | ステージに関わらず休眠 |
| 365日 | 1年以上休眠への特別案内 | `dormant_365d` | 強いオファーや特別案内 |

休眠判定は日次バッチで実行する。復帰時は来院完了または会計確定を起点に休眠タグを解除し、最新データでCPMステージを再判定する。

### 8.5 CPM判定で未確定のデータ

ノアファミリー判定に必要な以下の項目は、カルテ側での記録方法を確認する。

- 予防・健診継続の定義
- 紹介実績の記録方法
- 定期購入の記録方法

確定までの仮案:

- 過去1年以内に春・夏・秋・冬いずれかの健診を実施している。
- 過去1年以内に犬・猫・狂犬病いずれかのワクチン接種を実施している。
- 過去1年以内にフィラリア予防薬またはノミダニ予防薬を処方している。
- 上記のどれを「予防・健診継続」に含めるか、頻度を年1回以上にするか年2回以上にするかはクライアント確認後に確定する。

## 9. 配信シナリオ要件

カルテ側は配信本文やシナリオ順序を管理しない。カルテ側はタグ付与、タグ解除、個別送信の起点を提供し、Lステップ側がシナリオを管理する。

### 9.1 自動配信

| 配信内容 | トリガー | 優先度 | 実装方針 |
|----------|----------|--------|----------|
| 予約前日リマインダー | 予約登録 | 最優先 | カルテが予約タグを付与し、Lステップが前日配信 |
| ワクチン次回接種案内 | ワクチン接種記録 | 最優先 | 次回接種時期の2か月前から段階的リマインド |
| 狂犬病翌年案内 | 狂犬病ワクチン記録 | 最優先 | ワクチンリマインダと同じ仕組み |
| 健診案内 | 健診実施、または対象者抽出 | 最優先 | 年4回健診推進の重点施策 |
| 初診フォロー | 初回来院完了、CPM出会い判定 | 高 | 2回目来院促進。現在未実施 |
| 処方薬の補充案内 | 処方薬記録 | 高 | 投薬期間終了前に配信 |
| 慢性疾患の定期受診案内 | 慢性疾患フラグ付与 | 高 | CKD、心疾患、皮膚疾患など |
| 未来院リカバリー | 最終来院日から180日、210日、240日、365日 | 高 | 離脱防止 |
| キャンセル後の再予約促進 | 予約キャンセル | 中 | キャンセルタグで起動 |
| ノーショウ後の再予約促進 | ノーショウ検知 | 中 | バッチ検知タグで起動 |
| 誕生日配信 | ペット誕生日 | 中 | 定期バッチまたはLステップ側条件 |
| 去勢・避妊適齢期案内 | 生年月日、避妊去勢状態 | 中 | 月齢閾値は確認事項 |

### 9.2 半自動・スタッフ判断が必要な配信

原文では、退院後フォロー、術後フォロー、検査結果の来院案内は「スタッフ個別判断が必要」とされている。完全自動配信ではなく、カルテ画面からスタッフが対象と内容を確認して送信する。

| 配信内容 | 送信者 | 優先度 | 実装方針 |
|----------|--------|--------|----------|
| 退院後フォロー | 担当獣医師、スタッフ | 高 | 候補表示やテンプレートは可能だが、送信確定はスタッフ操作 |
| 術後フォロー | 担当獣医師、スタッフ | 高 | 手術記録を起点に送信候補を出し、スタッフが送信 |
| 検査結果の来院案内 | スタッフ | 高 | 検査結果確認後、個別送信UIから送信 |
| 治療経過の個別フォロー | 担当獣医師 | 高 | 個別メッセージとして送信 |

### 9.3 スタッフ個別送信

| 配信内容 | 送信者 | 現在の運用 | 実装後 |
|----------|--------|------------|--------|
| 検査結果PDF | 獣医師、看護師 | Lステップのメディアへアップロード後、個人トークでURL送信 | カルテ画面からURL付きPush Message |
| ワクチン証明書画像/PDF | 獣医師、看護師 | 同上 | カルテ画面からURL付きPush Message |
| 術後・退院後フォロー連絡 | 担当獣医師 | 個人トークで手動送信 | カルテ画面からテキスト送信 |
| 治療経過の個別フォロー | 担当獣医師 | 個人トークで手動送信 | カルテ画面からテキスト送信 |

### 9.4 対象外または現行運用継続

| 配信内容 | 扱い | 理由 |
|----------|------|------|
| 来院後サンクスメッセージ | 対象外 | LINE友だち追加時の自動配信は既に稼働中 |
| 初診飼い主への個別サンクス | 現行運用継続 | 受付が手動で選別して送る方針を残す |

## 10. 健診・検診対象者抽出

Q7の回答により、健診・検診対象者はカルテ側で抽出してLステップに連携する。タグを「種類 × 犬猫」で大量に作る方式は採用しない。

### 10.1 抽出条件

カルテ管理画面またはバッチで、以下の条件を組み合わせて対象者を抽出できるようにする。

- 健診・検診の種類
- 犬、猫、両方
- 最終実施日
- 年齢
- 慢性疾患の有無
- 最終来院日
- CPMステージ
- 累計診療費
- 年間来院回数
- LINE User ID連携済み
- opt-outではない
- 生存ペットがいる

### 10.2 連携方式

```text
カルテ側で対象者リストを抽出
  -> 飼い主LINE User IDを解決
  -> 対象外理由を判定
  -> 対象タグを一括付与
  -> Lステップ側で健診案内シナリオを配信
```

### 10.3 出力要件

- 対象者総数
- LINE連携済み件数
- opt-out除外件数
- 死亡ペットのみ除外件数
- API成功件数
- API失敗件数
- 対象外理由
- CSV出力または画面一覧
- 一括タグ付与の実行者、実行日時、対象条件

抽出結果は監査ログに残す。対象外となった理由、例えばLINE ID未連携、opt-out、死亡ペットのみ、APIエラーもログ化する。

## 11. LTV・顧客セグメント抽出

Q8の回答により、累計診療費や来院回数をもとに対象を絞り込める機能を実装する。

| 機能 | 用途 |
|------|------|
| 累計診療費でのソート | 上位顧客向け特別配信 |
| 累計診療費区分での抽出 | CPM、LTV別配信 |
| 年間来院回数でのソート | 継続来院度の高い飼い主の抽出 |
| CPMステージ別フィルタ | ステージ別施策の対象抽出 |
| 健診受診履歴との組み合わせ | 高LTVだが健診未受診の飼い主への案内 |
| LINE連携有無での絞り込み | 実配信可能対象の確認 |
| opt-out除外 | 誤配信防止 |

LTV上位顧客に絞った配信を行う場合も、最終的にはLステップタグを一括付与し、配信本文やシナリオはLステップ側で管理する。

### 11.1 年間来院回数

年間来院回数はカレンダー年ではなく、ローリング12か月で計算する。

```sql
visited_at >= NOW() - INTERVAL '365 days'
```

カレンダー年方式は1月1日に全員の年間来院回数が0回になり、CPMステージ降格が大量発生するため採用しない。

### 11.2 LTV区分

| タグ | 累計診療費 |
|------|------------|
| `ltv_amount_0` | 0〜19,999円 |
| `ltv_amount_2` | 20,000〜49,999円 |
| `ltv_amount_5` | 50,000〜79,999円 |
| `ltv_amount_8` | 80,000円以上 |

`ltv_amount_1` は使用しない。区分値はCPM閾値の2万円、5万円、8万円に合わせる。

### 11.3 年間来院回数区分

| タグ | 年間来院回数 |
|------|--------------|
| `visit_count_annual_1` | 1回 |
| `visit_count_annual_2` | 2回 |
| `visit_count_annual_3` | 3〜4回 |
| `visit_count_annual_5` | 5〜9回 |
| `visit_count_annual_10` | 10回以上 |

## 12. 飼い主LINE User ID管理

タグ連携と個別送信の前提として、飼い主に紐づくLINE User IDが必要である。

### 12.1 必須要件

- 飼い主ごとにLINE User IDを保持する。
- 現フェーズでは、飼い主1件に対してLINE User ID 1件を管理する。
- LINE User ID未連携の飼い主は、タグ連携、個別送信、一括配信対象から除外する。
- 未連携で除外した件数をログと画面で確認できるようにする。
- LINE User IDは個人情報として扱い、画面やログでは必要に応じてマスクする。
- LINE User ID連携解除時は、Lステップタグをどう扱うか運用方針を明確にする。

### 12.2 取得方式の候補

| 方法 | メリット | デメリット |
|------|----------|------------|
| LステップWebhook | 友だち追加やイベントを起点に取得できる | カルテ側にWebhook受信口が必要。カルテの飼い主との紐付けフローが必要 |
| LIFF | LINE上で飼い主認証とUser ID取得を行いやすい | LIFF開発が追加スコープ |
| CSVインポート | 初期移行として実施しやすい | 継続的な同期には向かない |
| 手動登録 | 小規模導入時に始めやすい | 入力ミス、更新漏れ、運用負荷がある |

取得方式はクライアント確認事項とする。

### 12.3 複数LINE ID対応

現フェーズでは、飼い主1件に対してLINE User ID 1件を管理する。世帯内の複数人への配信は対象外とする。

将来的に複数LINE IDが必要になった場合は、`owner_line_users` のような1:N構造を別途設計する。

## 13. opt-out・ペット死亡・安全制御

### 13.1 opt-out

配信停止希望の飼い主には、自動タグ付与と個別送信を行わない。

必須要件:

- 飼い主単位でopt-out状態を保持する。
- opt-out中はタグ付与バッチ、一括タグ付与、個別送信の対象外にする。
- opt-out登録時に既存の配信用タグを解除するかどうかを運用方針として決める。
- opt-out解除時に自動復元するタグ範囲を決める。無条件に過去タグを復元しない。
- opt-out理由、実行者、実行日時を監査ログに残す。

### 13.2 ペット死亡

ペット死亡時は、死亡ペット由来のタグを解除し、ペット関連配信を停止する。

必須要件:

- 死亡ペットは犬猫分類、犬種・猫種、年齢、誕生日、避妊去勢、健診対象者抽出、CPM判定の集計対象から除外する。
- 複数頭飼いの場合、生存ペットだけでタグを再計算する。
- 全ペット死亡時は、ペット関連の配信タグを解除し、自動配信対象から除外する。
- 死亡解除時に自動復元するタグ範囲は運用で決める。
- 死亡登録、死亡解除、タグ解除結果を監査ログに残す。

### 13.3 複数頭飼いのタグ方針

| タグ種別 | 方針 |
|----------|------|
| 犬/猫/両方 | 生存ペット全頭で論理和を取る |
| 犬種・猫種 | 最初に登録した生存ペットを代表とする。複数犬などはミックス扱いを検討 |
| 誕生日 | 複数ペット分を複数タグ付与する |
| 性別 | 代表ペットの性別を使う |
| 避妊去勢 | 1匹でも避妊去勢済みなら `spay_neutered`、全頭未実施なら `intact` |

死亡ペットは集計対象から除外する。

## 14. ノーショウ対応

原文の優先度「中」にある予約キャンセル・ノーショウのうち、ノーショウはスタッフの明示操作がないため、バッチ検知が必要である。

| 条件 | カルテ側処理 | Lステップタグ操作 |
|------|--------------|------------------|
| 予約日時から一定時間経過後に来院記録がない | ノーショウとして検知 | `no_show_visit`、`no_show_YYYY-MM-DD` 相当を付与し、予約タグを解除 |
| ノーショウ後に再予約 | 予約登録 | ノーショウタグを解除し、予約タグを付与 |
| ノーショウ後に来院完了 | 会計確定 | ノーショウタグを解除し、最終来院日タグを更新 |

検知タイミングは運用に合わせて調整する。初期案では「予約日時から4時間経過後」を候補とする。

## 15. ファイル送信とセキュリティ

スタッフ個別送信でPDFや画像を送る場合、LINEからアクセス可能なURLが必要である。

### 15.1 対象ファイル

- 検査結果PDF
- ワクチン証明書PDF
- ワクチン証明書画像
- その他、術後・退院後フォローに必要な画像

### 15.2 必須要件

| 項目 | 要件 |
|------|------|
| 保存先 | S3などのオブジェクトストレージ、または開発環境用ローカルストレージ |
| URL | 推測困難な署名付きURL、または期限付き公開URL |
| 有効期限 | 原則24時間など短期間。運用要件に応じて調整 |
| ファイルサイズ | LINE Messaging APIの制限に合わせる |
| 許可拡張子 | PDF、JPG、PNGを基本とする |
| 監査ログ | 誰が、いつ、誰に、何を送ったかを記録 |
| 送信後タグ | ワクチン証明書送付済みなど、既存タグがある場合は自動付与できるようにする |

個人情報や動物医療情報を含むため、URLの有効期限、アクセス制御、監査ログは必須とする。

## 16. 監査ログ

以下の操作はすべて監査ログに記録する。

- Lステップタグ付与
- Lステップタグ解除
- タグ一括付与
- LINE個別送信
- ファイルURL発行
- 健診対象者抽出
- LTV/CPM対象者抽出
- 休眠判定バッチ
- ノーショウ検知バッチ
- APIエラー
- LINE ID未連携によるスキップ
- opt-outによるスキップ
- ペット死亡による除外

ログに残す項目:

- 実行日時
- 実行者、自動処理、バッチの区別
- 対象飼い主
- 対象ペット
- 実行内容
- 付与・解除したタグ
- 送信メッセージ種別
- APIリクエストIDまたはイベントID
- API応答結果
- エラー内容
- 対象外理由

LINE User IDはログ表示時にマスクする。

## 17. 設計原則・制約

| 原則 | 内容 |
|------|------|
| イベント駆動 | カルテイベント発生時にタグ付与・解除を行う。休眠、ノーショウ、健診対象者抽出など明示イベントがないものはバッチで扱う |
| タグ競合の回避 | 同一カテゴリのタグは原則1つだけ保持する。新タグ付与前に旧タグを解除する |
| 冪等性 | 同じイベントが複数回処理されても同じ結果になるようにする |
| 拡張性 | タグ名、付与条件、解除条件、既存タグマッピングを設定化する |
| LINE ID未連携 | LINE User IDがない飼い主は連携対象外としてスキップし、エラーではなく警告ログにする |
| opt-out尊重 | 配信停止希望の飼い主には、自動タグ付与と個別送信を行わない |
| ペット死亡時の停止 | 死亡ペット由来のタグを解除し、全ペット死亡時は配信タグを解除する |
| 月間配信数 | Messaging API送信は配信数にカウントされるため、送信前にスタッフへ分かるようにする |
| 監査ログ | タグ操作、個別送信、バッチ抽出、APIエラーを記録する |
| タイムゾーン | 日付・時刻処理はJST、`Asia/Tokyo` 基準に統一する |
| Lステップ制約回避 | カルテ側はシナリオを直接動かさず、タグ操作だけを行う |
| 個人情報保護 | LINE User ID、ファイルURL、医療情報は必要最小限に表示し、ログではマスクする |

## 18. 既存運用からの移行戦略

ノア動物病院では、犬54件、猫52件のワクチンリマインダが既にLステップで稼働している。新連携導入時に二重配信やタグ競合を起こさないよう、段階的に移行する。

### 18.1 Phase A: 並行稼働

- 既存Lステップリマインダは停止しない。
- カルテ起点の新タグは、既存タグと衝突しない名称で付与する。
- テスト対象者を絞って配信精度を確認する。
- 二重配信が起きないよう、Lステップ側でテストタグ条件を分離する。

### 18.2 Phase B: タグ統一

- 既存タグと新タグの対応関係を確定する。
- 既存タグのうち継続利用するもの、廃止するもの、名称変更するものを整理する。
- 健診の季節別タグ、証明書送付済タグなど、既存タグの自動付与・切り替え対象を整理する。
- カルテ側のタグマッピング設定を本番タグ名に切り替える。

### 18.3 Phase C: 既存リマインダ停止

- 犬54件、猫52件の既存ワクチンリマインダを段階的に停止する。
- カルテ起点の新リマインダのみを本番稼働にする。
- 移行後1〜2か月は配信漏れと二重配信を監視する。

### 18.4 既存飼い主の初回判定

本番投入時に、既存飼い主に対して初回同期バッチを実行する。

- LINE User IDを紐付ける。
- 生存ペット構成を集計する。
- 最終来院日、初診日、累計診療費、年間来院回数を集計する。
- CPMステージを初回判定する。
- 必要なLステップタグを一括付与する。
- LINE未連携、opt-out、全ペット死亡などの対象外理由を集計する。

## 20. クライアント確認が必要な事項

実装前または本番運用前に確認が必要な事項。

### 20.1 Critical

| # | 確認事項 | 理由 |
|---|----------|------|
| 1 | LステップAPIオプションに加入済みか | LステップAPIは別契約の有料オプションであり、未加入の場合はタグ連携が実装できない |
| 2 | LINE User IDの取得方式 | タグ連携、個別送信、一括配信の前提 |
| 3 | LステップAPIキー、LINE Messaging APIチャネルアクセストークンの共有方法 | Phase 1着手に必要 |
| 4 | 既存Lステップタグ一覧 | Q6対応、既存タグ自動切り替え、移行戦略に必要 |
| 5 | ペット死亡時、飼い主opt-out時の運用 | 誤配信防止の最重要要件 |
| 6 | LINE User ID解除時のタグ扱い | 解除後にLステップタグを残すか、配信用タグを解除するかの運用判断が必要 |

### 20.2 High

| # | 確認事項 | 理由 |
|---|----------|------|
| 1 | LINE公式アカウントの月間配信上限と現在使用量 | 個別送信が配信数を消費するため |
| 2 | ファイルストレージの選定 | PDF、画像送信に必要 |
| 3 | ノアファミリー判定の「予防・健診継続」の定義 | CPM判定に必要 |
| 4 | 紹介実績、定期購入の記録方法 | ノアファミリー判定に必要 |
| 5 | 健診・検診名の正式マスタ | 健診対象者抽出に必要 |
| 6 | 慢性疾患フラグの対象疾患 | CKD、心疾患、皮膚疾患以外を含めるか |
| 7 | 処方薬補充案内の対象薬剤と補充推奨日の計算方法 | 投薬期間終了前リマインドの精度に影響 |

### 20.3 Medium / Low

| # | 確認事項 | 理由 |
|---|----------|------|
| 1 | Lステップ側のタグ数上限、タグ名文字数上限、APIレート制限 | 日付タグ、複数ペット、誕生日タグでタグ数が増える可能性がある |
| 2 | 予約前日リマインダーの送信時刻 | カルテ側には影響しないがLステップ設定に必要 |
| 3 | 休業日前の前日リマインダー扱い | 月曜予約を金曜または土曜に送るかなど |
| 4 | 去勢・避妊適齢期案内の月齢閾値 | 自動配信条件に必要 |
| 5 | 署名付きURLの有効期限 | 検査結果、証明書の閲覧運用に影響 |
| 6 | 予約日時から何時間後にノーショウ扱いにするか | 初期案は4時間だが運用確認が必要 |
