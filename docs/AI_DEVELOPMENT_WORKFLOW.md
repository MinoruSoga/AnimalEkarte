# AI エージェント協働開発ワークフロー (AI Development Workflow)

> **Animal Ekarte**: 仕様駆動・AI エージェント活用による高品質開発
> **最新更新**: 2026-06-12 | **ステータス**: 推奨手順 (Antigravity CLI / `agy` 対応)

---

## 1. 原則：仕様書を Single Source of Truth とする

AI エージェント（本プロジェクトでは **Antigravity CLI / `agy`** を標準運用）と協働する際、最も重要なのは**「仕様にないものは実装しない」**という徹底したスコープ管理です。

1.  **仕様の読解**: `docs/` 配下の最新仕様書および `docs/tasks/open/` の issue をまず読み込ませる。
2.  **正規名の遵守**: 項目名、エンドポイント、型名は仕様書に定義された「正規名」を 1 文字の狂いもなく使用する。
3.  **境界条件の確認**: 期間の優先順位、NULL の許容、数値の精度などの境界値を明確にする。

---

## 2. 開発プロセスの 4 ステップ

### Step 1: 要件定義とタスク分解
- **BE/FE 分離**: API 契約（バックエンド）と UI/UX（フロントエンド）のタスクを明確に分ける。
- **1 Issue = 1 責務**: 一つのタスクに複数の検証ポイントを混ぜない。

### Step 2: 既存パターンの踏襲
- **類似機能の参照**: 同じドメインやパターンの既存コード（handler/service/repository）を AI に読ませ、スタイルの不一致を防ぐ。
- **リファクタリングの制限**: 担当範囲外のコードには触れさせず、変更を最小限（Surgical Update）に留める。

### Step 3: 実装プロンプトの構築
AI に対し、以下の 5 点を明記した明確な「指示書」を渡します。
1.  **参照ドキュメント**: `docs/` 以下の関連ファイル。
2.  **担当範囲**: 編集を許可するディレクトリ・ファイル。
3.  **完了条件**: 仕様を満たすための具体的チェックリスト。
4.  **禁止事項**: 触ってはいけないファイル、戻してはいけない変更。
5.  **報告形式**: 変更ファイル、テスト結果、未解決事項の要約。

### Step 4: 厳格な検証とセルフレビュー
- **自動テスト**: backend/frontend それぞれの単体テスト・結合テストの PASS を必須とする。
- **多拠点分離チェック**: `clinic_id` によるデータ隔離が全エンドポイントで保証されているか。
- **境界値テスト**: 空データ、最大値、エラー時のフォールバックが機能するか。

---

## 3. PR (Pull Request) の標準
AI が作成した実装を PR にする際は、以下の項目を網羅します。

- **Summary**: 変更の目的と要約（1〜3行）。
- **Test Plan**: 実行した自動テスト名、および画面上での動作確認手順。
- **Changes**: 影響を受けたファイルと、その理由。
- **Notes**: 仕様上の補足や、将来的な課題（Technical Debt）。

---

## 4. 継続的な改善
開発完了後、AI との対話ログをそのまま残すのではなく、**「確定した仕様書」**と**「クリーンなコード」**として成果物を整理し、次の開発サイクルへの負債を残さないようにします。
