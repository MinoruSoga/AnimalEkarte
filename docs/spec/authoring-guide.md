# 仕様書の書き方

新規作成・更新の前に本書を読む。仕様の名前、本文形式、正本の分担を揃えるための文書規約であり、既存業務の仕様変更や承認を与えるものではない。今回の適用範囲は予約・受付・カルテ・会計の7画面、カルテ保存契約、横断フローの9本文。対象外の既存仕様は更新時に順次合わせ、一括改名しない。

<a id="naming"></a>
## 名前と参照

- 正本のファイル名は小文字 kebab-case。画面の意味を表す名前にし、並び順の番号を付けない。例: reservation-management.md、reception-board.md、medical-record-form.md、accounting-settlement.md。読む順は README で管理する。
- README.md はフォルダ入口という例外。CLAUDE.md 等のツール用指示ファイルは仕様本文ではない。既存の番号付き旧パスは互換案内としてのみ残せる。冒頭に「正本ではない」と明記し、現在の正本へ直接リンクする。本文を複製しない。互換案内から新しい仕様を引用しない。
- 1文書に1つの安定した文書IDを付ける（例: page.reservations.management）。文書IDは配置を変えても維持する。同じIDを複数の正本へ付けない。
- 重要な契約・項目・受入条件には意味を表す固定アンカーを付ける。参照は相対リンクとアンカー（例: lifecycle.md#hybrid-sync）で行い、「99 §2」「§5」だけを参照識別子にしない。既存番号は履歴照合用に残せるが、新しい参照の正本にはしない。
- 見出し名を変えるときは既存アンカーを保持するか全参照を更新する。今回の再配置では旧見出しも残して互換性を保つ。

<a id="ownership"></a>
## 文書の責務と正本

| 文書 | 記載する内容 | 他文書へ委ねる内容 |
|:---|:---|:---|
| domains/*/README.md | 対象範囲、読む順、関連資料、ルール・受入条件・未決事項の所在 | 詳細ルールの複製 |
| ドメイン業務ルール（必要な場合は business-rules.md） | 画面に依存しない制約、状態、不変条件 | 表示・入力操作、実装手順 |
| pages/ | 目的、利用者・権限、入口出口、表示、入力、操作、検証、エラー、受入条件 | API型・DBカラム定義の全コピー |
| lifecycle.md | 保存、確定、訂正、取消、再試行、競合・監査の契約 | 各タブの表示・項目の全コピー |
| workflows/ | 領域間の前後状態、担当者、契機、前提、引継ぎデータ、異常系 | ドメイン単独の詳細・実装台帳 |
| shared/ | 共通ルール・用語の正本、または既存正本への入口 | 領域別に同じルールを再定義すること |

既存の画面非依存ルールが横断フローや lifecycle に正本として置かれている場合はそこへリンクする。フォルダが違うだけで同じルールを複製しない。新しい business-rules.md は自然な責務分割が必要なときだけ作り、移す場合は旧本文を参照へ置き換える。今回は空のルール文書を作らない。

API wire契約は [backend/docs/api.yaml](../../backend/docs/api.yaml)、DB定義は backend/migrations が正本（[ERD](../architecture/erd.md)は参照入口）。実装はコード、テスト手順は [ops/testing](../ops/testing/README.md)、実行証跡・進捗の入口は [work/](../work/README.md)。仕様中の既存API表やモデル表は用途・対応を辿る参照情報として保持し、第二の型定義・DB定義にしない。既存シンボルは根拠として参照できるが、コードにあることだけで要望を決定しない。

<a id="status"></a>
## 決定状態と検証状態

冒頭に「文書ID・種別・決定状態・実装状態・実機検証状態・文書確認日」の表を置く。

| 軸 | 書き方 |
|:---|:---|
| 決定状態 | 未決／提案／合意済み。合意済みには決定者・日付・根拠を添える。混在する場合は節や条件ごとに書く。 |
| 既存文書の移行 | 決定根拠を確認できない部分は「既存記載を継承（決定根拠は未確認）」。合意済みへ格上げせず、既存の合意・未決の記述を保持する。 |
| 実装状態 | 未実装／一部実装／実装済み／未確認と、確認対象・根拠。既存本文の状態を引き継ぐだけなら「既存記載を継承（再監査なし）」。 |
| 実機検証状態 | 未実施／実施済みと対象環境・日付・結果・証跡。静的文書検査や Issue Closed を実機PASSへ読み替えない。 |
| 不足時 | 「未記載／要確認」は定義や根拠が不足。「未確認」は定義の検証が未完了。「該当なし（理由）」はその責務に含まれない。空欄・ハイフンで区別を消さない。 |

Planeは作業進捗の管理先。未検証をDoneにせず、仕様の決定と作業完了を同一視しない。文書確認日は構造・参照の確認日であり、業務承認日ではない。

<a id="page-format"></a>
## 画面仕様の本文形式

[画面テンプレート](templates/page-spec.md)を使い、以下の見出し名と順番を維持する。空の巨大な表を展開せず、既存で分かる項目・操作を記載し、不足を明示する。詳しい既存文章・図・表は該当節の下へ置く。

| 見出し | 記入内容・形式 |
|:---|:---|
| 目的・対象範囲 | 誰のどの業務を扱うか、対象と除外。画面目的を1段落で示す。 |
| 利用者・権限・前提 | 閲覧と操作の権限を分ける。利用者の職種、医院・患者・状態等の前提。不明な職種を権限から推測しない。 |
| 入口・出口 | URL、呼出元、引継ぎ値、戻り先。列は「入口／出口・契機・引継ぎ情報・根拠」。 |
| 表示情報・入力項目 | 表示は「項目・意味／表示条件」。入力は「項目・意味・型／形式・必須／任意・初期値・候補元・制約／根拠」。フィルタも入力に含む。APIの型を推測しない。 |
| 操作・業務ルール・状態遷移 | 操作表の列は「操作・実行条件・成功後状態／遷移・失敗挙動・根拠」。画面固有ルールを記載し、共通制約は正本リンク。必要な状態図はここに置く。 |
| 保存・取消・再試行・同時編集 | 下書き／即時保存／確定の境界、取消対象、再送条件、競合時の入力保持・破棄。ルーティング契約は lifecycle等へリンク。 |
| エラー・空状態 | 列は「状況・検知／表示・利用者の次の操作・根拠」。通信失敗、入力拒否、権限拒否、0件、競合を区別。未定のエラー文言を創作しない。 |
| 受入条件 | 列は「条件ID・前提／操作・期待結果・確認手順／証跡」。既存UATがある場合は条件の所在を参照し、実行済みを意味しない。 |
| 未決事項・関連仕様・根拠 | 未決項目・決定状態・次の確認先を記載。業務ルール正本、API/DB/実装の参照と元文書・確認日を示す。 |

すべての節で既存の詳細が別節にある場合は安定アンカーへリンクする。節を埋めるためだけに同じ本文をコピーしない。一覧と入力フォームを分けるのは既存内容の自然な単位に限る。

<a id="workflow-format"></a>
## フロー・保存契約の本文形式

[フローテンプレート](templates/workflow-spec.md)を使う。共通の順番は「目的・対象範囲」「担当者・権限・前提」「契機・入口・出口」「状態遷移・引継ぎデータ」「異常系・保存・取消」「受入条件」「未決事項・関連仕様・根拠」。フロー表の列は「担当者・前提・契機・前状態・後状態・引継ぎデータ・異常系／根拠」。詳細状態図・既存契約は該当節に配置する。

lifecycleでは「状態遷移・引継ぎデータ」に作成／確定／訂正の境界、「異常系・保存・取消」に送信先・保存単位・競合・取消・再試行を記す。今回のカルテ保存ルーティングの正本は [lifecycle.md#hybrid-sync](domains/medical-records/lifecycle.md#hybrid-sync)。API表は参照情報として根拠節に置く。

<a id="update-checklist"></a>
## 更新時の手順

1. 変更の目的・要求者・決定根拠を確認し、未決要望を既存仕様に混ぜない。質問への回答が何を承認したかを確認し、用語説明への「ok」を別の業務質問への一括承認と扱わない。
2. 正本の責務を選び、関連フロー・画面・API契約・DB・受入条件への影響を記録する。「なし」には確認範囲と理由を添える。
3. [オントロジーの変更確認](#ontology-maintenance)で新規・変更概念と語彙の影響を整理する。既存概念で表現できる場合は推奨語を再利用し、別概念なら違いを定義する。業務判断が未決なら定義・関係・制約もその状態を保持する。
4. 業務仕様・FRと受入条件の正本を更新し、影響する用語定義・概念関係・多重度・制約の参照を同じ変更で追従する。既存のオントロジー正本を更新し、本文を別ファイル・テンプレートに二重管理しない。画面ラベル・引用・内部識別子は対応を記載し、一括置換しない。
5. 根拠、決定状態、実装・検証の別軸、確認日を更新する。合意やPASSの証拠が無いときは未確認のままにする。
6. 仕様本文・受入条件・画面語彙・オントロジーの整合を差分レビューし、[記述完了の確認](#ontology-review-completion)で更新漏れ・用語揺れ・制約の矛盾を確認する。相違があれば修正し、未決なら依存する部分を未決として残す。
7. 参照先ファイル・見出しフラグメント・参照形式リンク・本文保全・88ルート対応・docs-symbol-driftを変更範囲で確認する。実行していないチェックは明記し、手動レビューを自動検査済みや実機PASSに読み替えない。

番号付き旧仕様の本文は正本に残る旧見出しへ照合できる。新しい深い参照は共通節の固定ID、または個別契約の意味を表すIDを使う。

<a id="ontology-maintenance"></a>
## 仕様変更ごとのオントロジー確認

新規仕様・既存仕様の変更・対話回答の仕様反映ごとに実施する文書上の手順。2026-10-14 14:57 JSTの「仕組みとしてオントロジーを整理するようにしましょう」（Sentinel_f2a8a28dc3708191a41c259986c5b619）が根拠。設定・スクリプト・CIを新設したものではなく、作成者とレビュー担当が以下を確認する。

予約ドメインの語彙・概念関係は[ontology/reservations.md](ontology/reservations.md#reservation-ontology)が既存の正本で、[shared/](shared/README.md)は入口。業務ルール・受入条件は各FRの正本、API・DB等は上記の技術正本を維持する。他領域も最初に既存の用語・概念の正本を探し、同じ概念の定義を領域ごとに複製しない。

| 確認対象 | 変更時に確認・記録する内容 |
|:---|:---|
| 概念の追加・変更 | 何を表すか、対象・対象外、短い例。既存概念を再利用するか、別概念なら何が異なるかを明記する |
| 推奨語・別名 | 正式な推奨語、文脈付き短縮、旧呼称・非推奨表現を確認する。同じ語が別概念を表す場合は限定語で区別する |
| 概念の関係 | どの概念が何を参照・担当・継承・生成するか、関係の方向と多重度を確認する。0または1、1、複数、未決を区別する |
| 制約・状態・境界 | 必須／任意、有効／無効、変更・取消・保持、時間・業務状態等の境界を該当FRへ照合する。関係図・定義が禁止操作を許可する矛盾を作らない |
| 画面語彙との対応 | ボタン・項目・状態ラベルと内部の業務概念の対応を記載する。利用者の呼称や引用、コード／API識別子を無断改名しない |
| 正本・参照 | 概念の正本と業務ルール／FR・受入条件の正本へ安定アンカーでリンクする。定義を移す場合は旧参照を更新し、並行管理しない |
| 決定状態・根拠 | 確定、提案、未決、未記載を区別し、決定者・日付・根拠を保持する。語彙整理だけで業務判断や多重度の未決を確定しない |
| 更新範囲・影響なし | 影響する定義・関係表・図・仕様・受入条件を更新する。概念への影響なしの場合も、確認した概念と理由を変更の確認記録へ残す |

確認記録は既存文書の決定根拠・関連仕様・文書確認日、または変更のレビュー記録に簡潔に置く。別の進捗台帳や概念定義のコピーを作らない。例えば所属数が変わるなら、用語定義だけでなく関係表・図・所属のFRと受入条件も照合する。一方、色値だけの変更で担当者や記録接続が変わらないなら、影響なしをその対象概念とともに記録する。

<a id="ontology-review-completion"></a>
### 記述完了の確認（業務承認・実装完了とは別）

- [ ] 追加・変更した概念の定義、既存概念との差異、推奨語・別名を正本で確認した。
- [ ] 関係・多重度・制約・状態境界が、参照するFR・受入条件と整合し、定義表・関係表・図の更新漏れがない。
- [ ] 仕様本文・画面呼称・受入条件に用語揺れや別概念の混同がない。維持する旧ラベル・引用・内部識別子は文脈・対応を示した。
- [ ] 正本の重複とリンク切れがなく、関連する参照側の追従を確認した。影響なしは対象・理由を記録した。
- [ ] 未決・提案を合意済みにせず、レビュー担当・根拠・確認範囲・未確認事項を記録した。

更新漏れ・矛盾が残る場合は該当チェックを未確認のまま残し、影響する仕様部分を記述完了と報告しない。記述完了は文書の整合性を確認した状態であり、未決業務の承認、実装・実機受入の完了、ドメイン全体の完了とは別である。未使用区分変更・業務分類未設定区分等の業務判断は、この手順の採用だけで承認済みにならない。実際の決定状態は該当FRの明示回答・根拠を参照する。

<a id="spec-kit-adaptation"></a>
## Spec Kitから取り入れる記述規約

[公式仕様テンプレート](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)と [品質チェックリスト](https://github.com/github/spec-kit/blob/main/templates/checklist-template.md)を2026-10-13に参照した。テンプレートの文章・コードは複製せず、以下を本体系に合わせて採用する。文書方式の採用時点ではCLI等を未導入としていた。その後の本体導入と現在の利用手順は [Spec Kit運用](../ops/spec-kit.md)を参照する。文書規約とCLIの導入状態は別に管理する。

- 目的節にユーザーシナリオと業務上の価値を記し、優先度とその理由を付ける。既存文書から優先度を判断できない場合は未決／要確認とする。シナリオは個別に確認できる単位にする。
- 操作節（保存契約では状態遷移節）にFR要件IDと定義の所在を記す。FR-ドメイン-意味の形式で、並べ替えで改番しない。1要件の定義は1箇所とし、他領域・シナリオ・品質レビューはリンクする。要件IDは合意済みという宣言ではない。
- 受入条件は「条件ID・Given（前提）・When（操作）・Then（期待結果）・独立確認・成功条件・確認手順／証跡」の表にする。成功条件は技術に依存しない観測可能な業務結果。未定の所要時間・件数目標を捏造せず、元のルールにある拒否・保持・遷移を観測条件にする。
- 前提条件・境界条件・異常系を明示する。原本の不足は未記載／要確認とし、コードから勝手に埋めない。『何を・なぜ』が仕様で、実装方式や作業順は関連設計・Planeへ分ける。既存の技術参照は根拠情報として保持し、業務要求に格上げしない。
- 品質チェックのチェック済みは要件記述の質を確認した意味だけを持つ。実装完了・実機PASS・臨床承認を意味しない。レビュー担当と根拠を記録し、未確認は未チェックのままにする。

業務を合意する際は、未決の優先度・前提・項目定義・成功条件をユーザーと確認し、その決定者・日付・根拠を元の正本へ記録する。feature specを別に作って既存domain正本を二重化しない。

[clarifyの公式手順](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)からは不足の検出と回答の仕様反映、[plan-template](https://github.com/github/spec-kit/blob/main/templates/plan-template.md)と [既存仕様の継続更新ガイド](https://github.github.io/spec-kit/guides/evolving-specs.html)からは仕様の維持と変更単位の計画を分ける考え方を参照する。ここでの「ドメイン正本＋変更単位の計画参照」は本プロジェクト向けの適用方針であり、公式の必須ディレクトリ構造という意味ではない。参照した公式mainのSHAは固定していないため、版固定済みとは記載しない。

clarificationの件数上限を理由に残りを推定する運用は採用しない。臨床・会計の不足事項はすべて未決のまま明示し、対話の質問だけを小分けにする。新しいconstitutionは作らず、既存の [臨床安全原則](specification.md)と [意思決定原則](../product-philosophy.md)の明示された内容を参照する。仕様品質は明確性・対象範囲・整合性・検証可能性・要件と受入条件の対応を確認する。実装計画・作業状態は関連設計／Planeを参照し、仕様のコピーを増やさない。
