<a id="requirement-fr-line-reservations-public-business-routing"></a>
### 公開対象と業務分類による接続

医院が公開した診療・トリミング・ホテルの予約区分をLINEから予約可能にする。ホテルは相談のみとせず予約対象に含め、入院は医院への相談へ案内する。動的に自由登録する予約区分に、固定の業務分類を必須で結び付ける。名称・表示グループから推測せず、分類により診療→通常カルテ、トリミング→専用記録、ホテル→宿泊管理、入院→入院管理へ接続する。記録生成タイミングは各分類の既存業務ルールに従い、LINE予約確定だけで通常カルテや実入院を作るものにしない。公開設定と業務分類は別概念で、院内利用可能でも自動的にLINE公開しない。


<a id="requirement-fr-line-reservations-acceptance-bounds"></a>
### 受付期間・休診日・時間外・対応可能人数

医院設定の受付期間内で受け付ける。休診日・時間外・対応可能人数を超える予約は不可とし、院内の警告確認による例外登録を飼主側に設けない。診療・トリミングの担当可否は登録済みシフトと医院別対応可能区分等の既存適格性で判定する。ホテルの休診日・時間外制限は選択する入室・退室日時に適用し、滞在途中の休診日だけで宿泊不可にしない（18:26合意）。ホテルへ医師人数・医師シフトの計算を代用適用しない。ホテルは17:35合意の医院別同時宿泊頭数上限で宿泊期間全体を判定する。ケージ・任意担当医師割当とは別で、計算・保存方式は設計へ分ける。


飼主の会員区分変更だけで予約受付条件を自動変更しない。[D04共同確認](../domains/owners-pets/lifecycle.md#agreement-owner-membership-dm-20261015)に従い、退亡者・他診/準から予約拒否を推定しない。上記の医院／枠／勤務・能力等の独立した既存条件は維持する。

<a id="requirement-fr-line-reservations-business-start-times"></a>
### 分類別・担当者別の開始時刻と変更（2026-10-15追加合意1）

通常診療のLINE予約開始時刻は営業時間から自動生成する。トリミングは医院が登録した開始時刻だけを予約候補にし、営業時間から自動生成した未登録時刻を加算しない。開始時刻は担当者別に設定でき、設定した時刻を変更できる。担当者別設定を反映しても、通常診療を登録時刻だけに限定する方式へ変えない。ホテル・入院はそれぞれ既存の受付契約に従う。

開始時刻の設定と実際に受け付けられることは別であり、営業時間・休診日・受付期間、予約時間全体の勤務・休憩、医院別の個人対応可能区分、有効性・公開条件、予定枠の重複と全体の対応能力を引き続き照合する。担当者別設定を勤務・能力・予約担当そのものと扱わず、他の担当者の設定や別医院の設定を流用しない。時刻変更だけでこれらの条件を免除しない。

明示指名ではその担当者の設定を使う。指名なしでは、担当者別の開始時刻設定を満たす適格候補を使って既存の全体対応可能性を判定する。例えばトリミングのある開始時刻がAの設定だけにあれば、Aが対応不能なときに、その時刻を設定していないBが空いているだけで受け付けない。受入可能でも[追加合意2](#line-no-nomination-unassigned)どおり実担当は未定のままで、設定の所有者や仮候補を実担当として保存しない。

時刻設定の変更は予約の自動変更ではない。保存済み予約の予定日時・明示担当・状態・履歴を黙って変更、移動、取消しない。変更後のLINE空き表示と確定時検証は最新の設定を用い、既存予約の予定枠は引き続き能力判定の対象とする。選択後に設定が変わり受け付けられなくなった場合は、入力を保持して日時を再選択する。既存予約の変更は既存の権限・状態・適格性・確認条件を持つ別操作として扱う。

決定根拠：質問 Sentinel_0db1cd35a25881918ab9f7b72b550f3f「通常診療は営業時間から自動で時刻を出し、トリミングは医院が登録した開始時刻だけに限定する、という理解で合っていますか？」に直接返信したユーザー Sentinel_9038af92002c819191dd97459b391b13「はい」「ちなみに時刻は変更可能にしてください」「あと、担当者別に設定できる必要があります」。2026-10-15の追加合意として扱う。具体的な時刻間隔・同時枠数・件数上限・未指定の既定値・遡及変更はこの回答から追加しない。従来の加算モードは現行差分であり、トリミングの目標仕様へ維持しない。実装・実機確認は未実施。


<a id="line-scheduled-slot-basis"></a>
#### LINEの空き判定は予約の予定枠を基準とする（最新訂正）

診療・トリミングのLINE空き表示と確定時再判定は、予約の予定開始・予定終了、既存予約の予定枠による重複、登録済みシフト・休憩・医院別対応可能区分など合意済みの適格性を基準にする。実際に診療中かどうか、診療開始／終了の実状態、予定終了超過、実診療の見込終了を追加の空き判定条件にしない。予定枠が空き、他の受付条件も満たす場合、先行診療が予定終了を過ぎても診療中であることだけで判定不能・受付不可へ変えない。

診療が終了していても、既存予約の予定枠を実終了だけで短縮・除外しない。取消等の既存計数対象の境界は保持する。予定枠に正幅重複がある場合の指名済み占有・対応能力の判定、全予約時間の勤務／休憩条件、全員／一部未登録の区別、依存情報の取得失敗・探索未完了時の扱いは維持する。診療状態を確認しないことを、予約予定の重複判定を廃止する意味にしない。

本訂正は通常時間指定のLINE診療・トリミングに適用する。ホテルの予約済み・実滞在を数える全期間定員管理、予定超過でも未退室なら計数する契約は変更しない。院内の診療中引継ぎ、スタッフ／シフト変更時の未終了指名予約保護、開始・終了の明示操作も別契約として維持する。

決定根拠：ユーザー Sentinel_08ce4d91de608191a05c30220331a832「LINEでは空きが前提です、診療中とかはチェックしなくていいです」。文書編集は Sentinel_2334916604f88191830b7a194c74bf85「許可します」、Sentinel_61b62c3381b88191ad0d5af32bdcffb5「docs/配下のみ許可です」による個別許可。予定終了超過の診療中医師を判定不能としてLINE受付禁止にする案は不採用。実装・実機検証は未実施。

<a id="requirement-fr-line-reservations-no-nomination"></a>
### 指名なしとホテルの担当分離

診療・トリミングで指名なしは医院が許可した場合に選択可能とする。LINE予約は実担当が未定のまま確定し、後から院内で担当者を決める。予約確定時に医師・トリマーを自動決定しない。登録済みシフト・休憩・医院別の対応可能区分等で受入可否を判定し、未登録を勤務可能と推定しない。既合意の全員／一部未登録の区別を保持する。受入可否の計算に使う仮候補と実担当を分け、固定指名と他の未定予約を含む全体の対応可能性を確認しても、計算上の候補を実担当として保存しない。ホテルでは指名医師を選ばず、宿泊管理の担当医師は任意とし、未設定だけで受入開始を拒否しない。ホテルの指名医師なしを診療の「指名なし」設定・医師シフト・自動医師割当へ置き換えない。


<a id="line-no-nomination-unassigned"></a>
#### 指名なしは担当未定で受け付け、院内で後から決める（2026-10-15追加合意2）

指名なしの予約では、保存結果、飼主の確認・完了・マイ予約、院内の未定列・予約編集で、担当未定という同じ事実を扱う。判定用の仮候補を担当者名として表示・通知したり、担当履歴・引継ぎ・接続先の記録へ実担当として転記したりしない。再計算で候補の組合せが変わっても実担当未定を維持する。明示指名の予約と既存の固定指名は保持し、指名なしを受け入れるために別予約の担当を自動変更しない。

後からの担当設定は、同じ予約を院内で編集して明示確定する。業務分類に応じた担当種類、医院・個人の対応可能区分、有効性・勤務・休憩、既存権限・状態別の編集制限をその時点で再確認する。診療中の引継ぎは既存の残り担当時間の契約に従い、診療の変更制限をトリミングへ独断で拡張しない。担当を決める期限や新たな自動割当方式は本回答から追加しない。

担当未定で保存できることは、LINEの空き・確定時検証を免除する意味ではない。[対応能力の技術契約](../../design/domains/reservations/technical-spec.md#capacity-assignment-contract)に従い、固定指名の占有、全時間を同じ適格者が担当できるか、他の未定予約との共有能力・部分重複を仮計算する。対応不能または判定不能なら確定せず、入力保持・再選択へ戻す。院内の警告確認例外をLINEへ広げない。

決定根拠：2026-10-15の確認質問 Sentinel_8fcd9be0b3d081918f0e47e2a6f06025 の第2項「LINEの『指名なし』予約時に担当を自動決定しますか？ それとも、担当未定で受け付け、院内で後から決めますか？」に対するユーザー Sentinel_0ebd3189f3408191ae0f69b158fcd353「2 担当未定で受け付け、院内で後から決めます」。従来の自動委譲・no_staff_modeによる実担当自動決定は目標仕様と異なる現行説明として区別する。第1項の開始時刻方式は後続回答による[追加合意1](#requirement-fr-line-reservations-business-start-times)で確定した。担当未定受付と開始時刻の提示方式を別の契約として扱う。実装・実機検証は未実施。


<a id="requirement-fr-line-reservations-reselect-after-change"></a>
### 状況変化時の入力保持と日時再選択

日時選択後の状況変化によって受付不可となった場合は、入力を保持して別日時を再選択できるようにする。空き表示だけで受付を保証せず、確定時にも合意した受付条件へ従う。別予約の重複作成・条件を迂回した例外登録を行わない。エラー形式・取得／保存・再試行の具体的方式は設計とし、ホテル受入基準は17:35合意へ従い、未承認の別枠方式を追加しない。


<a id="requirement-fr-line-reservations-owner-cancel"></a>
### 来院受付前の飼主取消・変更案内

来院受付前は当日でも飼主から取消可能とする。本人・医院スコープと既存の取消履歴／作成済み記録保持を維持し、受付後・診療後・支払い確定後の訂正を飼主取消へ広げない。飼主からの直接の日時等変更・取消復元は設けず、変更希望は医院連絡へ案内する。院内で承認済みの誤取消復元を飼主側へ展開しない。現在の確定ステータス限定UIは実装参照であり、受付前という業務境界の全状態対応を実装済みとしない。


<a id="requirement-fr-line-reservations-required-setup"></a>
### 必要設定不足の新規選択不可と宿泊期間

所要時間・業務分類など必要設定が不足する予約区分は選択不可とし、必要に応じ医院連絡を案内する。設定不足を他分類の推測や勤務の推測で補わず、飼主へマスタ設定作業を求めない。所要時間と予約時間の既存契約を維持するが、ホテルの宿泊期間へ通常診療・トリミング予約の同日制約を適用しない。宿泊に必要な期間・受付条件の具体的設計は宿泊管理と照合し、通常予約の時刻枠だけで複数日の受入可否を推定しない。

### 医院別同時宿泊頭数と宿泊期間全体の受付判定（17:35合意）

医院ごとに、ホテルで同時宿泊できる頭数の上限を設定する。LINEホテル予約は、宿泊期間全体を通して同時宿泊頭数がその医院の上限内となる場合に確定する。一日の入口時刻だけや平均頭数で、期間途中の超過を見落とさない。既存の同期間のホテル受入と新しい宿泊予約を合わせた同時宿泊頭数を判定し、別医院の上限・人数を流用しない。計数対象・状態・期間端点と入退室の受付条件は下記18:26合意で明示する。照合・計算・保存方式は設計として分ける。入院をホテル頭数へ機械的に分類変換する合意ではない。

上限未設定または期間中の上限超過時はLINE予約を確定せず、医院への相談へ案内する。未設定を無制限・ゼロ・既定値として補完せず、超過を飼主の警告確認で許可しない。状況変化で受付不可になった場合の入力保持・別日時再選択、医院設定の受付期間・休診日・時間外の条件も維持する。相談案内だけで院内の上限超過受入を許可したものにはしない。ホテルの休診日・時間外制限は下記18:26合意の入室・退室日時へ適用し、滞在途中の休診日へ拡張しない。

ホテルの受付は医師指名・医師シフトで判定しない。ホテル予約の指名医師なしと、通常診療・トリミングの同日予約制約を宿泊期間へ適用しないことを維持する。同時宿泊頭数の上限は、[ケージ割当](../screens/09-hospitalization-form.md)・[ホテルの任意担当医師](../screens/settings/master-reservation-type.md#internal-batch-hotel-care)とは別の概念。ケージ割当と任意の担当医師設定は宿泊管理で扱い、担当医師未設定だけで受入開始を拒否しない。別責任担当・非医師担当・一名必須を追加しない。空きケージ数から上限を自動生成したり、ケージ必須へ変更したり、医師数から宿泊能力を推測したりしない。既存のケージ任意・占有表示／連結保護、宿泊管理の期間・状態・記録契約を保持する。

<a id="hotel-counting-boundaries-1826"></a>
#### ホテル同時宿泊頭数の計数・状態境界（18:26合意）

同じ宿泊は予約と宿泊管理の双方に現れても1回だけ計上する。予約済み・滞在中を数え、取消・未来院・退室済みは除外する。ホテルの頭数を数え、入院をホテルへ機械的に分類変換しない。頭数上限とケージ・任意担当医師の割当は引き続き別概念。

| 対象・契機 | 計数／判定結果 |
|:---|:---|
| 予約済み・滞在中のホテル宿泊 | 対象医院・対象期間の同時宿泊頭数へ含める。同じ宿泊の予約と管理レコードを二重計上しない |
| 取消・未来院・退室済み | 同時宿泊頭数から除外する。履歴・記録の削除を意味しない |
| 退室予定時刻と次の入室時刻が同じ | 予定期間の重複はない。期間途中の超過判定は維持する |
| 延泊 | 変更後の期間で同時宿泊頭数上限を再判定する |
| 退室予定を過ぎても未退室 | 滞在中として扱う。予定終了だけで自動退室・計数除外しない |

予定期間の端点判定と実際の未退室を区別する。予約・宿泊管理の対応キー、更新・同時操作・保存方式は技術設計であり、二重計上や予定超過時の自動除外を許可する裁量ではない。延泊超過時の運用は[業務5点合意](#hotel-extension-over-capacity)へ従う。具体的な調整案・実績・確定の保存方式は宿泊管理の設計。

<a id="hotel-extension-over-capacity"></a>
#### 延泊定員超過時の運用（業務5点合意）

延泊で同時宿泊頭数上限を超える場合、実滞在は記録し続け、宿泊管理の責任者が他予約・退室見込みを確認して調整した後に延泊を確定する。初期仕様では定員超過の例外承認を設けない。実際に滞在している患者を予定終了だけで退室扱いにせず、既存予約を自動取消しない。LINEの上限超過受入禁止は維持する。

延泊希望・未確定の調整案と、実滞在の記録・確定済み予定を区別する。超過中に実績記録を拒否して状態を偽ることも、希望を記録しただけで延泊受入を確定することもしない。調整後も全期間を再判定してから確定する。責任者の具体的権限・連絡手順・調整案の画面／保存と同時処理は宿泊管理の設計であり、別予約の変更権限・既存安全条件は免除しない。

## 1. システム概要

本システムは、飼主が LINE アプリから直接病院の空き枠を確認し、診察予約を完結させるためのプラットフォームです。

### 特徴
- **シームレスな体験**: 検証済み LIFF identity に対応する同一 clinic の `line_customers` に保存済みの氏名・電話等がある場合、二回目以降に補完する。LINE profile 自体から電話番号を取得する契約ではない。
- **高精度な空き枠計算**: スタッフの勤務シフト、休憩時間、既存の院内予約をリアルタイムに集計。
- **カルテ統合**: LINE 経由の予約は、院内の受付カンバンボードへ「source=line」として自動反映。

## 2. 飼主側の予約フロー (LIFF App)

以下は現行実装の説明であり、新合意と差がある箇所は上記17:23業務契約を優先する。実装正本は別エントリ `frontend/line-reserve` と画面仕様 [37-line-reserve-owner-flow.md](../screens/37-line-reserve-owner-flow.md)。ローカル dev の Vite rewrite と maintenance / mock 上書きも 37 を正本とする。概要のみ:

1.  **お客様情報**: 氏名・電話（必須）、飼主名（任意）、ペット選択/新規入力。
2.  **コース選択**: 診察、ワクチン、トリミング等（マスタで公開設定されたもののみ）。`category=trimming` 時はトリミングコース → オプションへ分岐。
3.  **スタッフ選択**: 担当の指名、または設定が有効な場合の「指名なし」。`staff_id=0`は旧wireの現行説明であり、[目標API](../../design/domains/reservations/technical-spec.md#reservation-api-closed-contract)はnullを使う。指名なしの保存結果は[追加合意2](#line-no-nomination-unassigned)に従い担当未定とする。
4.  **日付・時間選択**: カレンダー形式の空き日と当日空き時刻。[追加合意1](#requirement-fr-line-reservations-business-start-times)では、通常診療は営業時間から生成し、トリミングは医院が担当者別に登録した開始時刻だけを使う。時刻は変更可能で、既存の受付・能力条件を照合する。新しい固定間隔は本合意から定めない。
5.  **ご要望 → 確認 → 完了**: 任意テキスト後に確定。成功時は予約完了通知（飼主 LINE + 病院メール、best-effort）。
6.  **マイ予約**: 一覧と **確定（confirmed）** のみキャンセル可。予約の変更 UI は無い。

> **注意**: 予約確定時の **氏名+電話による `line_customers.owner_id` 自動紐付けは行わない**（SEC-CS2-F02）。既に link-token / スタッフ経路で紐付いている顧客のみ、予約へ owner/pet を best-effort 反映する。

## 4. 時間枠計算ロジック (Timeslot Engine)

以下は診療・トリミングの旧計算の参照説明であり、[追加合意1](#requirement-fr-line-reservations-business-start-times)の分類別・担当者別開始時刻を実装済みと示すものではない。目標仕様では通常診療を営業時間から生成し、トリミングは担当者別の登録開始時刻だけへ限定したうえで、勤務・休憩・予定枠・能力を検証する。旧加算モードはトリミングへ残さない。ホテルの受入基準は別契約。以下は既存要素の説明：

1.  **Positive (加点要素)**: 指定されたスタッフの「勤務時間」。
2.  **Negative (減点要素)**: スタッフの「休憩時間」、医院の「休診日」。
3.  **Conflict (除外要素)**: 既に入っている「診察予約」「トリミング予約」等の既存予約（予約区分は general/trimming の2種）。

```mermaid
flowchart LR
    Shift["スタッフの勤務時間<br/>Positive（加点）"]
    Rest["休憩時間・休診日<br/>Negative（減点）"]
    Appt["既存予約（general / trimming）<br/>Conflict（除外）"]

    Shift --> Calc["空き枠の動的合算"]
    Rest --> Calc
    Appt --> Calc
    Calc --> Slots["当日の空きスロット"]
```

---

### 作成時の再検証と限界

空き枠表示後に状態が変わり得るため、LIFF の確定は `liff_service_reservations.go` から `ValidateAndCreate` を呼ぶ。予約種別・appointment conflict を transaction 内で再検証し、明示 staff の医院所属・capability・LINE 公開/active を検査する。追記（2026-10-07 監査）: **選択時刻の勤務 shift 再検証は未実装**という既知 source gap の正本は [reservation-to-record-flow.md §7](../workflows/reservation-to-record-flow.md)（Deferred / known gaps）。空き枠表示を保存時の shift 保証と扱わない点は同節に従う。

## 5. 通知のライフサイクル

予約確認・変更・予約リマインドの飼主LINEは、DM未設定／不要だけで除外しない。[D15目的別条件](lstep-integration.md#crm-dm-purpose-contract)と既存のLINE連携・アカウント・ブロック・本人／宛先・独立停止等を満たすことが前提。日付だけの未予約予定を名前だけで予約通知例外へ含めない。これは病院メールの配信希望変更や以下の未実装機能の実装済み宣言ではない。

- **予約完了時**: 病院への受付通知 ＋ 飼主への完了メッセージ。
- **キャンセル時**: DB のキャンセル状態は同期的に更新する。飼主 LINE / 病院メール通知は設定済みの場合の bounded background best-effort であり、即時到達や成功を保証しない。
