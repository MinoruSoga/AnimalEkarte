<a id="requirement-fr-common-retention-interim"></a>
### FR-common-retention-interim — 業務履歴・監査の保持と製品境界

業務履歴・必要監査・予約再送の最小対応を共通保持方針へ接続する。通常の取消・非表示・論理削除は保持された事実へのアクセス／業務状態を変える操作であり、物理廃棄の許可ではない。保存年数による自動削除・一括物理削除は今回の通常製品仕様に設けず、必要時の別手続きで対象・保存義務・承認・復旧方法を確認する。API／インフラログ等の既存プラットフォーム保持はこの承認から変更しない。

<a id="requirement-fr-common-retention-visibility"></a>
### FR-common-retention-visibility — 非表示・取消・削除・復元の区別

各Dの取消／非表示／論理削除／復元／履歴参照の既存合意を保持。保持することと一般画面に公開することを区別し、論理削除情報を通常一覧へ勝手に戻さない。空の誤作成カルテの削除、記入済みの訂正、既存追記の保持、会計取消と金銭復元／実返金の違いは各正本のまま。通常カルテの旧finalizedだけの通常編集拒否は[D03最新合意](../domains/medical-records/lifecycle.md#medical-record-agreement-autosave-20261015)で置換するが、以前の保存版・追記・監査を削除する許可ではない。全対象の「削除」を一括で同じAPIや物理動作に置換しない。

D03のタブクリアはタブを開いた時点、履歴複製取消は対象複製の直前への復元。自動保存済みの対象には新しい復元状態・元操作との対応・実編集者／時刻を履歴として残す。新規行を通常表示から除く場合も元ID・作成／復元の履歴を保持し、原本画像object・保存版・必要監査を物理削除しない。他者版・後続操作や別ownerの実行を無警告で消さず、返金・在庫戻し・通知回収を復元の副作用にしない。タブ内の入力復帰と、保存事実の保持／廃棄を区別する。

<a id="requirement-fr-common-retention-trace"></a>
### FR-common-retention-trace — 履歴・監査・再送の整合

保存期限や将来の削除手続きは、原事実・訂正関係・必要監査・再送キーの非再利用と整合する必要がある。[予約の保存詳細](../../design/domains/reservations/technical-spec.md#reservation-storage-details)を維持。業務履歴、監査sink、receipt／冪等キー、外部送信履歴を混同せず、削除を利用した同一効果の再実行を許可しない。

監査の主ownerはauditで、各業務ownerが対象操作・actor・時刻・対象・成功／失敗・必要txを明示する。必須監査の存在はバックアップから復旧可能という証明ではない。秘密情報や不要な個人情報をログへ増やさない。保持対象とアクセス権は独立し、C04の閲覧／照会scopeを維持する。

## 期限付き配送コピーとURL（現行実装参照）

[shared_file_service.go](../../../backend/internal/lstep/shared_file_service.go)を同じ基準commitで読み取り確認した。shared_filesは独立したアップロード記録・object key `shared/<clinic>/...` を持ち、LINE配送用URLと管理画面用URLを発行する。CleanupExpiredは143時間以上経過した対象のstorage objectを削除し、DB側をsoft-deleteする。署名URLは配送1時間、対話15分。CleanupExpiredコメントには旧24時間URLの説明が残るが、現行定数は1時間／15分であり混同しない。

この現行経路は配送用ファイル管理の実装だが、UploadのContentは任意入力を受けるため、全ファイルが再生成可能な一時コピーで、別の業務原本が必ず保存されるとは証明できない。単にshared_filesという名前であることを保持方針の例外根拠にしない。CleanupExpiredの現在の143時間条件には一時分類・別原本保持確認がないため、承認済みの業務履歴保持へ適合済みとはしない。CleanupExpiredの実稼働／scheduler配線は本読取だけでは検証していない。

<a id="requirement-fr-common-retention-delivery-copy"></a>
### FR-common-retention-delivery-copy — 保持方針を満たす配送コピー削除の技術条件

業務上の保持範囲の追加承認ではなく、上記合意を守るための技術的な成立条件。実装済み・運用変更済みを意味しない。

- D15が一時配送用と分類でき、別原本の所在・保持を確認できる対象だけを配送コピーのcleanup対象として判定する。必要な業務履歴／監査そのものを一時コピー扱いにしない。
- 一時分類または別原本保持を確認できない対象は、確認まで自動cleanup対象から除外する。対象を安全に識別できない現行の一律cleanup経路は、識別・保護条件を実装／検証するまで自動削除を停止する必要がある。今回の文書変更自体はサービスやschedulerを停止／変更しない。
- 確認済み配送コピーについては、現行143時間という技術的期限を無期限へ変更する新方針を作らない。業務原本と必要監査の保存年数による自動削除禁止とは対象を分ける。
- 署名URLのアクセス期限（配送1時間／対話15分）とstorage object削除・DB soft-deleteを別に扱う。原本保持のためにURLを長寿命化したり、URL失効を原本廃棄と扱ったりしない。
- API／分類方法・原本参照・既存fileの判定方式、失敗／途中削除からの復旧はD15技術設計で具体化する。未判定を「コピー確認済み」に自動移行しない。

この技術条件はcleanupの新実行許可や法令の年数判断ではない。現行実装との差と各fileの原本確認はD15/C05の設計・適合残件として残す。
