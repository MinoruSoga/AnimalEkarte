## 正本・適用順

[全体要件§2.1](../specification.md)の臨床安全は[業務効率の思想](../../product-philosophy.md)より優先する。安全手段の選択は効率化の検討対象でも、安全性自体を削らない。具体的な保存・臨床状態・薬量条件は[D03正本](../domains/medical-records/lifecycle.md)と[技術契約](../../design/domains/medical-records/technical-spec.md)。本書から他ownerに未承認の一律確定ロックや新職種を導入しない。

<a id="requirement-fr-common-safety-patient"></a>
### FR-common-safety-patient — 患者文脈と死亡ゲート

識別表示を伴う死亡個体の選択と、新規記録／臨床操作の禁止を区別する。既存記録の閲覧／許可済み追記まで禁止へ拡大しない。未知status・患者／医院／関連の照合失敗を正常へ置換しない。実際の操作例外は各D正本。staff向け特記をowner向け情報へ漏らさない（[患者選択](../screens/00-pet-selection.md)）。

<a id="requirement-fr-common-safety-finalize"></a>
### FR-common-safety-finalize — 確定・訂正と安全性

カルテは医師による明示確定と確定後の不変化・追記訂正を維持し、診療終了／支払を自動確定としない。確認ダイアログだけで安全性を成立させず、サーバ状態検証・lock・権限を必要とする。通常Undo停止や記入済み記録の専用訂正を守り、共通UIの閉じる／戻る操作で金銭・在庫を巻き戻さない。保存§2のハイブリッド同期を本整理では変更しない。

<a id="requirement-fr-common-safety-evaluation"></a>
### FR-common-safety-evaluation — 未評価・不明と安全判定の分離

評価不能時の理由付き手入力はD03の合意条件と医師確認に従う。評価可能な絶対上限超過を確認で解除しない。通信・認可・患者／薬剤照合の失敗を「未設定だから手入力可」へ変換しない。薬量の数値・対象薬・種・単位・出典の医師承認は別工程で、ここでは承認しない。未完了プランの警告確認後確定可と、取得失敗で完了不明を区別し、確認だけで実施済みへ変更しない。

<a id="requirement-fr-common-safety-audit"></a>
### FR-common-safety-audit — 意味のある変更を追えること

臨床・会計・権限の重要変更は明示された監査経路でactor・時刻を追跡する。全136テーブルの一律自動監査とはしない。integrityが必要な経路は必要監査失敗時にfail-closed。同一txの有無と選定仕様／現行実装差は[共通技術接続](../../design/shared/integration-contracts.md)で分ける。担当医を編集actorの代用にせず、確認医師・編集者・担当・指名は別概念を維持する。

<a id="requirement-fr-common-safety-automation"></a>
### FR-common-safety-automation — 自動化の停止・失敗・監査

業務状態を変える自動化は停止手段・失敗通知・手動代替と追跡可能性を持つ。手動ownerのuse caseを再利用し、定義された17トリガーやAPIキー保存をLステップ再開の証拠にしない。#259等の既存稼働停止条件を解除しない。自動化による便利さを理由に未確認の臨床値・資格・同一個体・配信対象を推測しない。

| D10/D11/D12/D13 | 請求・見積・実入出金・締め・在庫の独立した履歴 | カルテ訂正から自動金銭／在庫巻戻ししない |

## 未確認・仕様完成の残件

全ownerの具体的なAC／権限／状態／ID／版／監査／競合契約をowner対応表とX01〜X08で照合し、一般原則の再掲だけでなく対象操作の成功・拒否・失敗／結果不明時条件を独立レビューした。患者context・D20公開範囲・原本保持・旧版更新の指摘は正本へ反映済み。今回の文書範囲に未解消の重大指摘なし。臨床数値の医師承認、実機・実装・運用／法的適合は別工程であり、新たに見つかる仕様不足を対象外へ隠さない。
