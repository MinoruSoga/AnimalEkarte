# 業務効率ソフトウェアとしての設計思想 (Product Philosophy)

> **目的**: 業務効率ソフトウェアとしての意思決定原則(5ステッププロセス)を定義する。
> **読者**: 全開発者・PO。
> **タイミング**: 新機能着手前・仕様議論時(必読)。

> **対象**: Animal Ekarte を「次世代の業務効率ソフトウェア」として進化させるための意思決定原則。
> **位置づけ**: 本書は技術設計 ([architecture/overview.md](architecture/overview.md)) や UI 規約 ([spec/design-system.md](spec/design-system.md)) の上位にある。**何を作るか・作らないかを決める文書**であり、どう実装するかの文書ではない。
> **原典**: [Elon Musk's Five-Step Design Process](https://www.jeffwinterinsights.com/insights/elon-musks-five-step-design-process)

---

## 0. 大原則 — 順序を逆行してはならない

```
① 要件を疑う → ② 削除する → ③ 簡素化・最適化する → ④ サイクルを速くする → ⑤ 自動化する
```

この 5 ステップは**この順序でのみ**適用する。順序こそがプロセスの本体である。

> "Possibly the most common error of a smart engineer is to optimize a thing that should not exist."
> （賢いエンジニアが最も犯しやすい過ちは、存在すべきでないものを最適化することである）

業務効率ソフトウェアにおける典型的な失敗は、**紙とExcelの業務をそのままデジタル化し、その非効率を最適化・自動化してしまう**ことである。動物病院の現場慣習（紙カルテの転記、二重帳簿、手書き集計）は「デジタル化すべき対象」ではなく、まず「①存在を疑い ②削除を検討する対象」である。

---

## ① 要件を疑う (Make Requirements Less Dumb)

### 原則

- **すべての要件には責任者の名前を付ける。** 「現場の要望」「業界の慣習」「以前からそうだった」は要件の出所として認めない。部門やドキュメントではなく、**特定の個人**が要件に責任を持つ。名前のない要件は疑えないからである。
- 賢い人が出した要件ほど危険である。疑われにくいからだ。PO・獣医師・受付リーダーの要件であっても、必ず「なぜ」を遡って検証する。
- 要件は「業務の目的」で記述する。「〇〇画面に△△ボタンが欲しい」は要件ではない。「会計締めに毎日 40 分かかっている。これを 10 分にしたい」が要件である。

### 本システムでの適用

| 来た要望 | 疑うべき問い |
|---|---|
| 「この帳票を印刷したい」 | その紙は誰が何のために見るのか。画面・通知で代替できないか。 |
| 「確認ダイアログを追加してほしい」 | 誤操作の真因は何か。ダイアログは操作を遅くするだけで誤操作を防がない（形骸化する）。Undo・確定ロックで代替できないか。 |
| 「Excel に出して集計したい」 | 集計結果そのものを画面に出せば Excel 工程ごと消せるのではないか。 |
| 「入力項目を増やしてほしい」 | その項目は誰がいつ読むのか。読まれないデータの入力は現場の時間の純損失である。 |

### 実例（本プロジェクトの教訓）

- **予約入口の一本化**: LINE予約・予約管理・当日受付という 3 入口が別データを作る要件をそのまま実装せず、`appointments` を単一の source of truth とする再定義を行った（[reservation-to-record-flow.md](spec/reservation-to-record-flow.md)）。要件を疑わなければ、3 系統の二重作成バグを恒久的に「最適化」し続けることになっていた。
- **推測オーバー実装の禁止**: 仕様にない「気の利いた」追加は要件のない実装であり、削除対象を自ら生産する行為である（運用ルールとして確立済み）。

## ② 削除する (Delete the Part or Process)

### 原則

- **最良の画面は、存在しない画面である。最良の入力は、入力しないことである。**
- 削除の目標値: 削除した結果、**10% は後で戻すことになる**くらい攻めて削る。「一度も戻す羽目にならない」なら削除が足りていない。
- 機能・画面・入力欄・クリック・確認ステップ・データの二重保持 — すべてが削除の対象である。
- 「念のため残す」は禁止。使われていない機能は保守コスト・学習コスト・バグ表面積であり、ゼロコストではない。

### 削除の優先ターゲット

1. **二重入力**: 同じ情報を 2 回入力させる箇所（受付→カルテ、カルテ→会計、会計→締め）。上流で入力された事実は下流に自動で流れなければならない。
2. **二重管理**: 同じ事実を 2 箇所のデータで持つ構造。payment_method の二重管理が close/monthly 集計バグを生んだ教訓の通り、二重管理は必ず不整合を生む。
3. **転記・確認作業**: 人間がシステム A を見ながらシステム B に打ち込む工程。工程ごと削除する。
4. **形骸化した確認**: 全員が無意識に「OK」を押すダイアログ。押させるコストだけが残る。

### 判断基準

新機能の議論では、まず「**この機能で削除できる業務工程は何か**」を問う。削除できる工程がゼロの機能追加は、現場の複雑さを増やすだけの可能性が高い。

---

## ③ 簡素化・最適化する (Simplify and Optimize)

### 原則

- 簡素化は**①②を通過した後にのみ**行う。存在意義が検証されていない画面の UX を磨くのは、存在すべきでないものの最適化である。
- 目指すのは「機能が多いのに使いやすい」ではなく「**工程が少ないから速い**」である。
- 現場の 1 操作は 1 日に数十〜数百回繰り返される。**1 クリック・1 画面遷移の削減は、現場では毎日の分単位の削減**である。

### 本システムでの具現化

- **コンテキストを壊さない**: サイドパネル編集・リアクティブ検索により、画面遷移そのものを削減する（SPECIFICATION 2.2）。画面遷移は「現場の思考の中断」であり、遷移アニメーションの高速化ではなく遷移の削除で解決する。
- **入力より選択、選択より自動補完**: 診察室のタブレットでフリー入力は最も遅い操作である。頻出パターンのテンプレート化・前回値の引き継ぎ・マスタからの選択を常にフリー入力より優先する。
- **例外だけを人間に見せる**: 検査異常値の自動ハイライトが原型である。正常なものを人間に確認させず、異常・要判断のものだけを浮かび上がらせる。一覧画面は「全件を見る場所」ではなく「対応が必要なものが見える場所」として設計する。
- **デフォルトを賢くする**: 大半のケースで正しい初期値（診療日=今日、税率=区分から自動、次回ワクチン=接種日から自動計算）を置き、ユーザーの仕事を「入力」から「確認と例外修正」に変える。

## ④ サイクルタイムを短縮する (Accelerate Cycle Time)

### 原則

高速化するのは**①〜③を経て残った正しい工程だけ**である。誤った工程を高速化してはならない。

対象となるサイクルは 2 つある。

### 4-1. 現場業務のサイクル

外来 1 件のサイクル（受付 → 診察 → 検査 → 会計 → 次回予約）と、1 日のサイクル（開院 → 診療 → 締め）を計測し、短縮する。

- **主要メトリクス**（機能の成否はこれで判定する。「使いやすくなった気がする」は成果ではない）:
  - 受付から診察開始までの待ち時間
  - カルテ 1 件の記載所要時間
  - 会計 1 件の処理時間（患者を待たせている時間）
  - 日次締めの所要時間
  - 予約 1 件の登録操作数（クリック数・入力欄数）
- Tesla Berlin が Model Y を競合の 30 時間に対し 10 時間で組み立てるように、**同じ診療品質でサイクルが 1/3 になること**が「次世代」の定義である。診療の質を落とす高速化は臨床安全原則（SPECIFICATION 2.1）に反するため採らない。

### 4-2. 改善のサイクル

- 現場のフィードバックが実装され現場に届くまでのリードタイムを短く保つ。`main` での日常開発 → `main`→`staging` PR → `staging` push 後の STG 検証というこのプロジェクトの運用は、このための構造である。
- 大きな機能を長期間隠れて作らない。薄い縦切り（vertical slice）で早く現場に当て、要件の誤りを早く発見する。**要件の誤りは、①に戻って修正する**。

---

## ⑤ 自動化する (Automate) — 最後に、監視付きで

### 原則

- **自動化は 5 番目である。** 欠陥のあるプロセスを自動化すると、欠陥が高速・大量に再生産される。手動で運用され、正しさが検証されたプロセスだけを自動化する。
- 自動化は導入して終わりではない。**自動化されたプロセスは人間の目から消える**ため、監視と改善を継続しなければ静かに腐る。

### 本システムでの適用

| 自動化 | 前提となる検証済みプロセス | 監視 |
|---|---|---|
| ワクチン次回予定の自動計算 | 接種間隔ルールの臨床的正しさ | 計算結果の画面上での確認可能性 |
| CPM 連動の自動配信（15 トリガー） | 手動運用で検証された配信条件・文面 | 配信ログ・エラータグ・停止手段 |
| 日次・月次の自動集計 | 締めプロセス自体の正しさ（②で二重管理を排除済みであること） | 実査との過不足管理・audit_logs |

### 自動化の鉄則

1. **止められない自動化を作らない**: すべての自動処理に停止手段と手動代替経路を用意する（Lステップ Write API の一時停止運用が実例）。
2. **黙って失敗させない**: 自動処理の失敗はログに書いて終わりではなく、人間に届く形で通知する。サイレント障害は自動化の最大の敵である（silent-failure 監査の教訓）。
3. **監査可能であること**: 永続的な業務状態を変更する自動化は、明示した専用監査 sink（原則 `audit_logs`）で追跡する。例外は各仕様に sink・保持・照会方法を記載し、「システムが勝手にやった」をブラックボックスにしない。

## 実践ゲート — 機能要望が来たときのチェックリスト

すべての機能要望・改善提案は、実装前に以下を順に通す。途中で止まったら実装しない。

```
□ ① この要件の責任者（個人名）は誰か。業務上の目的で記述されているか。
□ ① この業務工程は、そもそも存在すべきか。
□ ② この機能で削除できる工程・画面・入力・二重管理は何か。
      追加だけで削除がゼロなら、本当に必要か再検討したか。
□ ③ 残った工程は最少の操作数か。入力を選択・自動補完・デフォルト値に置き換えたか。
□ ④ どのメトリクス（所要時間・操作数）が改善されるか。改善を測定できるか。
□ ⑤ 自動化する場合、手動プロセスとして検証済みか。停止手段と失敗通知はあるか。
```

## アンチパターン（禁止事項）

| アンチパターン | なぜ禁止か |
|---|---|
| 紙業務・Excel 業務の忠実なデジタル化 | 存在すべきでない工程の固定化（①違反） |
| 「あれば便利」機能の追加 | 要件なき実装。削除対象の自己生産（①②違反） |
| 二重入力・二重管理を許容する設計 | 必ず不整合を生む。payment_method の教訓（②違反） |
| 確認ダイアログだけを安全性の成立根拠にする | 不可逆操作はサーバー側ロック・状態検証・Undo/補償経路で守る。ダイアログは補助的な明示同意に限定する（③違反） |
| 全件一覧を人間に目視させる運用 | 例外抽出をシステムがやるべき仕事の放棄（③違反） |
| 検証されていない業務ルールの自動化 | 欠陥の高速再生産（⑤違反） |
| 停止手段・失敗通知のない自動処理 | サイレント障害の温床（⑤違反） |

---

## 本書の使い方

- 新機能の Issue・PRD・仕様議論では、本書のチェックリストを通過させてから実装計画に進む。
- 「臨床の安全」（SPECIFICATION 2.1）は本書に優先する。効率のために安全を削ることはしない。ただし安全対策の**手段**（ダイアログか、ロックか、物理ブロックか）は本書③の基準で選ぶ。
- 本書自体も①の対象である。運用して機能しない原則は削除・改訂する。
