### FAIL詳細①（S05 手順1・ケアプラン: 投薬/処置/持ち物タイプ）

**内容**: ケアプラン項目を type=「投薬」「処置・検査」「持ち物」で追加しようとすると、UIでは常に「入力値が正しくありません」というトーストが表示され追加が失敗する。type=「食事」「指示・その他」は正常に追加できる。

**再現手順**:
1. 入院詳細画面（`/hospitalization/{id}`）を開く
2. 新しいケアプラン項目を追加のセレクトで「投薬」を選び、名称を入力して「追加」を押す → 「入力値が正しくありません」
3. API直接検証（`POST /v1/hospitalizations/{id}/care-plan-items`、body: `{type, name, timing}`）で type を総当たりした結果:
   - `food` → 201 成功
   - `instruction` → 201 成功
   - `medicine` → 400「入力値が正しくありません」
   - `treatment` → 400「入力値が正しくありません」
   - `item` → 400「入力値が正しくありません」
   - 順序を入れ替えても再現性は同一（`food`/`instruction` のみ常に成功）
4. 意図的に無効な type（`bogus_invalid_type`）を送ると `"type は次のいずれかで指定してください: food, medicine, treatment, instruction, item"` という **異なる**（フィールド固有の）エラーメッセージが返るため、`medicine`/`treatment`/`item` の失敗はバリデーションエラーではなく、それより後段（DB挿入や別のエラー分類ロジック）で発生している一般化されたエラーであることを確認。

**根拠**: バックエンドの `care_plan_type` という DB enum、Go 側の `oneof=food medicine treatment instruction item` バリデーション定義、サービス層の `validateCarePlanType` はいずれも 5種類とも許可する定義になっており、コード上の定義だけでは原因を特定できなかった。実際に発生しているエラー経路（DB制約 or 別のフォールバック分岐）はログ確認（DB/バックエンドログ）が必要で、USER 側での追加調査を推奨する。

### FAIL詳細②（S05 手順3・ケアログ登録および再読込）

**内容**: デイリーカルテの「ケアログ」追加が **全ての種別で** HTTP 500（内部サーバーエラー）を返し、UIでも「サーバーエラーが発生しました。しばらく経ってから再度お試しください。」が表示される。加えて、正常に保存できたはずのバイタル記録も、ページを再読み込みすると「記録なし」に戻って見える。

**再現手順**:
1. 入院詳細画面でバイタルを1件追加 → 保存成功・即時表示される
2. 同画面をリロード（またはページ遷移して再度開く）→ バイタルが「記録なし」に戻って表示される
3. API直接検証: `GET /v1/hospitalizations/{id}/daily-records/{date}` → **HTTP 500「internal server error」**（バイタル追加は直前に成功しているにもかかわらず、日次記録の再取得自体が失敗する）
4. ケアログ追加: `POST /v1/hospitalizations/{id}/daily-records/{date}/care-logs`（body: `{time, type, value, notes}`）を type を総当たりで試行 → `food`/`excretion`/`medicine`/`treatment`/`other` の **全種別で HTTP 500「internal server error」**

**根拠**: 日次記録（daily-records）のGET取得自体が壊れているため、UI側でリロード後に空表示になる現象と、ケアログPOSTの全滅は同一の根本原因（daily_record 関連のサービス層・プリロード処理の不具合）である可能性が高い。優先度の高いバグ候補として記録。

## U-3（DB_RESET）後の再測結果（2026-07-17 メインセッション・API 直接検証）

**stale DB 仮説は両件とも棄却。実バグと実装ギャップが確定し、BUG-404 は即日修正済み。**

- **BUG-404 = 実バグ・修正完了**: 根因は `care_logs.time` / `staff_notes.time`（PostgreSQL TIME 型）を Go モデルが `time.Time` で受けていたこと。pg ドライバは TIME を string で返すため **書込は成功・読取が全て 500** になる（バイタル「消失」も同根 — 保存されているが読めない）。本リポジトリの TIME 列規約（clinic_settings 等は string）に揃えて修正。**テストが検出できなかった理由も特定**: 永続テスト DB が旧モデル時代の AutoMigrate で timestamptz 列のまま残り、本番 001（TIME）とドリフトしていた — テスト setup に冪等 ALTER の自己修復を追加。実機確認: GET 500→200 / care-log POST 500→201 / staff-note POST 201。
- **BUG-403 = FE 実装ギャップ（BE/DDL は設計どおり）**: 001 の CHECK 制約 `chk_care_plan_item_ref` が投薬=medicine_id・処置=procedure_id・持ち物=hospitalization_plan_id を必須としており（臨床的に妥当な設計）、`CarePlanTab/AddForm.tsx` にマスタ選択 UI が無く FK を送れないことが真因。API 層の型定義（care-plan-items.ts）には FK が存在する。修正方向 = AddForm/EditRow に type 連動のマスタ選択を追加 + BE エラーメッセージの具体化。
- 検証用テストデータ（入院 #1・ケアログ 2 件・申し送り 1 件、名称「再測」）は dev DB に残置 — 次回 reset で消える。
