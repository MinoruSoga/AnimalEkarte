# STG パフォーマンス測定チェックシート

> 用途: STG の画面操作・API応答・負荷時の状態を、同じ条件で測定・比較する。
> このファイルは未記入のテンプレート。チェック済み項目・承認・実測結果は含まない。

実施ごとに本書を `reports/uat-YYYY-MM-DD/performance/<RUN-ID>/checklist.md` へコピーする。結果は Git 管理せず、共有が必要な証跡は承認済みの保管先へ保存する。パスワード、token、cookie、個人・臨床情報を記入しない。画面画像、HAR、トレース、ログは保存前に機密情報を除去する。

状態は `未実施 / PASS / FAIL / BLOCKED / SKIP / UNKNOWN`。SKIP・BLOCKEDには理由を書く。チェック欄は実施・確認後だけ埋める。未測定をゼロやPASSとして扱わない。

関連: [測定手段と制約](PERFORMANCE_PROFILING.md)、[k6ガイド](../../../load-tests/README.md)、[STG運用](../deploy/STG-CONTINUOUS-OPERATIONS.md)。本書はUAT全体・本番性能・リリースの合格判定を代替しない。

## 2. 合否基準と中止条件

業務上の基準は測定前に合意する。下表の数値は提案例であり、空欄の採用値を自動的に補完しない。既存文書の画面操作時間も承認済みSLOではない。

| 指標・適用範囲 | 提案例 | 今回の採用値・集計方法 | 合意者・記録 |
|:---|:---|:---|:---|
| 通常稼働中の主要API | API別p95 < 500 ms、p99 < 1,000 ms | | |
| 認証付き画面の初回表示 | 操作可能になるまで1.5秒以内 | | |
| 検索 | debounce終了後200 ms以内 | | |
| 保存 | クリックから保存完了表示まで1秒以内 | | |
| 通常負荷の失敗率 | HTTP失敗率 < 1%、業務チェック成功率も評価 | | |
| ピーク後の回復 | 指定時間内に基準負荷の応答時間へ戻る | | |

初回表示・少数回の操作は各回の実測値を記録する。少数サンプルのp95/p99を多数リクエストの統計と同等に扱わない。

| 中止条件 | 提案例 | 採用値・観測窓 | 停止担当・手段 |
|:---|:---|:---|:---|
| サーバーエラー | 5xxが直近1分で1%超 | | |
| 応答悪化 | 主要APIが連続して3秒超 | | |
| リソース・接続障害 | DB接続枯渇、OOM、再起動の反復 | | |
| 他利用者・データへの影響 | 業務阻害、想定外の書込・外部送信 | | |
| 時間・利用量 | 承認時間または負荷・費用上限に到達 | | |

- [ ] 指標の測定開始・終了点と、集計対象のAPI・時間帯を決めた。
- [ ] 中止を判断できる監視間隔・ログ・メトリクスがある。
- [ ] k6の終了時の合否閾値と、途中停止条件を区別した。
- [ ] 手動停止方法を確認した。自動停止を使う場合は設定と評価間隔を検証した。

既存STGスクリプトのthresholdsは全体p95 < 3,000 ms、HTTP失敗率 < 5%、カスタムerrors < 5%。errorsにはクリニック取得の時間超過も含む。コールドスタートを考慮した観測用設定であり、業務上の合否基準とは別扱いとする。現行コードに `abortOnFail` はない。追加する場合も、累積メトリクスの判定を「直近1分」の監視と混同しない。

## 4. k6負荷測定

既存の [STG専用スクリプト](../../../load-tests/k6-cf-stg-sustained.js) は、30秒で3VUへ増加、9分保持、30秒で0VUへ減少する。対象は `/health` と `GET /api/v1/clinics`。setupで1回ログインし、全VUが同一セッションを共有するため、複数スタッフ・複数clinicの再現には追加設計が必要。

- [ ] Dockerで実行するスクリプト、明示的なBASE_URL、負荷設定を確認した。
- [ ] 認証はSTG専用の `STG_DEMO_EMAIL` / `STG_DEMO_PASSWORD` を安全に環境変数へ渡す。値は記録しない。
- [ ] スクリプト内のstagesと、今回の承認負荷が一致している。初期設定の変更が必要なら実行前に準備した。
- [ ] ログイン成功、認証付きAPIの200応答、期待する内容の取得を確認した。
- [ ] 高頻度の再ログインを避けた。401・403・429を性能成功として扱わない。
- [ ] VU数と実測RPSを両方記録する。VUは仮想ユーザー数であり、RPSではない。
- [ ] p50/p95/p99の出力と、段階別・API別に集計可能な記録方法を準備した。
- [ ] 結果は実行ごとの書込可能な専用ディレクトリへ保存する。既存の固定名 `results-cf-stg-sustained.json` を別runで上書きしない。
- [ ] summary、必要な時系列、標準出力、終了コードを保存する。総リクエスト数・iterations・checksが0なら合格にしない。

既存スクリプトのカスタム標準出力にはp99がない。p99が必要ならk6のsummary trend stats等を実行前に設定し、保存結果に含まれることを確認する。全実行のsummaryだけでは段階別の評価はできない。
