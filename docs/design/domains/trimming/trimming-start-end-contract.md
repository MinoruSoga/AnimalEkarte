Start does not require actual performer or nonempty performed lines. The trimming branch does not require medical-records:create and creates zero ordinary medical records. ### 3.1 Selected lifecycle fingerprint profile, separate from 480 booking

This section is a **new finite technical selection** in this document; the existing 480 booking contract did not select it. Supply and implementation remain outstanding. Do not hash booking_changes or use the booking schema tag for lifecycle commands.

- Start canonical projection has exactly `{schema,intent,appointment_id,prepared_record_ref}`. schema literal=`trimming-lifecycle.start.v1`; intent literal=`reservation.start_consultation`; appointment_id is the path's canonical decimal string. prepared_record_ref has exactly `{owner,kind,id,revision}` using the typed literals and canonical positive decimal strings above.
- End canonical projection has exactly `{schema,intent,appointment_id,record_ref,confirmed}`. schema literal=`trimming-lifecycle.end.v1`; intent literal=`reservation.end_consultation`; appointment_id is the canonical path string; record_ref is the exact typed object above; confirmed is JSON boolean true, not a string or number.
- No optional projection keys and no nulls. Reject unknown or duplicate keys in the source request and nested refs before canonicalization. Reject ID strings with whitespace, sign, leading zero or out-of-range values; do not silently coerce them. Owner/kind/schema/intent must match exact literals. There are no floating point numbers, timestamps, free text or arrays in either profile.
- Serialize the validated closed projection with RFC 8785 JCS, UTF-8 encode the canonical bytes and SHA-256 them; payload_sha256 is exactly 64 lowercase hexadecimal characters. No Unicode normalization, whitespace trimming or original raw-JSON-byte hashing. Object member order in the submitted request does not alter the digest. Apply reconstitutes only the same validated VerifiedCommand projection and checks this digest.
- C06 Content.Fields exact values: schema_version=`1` (string), resource_kind=`appointment` (string), target_ref=appointment_id canonical string, payload_sha256=the digest above. The typed detail ref is fully bound inside the digest, not compressed to a bare detail number. Scope owner_kind=`reservation`, trusted clinic/actor and exact intent remain C06 scope/fingerprint inputs, not user-controlled projection fields. This use of SHA-256 as payload digest does not replace C06's existing keyed HMAC or its key-management rules.
- Explicitly excluded from Content and digest: expected_version, prepare_receipt, operation key, current grants, client UI generation, transport headers and timestamps. expected_version is CAS-only Preconditions. The prepare receipt's exact UUID wire is specified in §3.2 (T05-PREP-01); its server-verified binding must equal the included prepared_record_ref before a first Apply can run. No invented parse/verify code is considered supplied here.
- Changing only request key order or refreshing the same-bound preparation evidence leaves Content unchanged. Changing appointment/detail identity, owner/kind, prepared/confirmed detail revision, or intent changes Content and cannot reuse the key. Ref revision remains business content even though it is also compared to the current locked revision. Start evidence refresh against a different record revision is a new command, not a CAS-only retry. Prior success replay is resolved with current original-target authorization before first-Apply preparation/CAS validation; it does not require rerunning preparation or issue another transition.
- Required deterministic fixtures (not executed): permuted JSON key order gives equal canonical bytes/hash; start/end tags differ; string `1` versus `01` rejects the latter before hashing; each typed-ref field change changes digest; CAS/token-only changes keep digest; source unknown fields reject; same key with changed typed revision conflicts; same key with refreshed evidence for the same ref can proceed only after evidence verification and current checks.

This selects the lifecycle canonicalization profile and §3.2 preparation-evidence design. Neither API/schema integration supply nor implementation is established by this document.

### 3.2 T05-PREP-01 selected preparation metadata proof

The investigation found no supplied implementation. This section **selects the concrete technical design**. API/auth integration acceptance, supply and implementation remain outstanding. Proposed choice: a small server-owned immutable metadata proof, issued alongside an authorized complete read, with no new signing key or general workflow service. Existing D01 current-state/read-success requirements are preserved; no new business gate, extra visible button, actual-performer prerequisite or fee prerequisite is introduced for start.

**Endpoint and authority.** Propose POST `/api/v1/reservations/{appointment_id}/trimming-start-preparations`, registered under the existing reservation routing owner. It only reads the explicit existing detail and writes preparation metadata. It never creates a reservation/detail/ordinary medical record, saves form edits or changes lifecycle. Strict request has exactly `{expected_version,record_ref}`; expected_version and record_ref.revision are positive canonical signed-int64 decimal strings, and record_ref has the exact four fields/literals from §3. All nested unknown/duplicate fields rejected, no nulls, zero, negative, leading-zero, whitespace, sign, numeric JSON ID, or unknown owner/kind. Body clinic/pet/actor/status fields are forbidden. Reuse trusted authenticated staff context and the same approved composed start authority/current trimming:view scope, rather than a new permission. The final composed authority remains the separate API/auth mapping proposal in §5.

**Complete response profile.** Successful HTTP 200 body has exactly `{prepare_receipt,record}`. prepare_receipt is a server-generated lowercase RFC4122 UUIDv4 string, nonnil; it is an identifier, not a bearer credential or client-generated UUID. record exact keys are `{schema,appointment_id,appointment_version,record_ref,detail_values,lines}`; schema=`trimming-start-read.v1`. appointment_id/version and typed ref equal the validated current target; detail_values is the full saved T4 schema1 or proposed schema2 object from §4/482 §3, with schema-discriminated strict decoding, never a partial UI cache. lines is the complete current T4 line array using 482 §3's exact GET element `{source_line_id,master,adopted_master,input,tax_input}` and nested closed types, sorted by numeric source_line_id. Nullability and canonical exact-decimal values are exactly those selected T4 types; an empty stored set is valid for start and must match line_count. Unknown price/tax values stay null/unknown and do not block start. Schema1's absent actual performer remains unknown, not injected as an actor; schema2 permits explicit null. Unknown schema or impossible scope/count/identity is an error, not an empty record.

The read returns persisted image reference strings exactly as the existing authorized record DTO, not newly inferred image content. Loading optional image blobs is not a new start requirement. This proof certifies successful authorization, target resolution, complete database projection decoding/validation and response serialization on the server. It cannot prove human reading, actual display or successful optional image download. The supported client waits for the complete HTTP response, validates all expected fields and matching context, then invokes start within the same button flow; it must not call start from a partial/aborted/failed response, stale cache or an isolated token. No `read_ok:true` claim is trusted by the server.

**Issuer consistency and ordering.** Obtain current authorization and the appointment/detail/full source set in one owner-controlled consistent database snapshot. Scope is the original appointment and explicit detail, never a latest-by-pet search. Verify expected appointment version and exact current detail revision. Existing reader adapter assembles and strictly validates the entire response record, JCS-serializes that record and computes SHA-256 of those UTF-8 bytes. Only after serialization succeeds may it issue and insert the proof metadata. Retain the exact serialized record bytes for this response; do not fetch a different current version after issuance. Proof insertion occurs in the same short read/metadata transaction so a failed insert/commit returns no successful preparation. Holding ordinary short server read/metadata transaction locks is not waiting on a client; finish the transaction before returning and retain no database lock across the user's read/start interval. A concurrent dependency change after the snapshot is deliberately caught at start, not prevented by a long read lock. This proof transaction has no domain mutation or C06 claim/Execute; its metadata insert must not acquire new FK locks back into appointment/detail after later owner locks.

**Selected necessary storage design, not implemented.** Add `reservation_trimming_start_proofs` under 468/446 ownership if no equivalent accepted store is found at implementation reconciliation. Columns: `clinic_id bigint NOT NULL`, `proof_id uuid NOT NULL`, `actor_kind text NOT NULL CHECK(actor_kind='staff')`, `actor_ref bigint NOT NULL CHECK(actor_ref>0)`, `appointment_id bigint NOT NULL CHECK>0`, `appointment_version bigint NOT NULL CHECK>0`, `pet_id bigint NOT NULL CHECK>0`, `detail_id bigint NOT NULL CHECK>0`, `detail_revision bigint NOT NULL CHECK>0`, `record_owner text NOT NULL CHECK='trimming'`, `record_kind text NOT NULL CHECK='appointment_trimming_detail'`, `read_profile text NOT NULL CHECK='trimming-start-read.v1'`, `projection_sha256 bytea NOT NULL CHECK(octet_length=32)`, `issued_at timestamptz NOT NULL DEFAULT clock_timestamp()`. Primary key `(clinic_id,proof_id)`; proof_id rejects the nil UUID. No user content, prices, secret, complete record payload, generated signing key, mutable used/expired flag or second operation receipt is stored. Server IDs are uint64 only after signed-int64 range validation; UUID wire must match canonical lowercase serialization exactly.

Use clinic-scoped RLS and explicit clinic predicate; trusted actor must match on every read. Metadata references are intentionally logical immutable anchors, not new business-row FKs to appointments/details/staff, avoiding accidental history deletion/blocking-edge changes and proof insert deadlocks. Existence, staff membership, clinic/pet/detail ownership and versions are verified by the owner reader on issue and under normal owner protection on start. If existing platform schema requires a clinic FK, 446 must integrate its known safe order; no other business-row FK is implicitly selected here. Append-only INSERT, reject UPDATE/DELETE for ordinary application role, no expiry purge/background job. Retention follows existing no-automatic-delete policy; this proposal does not decide a retention period. No live schema operation is authorized.

**Start verification.** §3's prepare_receipt is now concretely a required canonical nonnil UUID string. Parse it but do not include it in Content/hash; it is a replaceable same-bound evidence precondition. On a first Apply, after current original-target authorization and standard graph/binding/lower locks, fetch the proof by authenticated clinic and UUID, check actor_kind/ref and every bound identity/version/profile. Server reconstructs the full current record projection with the same reader/schema, digest and stable ordering and compares projection_sha256. Check current appointment version equals both request expected_version and stored appointment_version; current T4 revision equals both command prepared_record_ref.revision and proof detail_revision; clinic/pet/appointment/detail/owner/kind all match. Any change, including identity reassignment, causes rejection. Price-only detail revision changes also require re-read because the explicit prepared record changed, not because price readiness is a new gate. Current grant/state/transition/clinic and safety guards remain mandatory and cannot be waived by a matching proof.

**同一readの再利用identity。** DBにUNIQUE(clinic_id,actor_kind,actor_ref,appointment_id,appointment_version,pet_id,detail_id,detail_revision,record_owner,record_kind,read_profile)を置く。projection_sha256は一意キーに含めず、その唯一行のimmutable保存値として比較する。同じ保存versionで異digestの並行要求も別行/別UUIDを作れない。現在認可付き完全read/validation/serialization後、同binding組かつ保存digest一致の既存proofがあればそのUUIDを返し、なければINSERTする。unique競合時は保存済み全binding/digest一致を読戻して同UUIDへ解決する。UPDATE上書きやactorを跨ぐ再利用をしない。同じ保存version/identityで異digestは既定の整合違反として失敗し、新proofを増やして回避しない。

lost response/abandoned/repeat readは同じ版/内容につき同actor一行。版変更に伴う本当の履歴増加と同一要求の無限増殖を分離する。TTL/通常purge/保持期限は追加せず、現在認可/版/identity再検査とsame-key成功replay先行を維持する。

**Reuse, staleness and atomicity.** No arbitrary TTL is added. A proof is usable only while all bound current versions/identities/profile and current authorization still match. Immutability means no consume step: duplicate same-key start resolves the C06 success before proof/CAS validation and does not transition again. A different key with the same proof must pass current status/version checks; the first successful start advances appointment version and invalidates fresh Apply with that proof. Undo/reopen advances version and cannot resurrect it. Proof refresh for the same typed record/appointment version leaves business Content unchanged and may replace Preconditions while the start operation has not succeeded. A changed typed record revision changes Content and requires new explicit preparation/command; never silently reuse the original operation key with changed Content.

The proof row is read inside the start transaction but never mutated. Start event, appointment version, mandatory audit and C06 result still commit atomically. Success replay/lookup reauthorizes original targets first and does not require the old proof to remain fetchable; its result is historical, current state separate. This protects receipt replay from proof loss without accepting missing proof for a new first Apply.

**Failures and recovery.** Prepare: invalid JSON/type/profile input 400; unauthenticated 401; current grant failure 403; absent/cross-scope explicit target 404 without foreign details; target current-version mismatch 409 using existing conflict envelope; read/decode/serialization/metadata-store/commit failure 503 generic evaluation-unavailable, no successful token/body. Lost prepare response or uncertain metadata commit may be retried as the same explicit read: the verified same-identity lookup/UNIQUE resolves to the existing proof UUID, without another metadata row or any lifecycle effect. It is not an invitation to retry unknown start. No idempotency key is needed for this read-plus-proof operation; it must never invoke the lifecycle command as a side effect.

Start first Apply: malformed token 400; no current authority 403 before proof detail disclosure; missing proof, wrong actor/scope/profile or mismatched target is non-disclosing 409 dependency-changed with no foreign refs; expected/current version mismatch uses existing version-conflict; changed digest/dependency uses dependency-changed; proof-store read error is 503 result-unavailable, not missing-proof success. UI keeps input and re-prepares only after the original start outcome is known not to have committed. Timeout/202/503/unknown start always checks its original C06 key first. Recorded unknown stays stopped; a new proof/new key does not bypass it. Lookup not-succeeded is not by itself permission to create another lifecycle operation. After a confirmed no-write rejection, re-read/re-prepare and retry the same key only if canonical Content is unchanged; otherwise the user-visible current target must be reconfirmed under a new command. Revoked actor cannot recover by borrowing another actor's proof.

**Required proof-specific fixtures (NOT_RUN).** Complete schema1 read and start without performer; schema2 null performer start; empty source set; inconsistent line_count; missing/unknown detail; receipt issue after serialization only; cross-actor/clinic UUID replay; fabricated UUID and client hash; changed appointment version/pet/detail/source revision; same-version projection drift rejected; deleted proof on first Apply versus successful replay; lost prepare response creates metadata only; aborted client read never calls start; unknown start then re-prepare cannot create a second Apply; re-open old proof invalid; two keys one proof yield at most one transition; grant revocation between issue and Apply/replay. 同一read再送/abandon/並行INSERTは同actor同版同内容で同UUID一行、別actorは分離。同保存versionの異digestは失敗し新proofへ逃がさない。版変更だけは別の正当な履歴として区別する。

**Alternatives.** (1) Client-only digest/boolean is smaller but proves no server-issued authorized read and is rejected. (2) Signed stateless token removes storage but introduces signing/key rotation and expiry choices with no established reuse evidence; not chosen. (3) C06 success receipt as prepare proof conflates mutation completion and record read, and would require extra command semantics; not chosen. The small immutable metadata record plus existing reader/participant is the minimal proposal for this scope. This closes T05-PREP-01's technical design proposal, while API/auth acceptance, exact integration receipt, implementation and nine-AC verification remain outstanding. No all-541 Ready or activation claim follows.

Success returns exact C06 `{status,operation_key,result_refs,committed_versions,recorded_at}`. Proposed closed refs: `{appointment_id,appointment_change_event_id,record_owner,record_kind,detail_id,detail_revision_id}`; versions `{appointment,detail}`. All values strings, no 0 placeholders. Detail version is the observed confirmed immutable revision, not an invented mutation from end. Add a narrowly typed adapter where C06 string maps require it, without modifying every consumer. operation_key is not the database operation_id: event and operation binding ID are stored/linked internally and lookup resolves that relationship.

Current state is a **separate read**, not recomputed into original receipt: current appointment version/status, current detail revision, and effective end operation/event identity or null. An undo/reopen/new lifecycle event makes the earlier receipt historical; receipt success alone never means currently ended. Returned original result remains immutable. Source detail GET is separately authorized; operation read does not leak body.

Use existing 480 C06 transport mapping: succeeded/replayed 200; validation 400; version-conflict/dependency-changed/edit-right-lost/operation-key-conflict 409; operation-in-progress 202; scope-not-found 404; not-authorized 403; result-unavailable 503; not-succeeded 200. Non-success carries only status/key. Unknown, 202, timeout, 503 or not-succeeded is not permission to generate a new key. No new reason-code vocabulary is asserted selected here.
