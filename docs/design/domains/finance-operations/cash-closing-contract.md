Digest is lowercase 64 hex. UTC time is RFC3339 with six fractional digits; business date is a separate JST date. Operation UUID uses existing C06 strict lowercase hyphenated parser. ### 2.2 Closed status and HTTP mapping (review correction)

Failure/non-success body remains exactly `{status, operation_key}`. No success fields, null success object, internal DB text or other-clinic identity. `operation_key` is the validated caller key when available; otherwise null. Successful result/detail shapes are defined separately. The complete non-success status set is:
`not-succeeded`, `operation-in-progress`, `result-unavailable`, `operation-key-conflict`, `scope-not-found`, `not-authorized`, `edit-right-lost`, `validation`, `version-conflict`, `dependency-changed`, `already-closed`, `source-incomplete`, `invalid-request`, `authentication-required`, `target-not-found`, `history-basis-unavailable`, `internal-error`.

| Status / source | HTTP | Exact response/recovery meaning |
|---|---:|---|
| C06 GET `not-succeeded` | 200 | Binding exists and helper lock/recheck establishes no success. This is NOT a success receipt. No automatic retry; human reviews current preconditions then same key/same content may be resent. |
| C06 `operation-in-progress` | 202 | Same actor/clinic/key lookup under current view. No new key or success banner. |
| C06 `result-unavailable` | 503 | Durable unknown/conservative stop; existing result reconciliation only, no automatic compensation/re-close/new key. |
| C06 `operation-key-conflict` | 409 | Original target current authorization first, no receipt disclosure, no re-execution. |
| C06 `scope-not-found` | 404 | Exact scope lookup miss, not proof of no other-scope operation or no real cash fact. |
| C06 `not-authorized` / `edit-right-lost` | 403 | Current authorization denied, no result/hidden-target leak. |
| C06 `validation` | 400 | Definite domain rejection with no committed close. Correct facts, do not treat as successful close. |
| C06 `version-conflict` / `dependency-changed` | 409 | No effect. Repreview and human review before same-content/same-key precondition update. |
| Owner `already-closed` | 409 | Another binding already closed this scope. No duplicate or update. Detail only via independently authorized read. |
| Owner `source-incomplete` | 409 | Known incomplete source/opening/boundary or projection coverage blocks close. Repair/reconcile then fresh preview; no fall back to old aggregate. |
| Parser/query `invalid-request` | 400 | Malformed/duplicate/extra fields, invalid UUID/lexeme/query. Invalid key is never echoed; key=null if parsing did not establish it. |
| Middleware `authentication-required` | 401 | Unauthenticated, no operation or target disclosure. |
| Middleware `not-authorized` | 403 | No current clinic membership/grant, no C06 result disclosure. |
| Reader `target-not-found` | 404 | No accessible close in authorized scope; same non-disclosing response for another-clinic selector. |
| Reader `history-basis-unavailable` | 409 | Provenance/context cannot support requested basis, or source-late view requested for legacy. Preserve original, no synthetic data. |
| Unexpected store/read/serialization `internal-error` | 500 | Not a 404 or zero-value preview, not proof transaction failed; after POST uncertainty retain key and use C06 lookup. |

C06 owner rejections support only their existing typed statuses. `already-closed` and `source-incomplete` are owner-adapter public refinements of an existing `dependency-changed` rejection, carried only in the owner's validated error mapping; they do not add statuses to the shared operation package or attempt storage. A later common Lookup may report `not-succeeded`, not necessarily the original refined rejection. `history-basis-unavailable` is read-adapter-only. Successful POST remains 201 succeeded / 200 replayed; successful lookup 200 succeeded. Successful preview/detail/list 200 is a read, not an operation success, and preview completeness still controls whether it can be closed. This bounded mapping reuses [C06 status definitions](https://github.com/MinoruSoga/AnimalEkarte/blob/cff4debe2e4620584e3afc4faaabea370afc7d37/backend/internal/operation/contract.go#L102-L138) and the selected 464 error/retry model; no second receipt framework.

<a id="cash-closing-source-completeness"></a>
## 4. Source completeness and exact finite adapter

A1 accepts the two selected 464-R1 `owner-deposit-source/v1` forms exactly as §8 of the merged contract, including its fixed 22-field digest object, 14-field context, UTC6 encoding, typed refs and actual-vs-allocation split. Do NOT create a third cash source from the deposit entry. Actual receipt fund source contributes A once; deposit allocation contributes zero. Noncash receipt contributes zero cash. Do not rehash with a newly invented 509 representation or change producer digest.

The consumer internally reads canonical rows and authoritative origin rows, not an externally callable arbitrary source-ingestion POST. Validate saved raw32 digest by each producer's versioned encoder, all required refs/same clinic, amount relationships, source version, original origin coverage and producer schema eligibility. Unsupported schema/family is incomplete, even when cash delta appears zero. R1 must validate the paired allocation and origin/entry relationship from its immutable context. Existing same source ID+same digest ingestion is no-op; mismatch is conflict, not UPDATE. `finance_event_ingestions` identity remains `(clinic_id,'closing',source_event_id)`.

Completeness is NOT `MAX(id)` or “all currently ingested rows”. Under one consistent snapshot and the participating writer fence, compare authoritative origin coverage to canonical source membership and ingestion membership. Every relevant origin has its required canonical source(s), every member has exact supported digest and same-clinic origin, and every selected source has exactly matching ingestion. Anti-join fund/event origin rows catches a missing source that reading finance_source_events alone cannot see. No runtime producer capability claims are inferred from docs or empty tables. Actual segment containing unsupported existing funds/refunds/corrections is blocked; the adapter cannot declare them absent merely because their source producer is unfinished.

Finite unresolved-origin dependency: each participating source owner must provide a read-only `CheckClosingCoverage(clinic, start_at, end_at)` result with exactly `{complete, missing_origin_refs, unresolved_origin_refs, unsupported_origin_refs}`. Each reference is exactly `{owner_kind, origin_kind, origin_id, operation_binding_id, occurred_at}`; origin_id/binding_id/time are explicit null if not yet established, at least one identity is required. owner_kind is the declared producer family identifier; origin_kind is a closed enum per accepted adapter, not arbitrary fallback. For R1 these are `payment_fund`, `deposit_allocation`, and `receipt_operation`. Coverage includes canonical committed origins, expected paired origins and all unresolved operation/refund execution facts known to that source owner. Sticky unknown and independently evidenced pending actual-money operations are not automatically excluded. A bare claim is not an eternal financial blocker: C06 binding lock/recheck that returns not-succeeded after a never-applied claim, definite rejection, or rolled-back database-only Apply establishes no authoritative DB effect and may be excluded unless separate pending actual-money evidence exists. Do not treat an unlocked missing receipt as that proof. If persisted metadata cannot establish their occurred interval, conservatively return them for any requested segment of that clinic until the existing operation reconciliation determines whether an authoritative source is owed; do not infer time from recorded_at or current request. In particular the selected R1 owner-only claim anchor does not supply occurred_at, so sticky-unknown R1 bindings or independently evidenced unresolved actual-money operations need this conservative clinic-wide classification, not every unused/rejected binding. Definite no-effect outcomes may be excluded only using the source owner's explicit classification backed by the C06 locked result/unknown recheck, not missing source rows or a 404. A running participating writer keeps the upper gate; a durable unknown does not, so this coverage check remains necessary after gate acquisition. The interface/terminal-status mapping is a required 506/464 supply subset; it neither creates an external-money fact nor claims to prove absence of unrecorded physical cash. Missing coverage implementation means incomplete, not true. No new reconciliation table or public endpoint is required by this proposal.


Proposal avoids a new generation-head table: for immutable append-only eligible segment membership, `source_generation = source_event_count + 1`; `cash_adjustment_version = number of accepted replenish/collect sources`. Count is an opaque change token only, paired mandatorily with full digest and boundary/opening revisions. A generation is NOT max sequence ID, external watermark, upstream-completion proof, or global event revision. Changes of boundary may preserve count, so never compare generation alone. Maximum source count is DB int32 max; overflow incomplete. This selected meaning of the existing fields needs 509/446 implementation handoff; it is not a claim it is already implemented.

Source-set digest exact bytes: UTF-8/ASCII header `cash-close-source-set/v1\n`; for every member sorted by numeric source_event_id ascending, append canonical `id:source_version:lowerhex(content_digest)\n`; SHA256 raw32. No rows => hash of header, not a null/zero digest. Membership includes supported zero-movement source rows as well as cash rows. The stored `source_snapshot` has exact object `{schema,scope,boundary,source_basis,opening,cash_adjustment_version,totals}` (schema `cash-close-snapshot/v1`), with wire encodings above; source member rows persist separately in cash_close_source_events. No patient/owner names or arbitrary JSON are needed for this cash subset.

Opening must be an existing explicitly confirmed cash_opening_balances row with verified scope and revision. No automatic 0, no inferred previous closing amount, no “latest actual correction” rollover. Missing opening blocks this scope only. This design consumes opening/boundary/replenishment records; it does not invent an unselected writer API or business authorization for creating them.

<a id="cash-closing-lock-order"></a>
## 5. Serialization and identity order

Minimal reuse choice: 467's existing transaction gate identity `reservation-graph:write:v1` is the upper fence, because selected 464 already participates and its method/owner/account dependencies require it. Reuse same-namespace try/context/assert adapter selected by 464, not a second hash namespace. This is a bounded requirement for listed participating finance/settings/auth writers, NOT proof that every product writer is already gated or a proposal to lock all unrelated readers.

Existing lower cash lock identity remains `cash_register_close:clinic:<canonical clinic id>:date:<JST business YYYY-MM-DD>`, hashed by `hashtextextended(text,0)`. It serializes a day, but protection remains one period, never “any close means whole day closed”. Retain existing lower locks; do not replace correctness with hash uniqueness assumptions. Hash collisions only over-serialize. Add try-lock wrapper in same repository for C06 busy semantics rather than silently calling blocking lock a NOWAIT lock.

Total phases for this A2 family:
1. Separate metadata claim TX completes and releases its FK locks.

## 7. Late arrival and recovery decision table

- Source producer commits before A2: authoritative source is in the gated snapshot. If ingestion missing, preview says projection_missing; internal idempotent recovery fills projection, then user obtains/reviews fresh preview. A2 does not silently repair a changed expected set and close with old consent.
- Source accepted projection first and close second: source is in original membership once.
- Close commits first and genuinely later source commits for its stored interval: recovery inserts ingestion and cash_close_late_events to that original close, under source row lock and graph/date fence; original context/membership/totals untouched. Classification uses persisted close interval, not today's settings. If more than one stored interval matches, or a new boundary would overlap incompatible stored close scope, fail `source_scope_conflict`; do not guess a close or change occurred_at. Validate scope/boundary consistency before closing. No original source member may also be late.
- Duplicate notification/recovery: read canonical same ID/digest, existing assignment no-op. Same ID different digest or conflicting original/late target is a diagnostic stop, never delete/rewrite. Keep actual received money success even when its consumer projection fails.
- Source was authoritative before close but inexplicably absent from original snapshot: this is violated completeness, NOT ordinary late arrival. Stop recovery for that inconsistency and report source/close identity for reconciliation. Do not relabel corruption late merely because ingestion is late.
- Pending external financial outcome has no authoritative confirmed source: do not manufacture cash or report source completeness from a notification alone. Upstream owner must settle it; 509 does not call payment provider or create a compensating receipt.
- Existing close found with same key: stored result replay. Existing close with different key: `already-closed`, and current view required to show its detail. Never update original, cancel, reopen, or create an alternate close.

Ordering evidence for the “authoritative before close” distinction: source row `recorded_at` is NOT commit order and sequence IDs are NOT commit order. Classification uses the gate-protected A2 scan and immutable stored member set; recovery normally processes a source not present when A2 held gate as late. To distinguish a missed-before-close defect after the fact, require an additional minimal durable cutoff proof, not a wall-clock heuristic: proposed `source_snapshot.source_basis.cutoff_id` = maximum canonical finance_source_events ID for the clinic under gate, with all relevant source inserts required to allocate their ID only after taking that gate and commit before releasing it. The exact stored snapshot/public SourceBasis includes this value as `cutoff_id`; POST expected and committed_versions use `source_cutoff_id`. Preview obtains this value in its consistent snapshot, and A2 recomputes it under gate. A clinic source change outside the requested interval may conservatively invalidate the preview cutoff, requiring repreview rather than silent auto-refresh. Under this required ID-allocation rule, a row ID ≤ stored cutoff missing despite matching stored interval is inconsistent; > cutoff may be late. Sequence rollback gaps are permitted. Strict monotonic allocation is an explicit activation prerequisite: the finance_source_events sequence must use CACHE 1 / NO CYCLE, with no cached reservations, sequence rewind/setval, caller-supplied IDs or import insertion into this normal source table. Allocation occurs under the same gate. PostgreSQL sequence IDs with CACHE >1 can arrive out of numeric order even with this gate, so ordinary BIGSERIAL alone is not proof. 446/466 must supply the exact sequence configuration/allocator contract and operational exclusion evidence at the active schema revision; none was verified against a live DB here. An out-of-gate/preallocated-ID/nonmonotonic producer invalidates this proof and blocks activation. This restriction concerns normal finance source publication, not authorization to alter existing sequences or migration data. IDs still do NOT prove source completeness; origin anti-join and digest remain required. This is a bounded addition to existing source identity, not a new queue/head/event table.
